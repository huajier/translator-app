## 一、已定

### D1 拷打强度 = 4（深挖）
**理由**：「乱七八糟」里混着三类完全不同的东西——垃圾（`.tmp`、`临时2`）、历史（`backup`、`release`）、真资产（`tessdata`、`语料`、探针源码）。清错一类就是事故，需要主动找边界情况。

### D2 决策记录位置 = `docs\decisions-cleanup.md`（本文件）
**理由**：最初约束是「只允许读取」，所以第一轮选择只贴对话；2026-10-23 用户放开写权限后落盘。不并入 `progress.md` 第三节，因为该文件已超自定的 500 行红线，且清理专项是一次性任务，不属于长期架构决策。

### D3 产出形态 = 清理方案，不直接执行
**理由**：2.3G 的问题是「怎么安全扔」，不是「怎么改代码」。用户要自己执行。
**变更**：2026-10-23 用户追加「允许删东西」，执行权开放，但方案本身仍是先看后动。

### D4 目标 = 体积优先，结构次之
**理由**：目录结构本身已经规范（`tools\说明.md` 有明确规则），乱的是执行——规则被违反，不是规则不存在。所以优先级是先把 2.3G 降下来。

### D5 `release\` 只留最新 2 版
**结论**：保留 `V0.3.4.3`（当前）+ `v0.3.4.2`（本机在跑），其余 9 版移出。
**理由**：每版 121M 里 91M 是同一份引擎（`x64\` 49M）+ `tessdata\` 42M，真正随版本变的 `TranslatorApp.dll` 只有 208K。11 版 = 同一份 91M 复制 11 遍。源码回滚能力由 84 个 git tag + GitHub 远程提供，二进制不需要留 11 份。
**依据**：`du -sh release/*` → 902M；`release\V0.3.4.3\` 内 x64 49M / tessdata 42M / Microsoft.Windows.SDK.NET.dll 24M / TranslatorApp.dll 208K。

### D6 `tools\探针\` 只清 `bin\obj`，源码全留
**结论**：删除 20 个 `bin`/`obj` 目录（约 500M），92 个 `.cs` 源码文件全部保留。
**理由**：探针的价值在源码里的断言和结论（E6末尾 72 条断言、折行对拍、真实数据 R12~R22），编译产物 `dotnet build` 随时重建。
**依据**：`tools\探针\` 总 510M；`bin`+`obj` 合计约 520M（含四舍五入）；源码仅 92 个文件。

### D7 日志分两类，只清运行日志
**结论**：`app-YYYYMMDD.log` 保留最近 7 天（10-17 起，42M），10-07~10-16 的 10 个（20M）移出；入库的 133 个证据文件（用户实测 76 / 实测期错例 11 / 取证截图 5 / 根目录 41 个 md）全部保留。
**理由**：运行日志可重生成且未入库（`.gitignore` 有 `*.log`）；验收证据不可重建，且 `progress.md` 明确要求判分时按日志三段配对还原顺序。
**依据**：`du -cm tools\日志\app-*.log` → 62M；旧 10 个 20M，近 7 天 42M。

### D8 处置方式：垃圾直删，历史先移后删
**结论**：A 类（构建产物、缓存、临时目录）直接删；B 类（旧发布版、安装包、实验素材、旧日志）移到 `D:\111Desktop\deepseek\_归档-翻译软件-20261023\`，放一个月再删。
**理由**：删和移的成本不同。可重建的删了无损失；不可判断是否还会用的，移走保留后悔药。

### D9 `backup\` 暂不动
**结论**：236M 保持原样，等用户单独拍板。
**理由**：用户答「说不清，先不动」。已查出的事实供后续决策：236M 里 230M 是**发布包**（`阶段3` 47M / `阶段3.1` 47M / `阶段3.1-final` 48M / `阶段3.2-553std` 90M，全是 exe+dll+tessdata+x64），真源码快照只有 7.4M（`阶段1` 1M / `阶段2` 3M / `阶段3-src` 1M / `阶段3.1-src` 1M / 2 个 zip 1.4M）。三份 47~48M 结构完全相同（5.0.0 引擎），是同一版三个副本。
**建议（待拍板）**：移走 `阶段3.1` + `阶段3.1-final`（95M），留 `阶段3`（最后一个 5.0.0 可运行回滚点）和 `阶段3.2-553std`（5.5.3 引擎）。

### D10 `.gitignore` 的「删了就没法回滚」注释已过时，但本次不改
**理由**：该注释写于没有远程的时候。现在有 `origin` = github.com/huajier/translator-app、84 个 tag、首次提交「阶段 0~3 首次入库」，源码回滚已由 git 保证。改它属于代码改动，与本次清理分开做。

### D11 `制作大纲.md` 重写成导航（204 行 → 103 行）
**结论**：只留「文档分工表 + 阶段总览 + 目录结构 + 六条最容易忘的约定」，删掉全死索引、过期三步走、与 `制作流程-AI版.md` 重复的九步流程、13 行全 ☐ 的进度表。
**理由**：状态信息只在 `progress.md` 一处维护，两份都写状态必然对不上——大纲原来就停在「等你填决策表，说开始阶段 0」，而项目已经走到 `V0.3.4.3`。地图只管「东西在哪」，不管「现在在哪」。
**依据**：原文件第 7 行状态过期；第 44~63 行 9 个链接全指向已归档的 `tools\归档\用户版-旧v1\`、`AI版-旧v1\`；第 67~85 行 v0.1→v2.0 与现行四位累加冲突；第 145~163 行进度表 13 行全 ☐。
**保留理由**：六条约定是真金（浏览器不许关、BOM、发布前归档实测记录），删了会重复踩坑。

### D12 `progress.md` 治超限：已结清待办整条搬进归档（562 → 444 行）
**结论**：21 条已办完的待办（2/3/5/7/8/9/11/12/15/17/18/19/20/21/22/24/31/32/33/37/40）原文一字未删搬进 `tools\日志\进度历史-归档.md` 新增的「五、已结清待办」节；`progress.md` 只留一行编号清单 + 指针。维护规矩补第 ⑤ 条：**结清的待办整条搬走，不许划线留着**。
**理由**：病根不是条目多，是**只进不出**——维护规矩原来只规定「每轮更新当前状态块 + 未完成代办」，没规定办完的搬去哪，于是 ✅ 划线的一条条堆在原地。
**依据**：562 行 > 第 20 行自定「超过 500 行就是又出毛病了」；「五、未完成代办」占 262 行（247~509 行）。
**做法要点**：**编号不重排**——别处靠「第 38 条」「第 1 条路二」互相引用，重排会全部指错。
**附带纠错**：第 20 条「无 git remote」已过时（`origin` 已加并推送 84 个 tag）；第 24 条「`Ctrl+Alt+D` 存图未正式验收」已过时（用户 m00217 确认验收过）。两条一并结清。

### D13 两个大档案都不动
**结论**：`docs\更新日志.md`（106KB / 28 节）和 `tools\日志\阶段3-验收.md`（581KB / 10516 行）保持原样。
**理由**：验收日志是「逐轮最权威记录」，`progress.md` 反复引用它的节号；更新日志是版本级索引。两者都是**追加型档案**，不进每轮必读路径，体积大不构成负担。真正压垮人的是 `progress.md` 这种「必读 + 只进不出」的文件。

### D14 顺序：先治文档，再清体积
**结论**：文档（D11、D12）先做，约 10 分钟；磁盘清理（A/B 类）后做。
**理由**：文档是「以后每轮都要读的东西」，先修好能立刻减负；磁盘清理要跑移动/删除命令，放后面不阻塞。
