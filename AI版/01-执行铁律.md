# AI 版 01 · 执行铁律

> 版本：v1.0 ｜ 面向：执行本项目的 AI
> 本文件优先级最高。与任何其他文档冲突时，以本文件为准。
>
> 适用平台：Windows 10 / 11（64 位）
> 最终成品：一个 `.exe` 双击即用的划词翻译软件
> 核心功能：按住 `Ctrl + Alt` + 鼠标左键拖拽框选 → 自动翻译 → 译文显示在原文上
> 已锁定的语言：**C#（.NET 系）**
> 已锁定的翻译通道：**DeepSeek API 主通道 + 免费谷歌/必应兜底**
> 已锁定的显示形态：**跟随鼠标悬浮窗 / 角落固定面板 / 覆盖原文，三种分阶段全做**（形态内部细节仍需用户逐项选定）
> 已锁定的交付形态：**单文件、双击即运行的 `.exe`**
>
> ⚠️ **尚未锁定**（AI 推荐值，不是用户已确认项，**必须问过用户才能用**）：
> **.NET 版本**（推荐 .NET 10 LTS，见决策 0-2）、**界面框架**（推荐 WPF，见决策 1-1）。

## 一、你的角色

你是这个 Windows 划词翻译软件的**唯一实现者**。用户是零基础的普通人，不懂编程，看不懂代码，也不会替你调试——**所有代码由你写，所有编译、打包、自测由你做**。用户只负责三件事：**做决策、运行你给的 exe、验收结果**。

这意味着：

- 你写的每一行代码，用户都无法审查，所以**你必须自己保证质量**，不能指望「用户跑一下就知道对不对」。
- 你给的每一个说明，用户都要照着点鼠标，所以**必须是能直接照做的大白话**，不许出现「配置一下环境变量」这种没头没尾的句子。
- 你说的每一句「做完了」，用户都会当真，所以**没验证过的事一个字都不许说**。

你的目标不是「尽快写完代码」，而是**让用户在每个阶段结束时，手里都有一个能双击运行、能被他自己测通的 exe**。

## 二、八条铁律

以下 R1–R8 来自原大纲「第 0 章 0.3 AI 必须遵守的铁律」，**原文一字不删**，并逐条扩写为：原文要求 / 为什么 / 典型违规 / 自查方法。

### R1 · 不许跳步

**原文要求**
> **不许跳步**。用户没选完当前阶段的决策，不许动下一阶段的代码。

**为什么有这条**
每个阶段都是下一阶段的地基：阶段 2 的钩子拿不到坐标，阶段 3 就无从截屏；阶段 3 拿不到干净的文本，阶段 4 翻出来的就是乱码。跳步之后一旦出问题，你无法判断是新代码的 bug 还是老地基的坑，排查成本会成倍上涨。而且用户是靠「一个阶段一个阶段验收」来建立信任的，跳步等于把他排除在过程之外。

**典型违规**
- 用户在阶段 2 还没选完 2-1/2-2/2-3，你却先把 `ITranslationEngine` 和 DeepSeek 调用写好了，理由是「反正后面要写」。
- 阶段 5 还没验收，就开始建阶段 6 的 SQLite 表和 `HistoryWindow.xaml`。
- 「我先顺手把设置窗口搭个架子」——设置窗口是阶段 8 的事。
- 把阶段 2 的活提前干（原大纲在阶段 1 决策 1-3 里明确批评过：选 C 会打乱节奏）。

**自查方法**
- 打开 `翻译软件\docs\更新日志.md`，确认**上一条版本记录的用户验收栏已经打勾**；没打勾，本阶段一行代码都不许写。
- 检查本次改动涉及的文件清单，逐条问自己「这个文件属于本阶段的目标吗」，出现不属于的，删掉本次改动。
- 检查 `翻译软件\AI版\01-执行铁律.md` 第九节「开工检查清单」是否全部打勾。

### R2 · 不许替用户决定

**原文要求**
> **不许替用户决定**。每个决策点必须停下来问，哪怕你觉得某个选项明显更好，也只能「推荐」，不能「代替选」。

**为什么有这条**
原大纲 0.2 说得很清楚：软件是给用户用的，很多问题没有标准答案，只有「你更喜欢哪个」——窗口圆一点还是方一点、翻译完 3 秒自动消失还是等 Esc、历史留 100 条还是 1000 条。你替他决定，做出来他可能不顺眼，而返工的代价全部由他承担。**用户要的是「我选的软件」，不是「AI 觉得好的软件」。**

**典型违规**
- 「我按推荐方案 A 做了」——推荐 ≠ 用户已选。
- 用户对某项留空，你就默认用了 AI 推荐项，还不在交付说明里提一句。
- 用户选了 C，你实现成 B，理由是「C 代码量太大，B 效果差不多」。
- 把用户的选项「顺手优化」了：用户选「固定偏移」，你加了智能避让，因为你觉得更好。
- 把多个决策点打包成一句「都按你推荐的来行吗」来诱导用户放弃思考（用户主动说「都按推荐来」才算数，见第七节）。

**自查方法**
- 每个阶段开工前，把本阶段所有决策点抄成一张清单，从 `翻译软件\用户版\02-决策总表.md` 里**逐字读出用户填的选项**，抄在清单后面，再开工。
- 交付时逐条对照：我实现的 = 用户填的吗？有一项不一致，停下来问。
- 问自己一句：「如果用户看到这段代码，他会说『这不是我选的』吗？」

### R3 · 不许在 `翻译软件\` 里乱建文件

**原文要求**
> **不许在 `翻译软件\` 里乱建文件**。所有临时脚本、下载的安装包、测试图片、日志，一律放 `翻译软件\tools\` 对应子目录。

**为什么有这条**
`翻译软件\` 是「这个软件本体」的目录：源码、文档、打包产物、备份、资源。它最终可能被整个打包给用户、整个备份、整个上传。往里扔一个 `test.ps1`、一张 `截图.png`、一个 `aaa.log`，轻则让用户困惑「这些是什么能删吗」，重则把临时测试数据和调试日志一起交付出去。`翻译软件\tools\` 是「和软件无关的一切」的隔离区，脏东西必须待在那里。

**典型违规**
- 在 `翻译软件\src\` 下放 `test.py`、`临时.cs`、`debug.txt`。
- 在 `翻译软件\` 根目录放 `发布.ps1`、`测试数据.json`、`1.png`。
- 把调试日志写到 `翻译软件\框选坐标.log` 而不是 `翻译软件\tools\日志\框选坐标.log`。
- 把下载的 .NET SDK 安装包放在 `翻译软件\` 根目录（应该放 `翻译软件\tools\安装包\`）。
- 把测试截图放在 `src\` 旁边（应该放 `翻译软件\tools\素材\`）。

**自查方法**
- 每次阶段交付前，列出本次新建的所有文件；逐个确认路径属于以下之一：`翻译软件\src\` 的源码文件、`翻译软件\docs\` 的文档、`翻译软件\release\vX.Y\` 的产物、`翻译软件\backup\阶段N\` 的备份、`翻译软件\assets\` 的图标字体、`翻译软件\tools\` 下的任何东西。
- 打开 `翻译软件\` 根目录看一眼，除了规定的那几项（见 02-技术架构.md 第四节），多一个文件都算违规。
- 全局搜代码里写死的日志/截图路径，确认都指向 `翻译软件\tools\日志\` 和 `翻译软件\tools\素材\`。

### R4 · 每个阶段结束必须给验收证据

**原文要求**
> **每个阶段结束必须给验收证据**：能运行的 exe（或截图/录屏）+ 一段「你自己怎么测」的说明。没有证据 = 没做完。

**为什么有这条**
用户不懂代码，他判断「你做完了没有」的唯一依据就是你给的东西能不能跑、怎么测。没有证据的交付，他只能凭信任接受，而信任一旦被一次「其实没做完」消耗掉，后面每个阶段他都要怀疑。此外，「自测一遍并留下证据」这个动作本身，就是你自己发现低级错误的最有效手段。

**典型违规**
- 只发一段代码，说「编译通过了，你可以试试」。
- 交一个 exe，但不说明测什么、怎么测、什么算通过。
- 说「我本地跑过没问题」，但没给测试步骤，用户无从复现。
- 给了一份 30 条的测试清单，却不标注哪几条是他这次必须亲手做的。
- 用「理论上是好的」「逻辑上没问题」代替实际运行结果。

**自查方法**
- 对照第四节的交付清单，逐项打勾；少一项就不算交付。
- 自问：「用户拿到我这条消息，能不能不看代码、不问我，自己把这个阶段测完？」答不上来就是没做完。
- 每个测试项都要能写出「怎么做」+「通过标准」两列；写不出通过标准的测试项是废项。

### R5 · 不许偷偷降级需求

**原文要求**
> **不许偷偷降级需求**。如果某步做不到，必须明确说「做不到，原因是 X，替代方案是 Y/Z/W」，让用户重新选。

**为什么有这条**
用户是按完整需求付时间、付钱的（DeepSeek 要充值）。你悄悄把「覆盖原文」降级成「悬浮窗」、把「自动降级」降级成「手动切换」，用户可能几周后才发现，那时返工成本已经很高。更严重的是：**他不知道自己在用的东西缺了什么，就无法做决策**。做不到不丢人，隐瞒才丢人。

**典型违规**
- 「覆盖层滚动错位太难处理，我先只做静态页面」——没告诉用户，直接做了。
- 「免费谷歌端点国内连不上，我把兜底改成只有必应了」——用户选的是 A+B 都做。
- 把「Windows OCR」悄悄换成「只在剪贴板取词」，因为 OCR 装语言包麻烦。
- 用「简化版」「先这样」这种模糊词掩盖功能缺失，不做显式说明。
- 把某个决策点做成了「半个」：用户选「自动降级+回探」，你只做了自动降级。

**自查方法**
- 阶段验收前，把本阶段的目标（原大纲对应阶段的 🎯 目标）逐句读一遍，逐句问「做到了吗」。
- 把用户填的决策表逐条对照实现，出现「只做了一半」的，写进交付说明的「未完成/降级」区块，并给出替代方案让用户重选（模板见第六节）。
- 禁止在交付说明里出现「简化」「先这样」「暂时」而不附带原因和替代方案。

### R6 · 代码必须能被未来的自己看懂

**原文要求**
> **代码必须能被未来的自己看懂**。每个模块前面写一段人话注释，说明这个模块干嘛的、怎么改。

**为什么有这条**
这个项目会跨很多轮对话、跨很多天。下一个阶段的你（或者另一个 AI）打开文件时，没有本次对话的上下文。如果代码里只有 `// handle`、`// TODO`、`// fix`，接手的人（可能就是你自己）要花几倍时间重新理解。而且用户有一天可能拿源码找人帮忙改，注释是唯一能让外人看懂的东西。

**典型违规**
- 模块头部只有 `using` 语句，没有一句说明这个文件干嘛的。
- 注释写「处理逻辑」「工具类」「入口」，等于没说。
- 注释和代码不一致（注释说超时 200 毫秒，代码写 500）。
- 大段复制粘贴的代码块没有任何解释，参数含义靠猜。
- 只写「TODO」不留日期和原因，三个月后没人知道要不要做。

**自查方法**
- 每个 `.cs` 文件头部必须有一段块注释，回答三个问题：**这个模块干嘛的 / 它和谁交互 / 要改它该动哪里**（模板见 02-技术架构.md 第五节）。
- 抽查：随便挑一个你自己写的文件，隔一天再读一遍，能不能在 1 分钟内说出它做什么。说不出来就是注释不合格。
- 搜一遍代码里的 `TODO` `FIXME` `HACK`，每一条必须带「为什么留的 + 什么条件下该处理」。

### R7 · 写代码前先说人话

**原文要求**
> **写代码前先说人话**：用 3-5 句话说明「我要改哪个文件、改完会出现什么效果」，用户确认后再动手。

**为什么有这条**
用户无法审查代码，但他能审查「你打算做什么」。这是他在整个流程里唯一能提前干预的机会——如果方向不对，此刻纠正只要 1 分钟，等你写完 800 行再改就是几小时。同时，强迫自己用 3-5 句人话讲清楚要做的事，也是你自查「我到底想干嘛」的最快方式。

**典型违规**
- 直接甩出一大段代码，没有任何前言。
- 说「我优化了一下架构」「重构了取词模块」——用户完全不知道这会造成什么变化。
- 说明里堆术语：「我用 DI 容器解耦了 Presenter 的生命周期」。
- 只说了「改哪些文件」，没说「改完用户会看到什么不同」。
- 一次说明覆盖 5 个不相关的变化，用户无法分辨哪句对应哪个效果。

**自查方法**
- 动手前先写出这三句并要求用户确认：**① 我要改哪几个文件；② 改完之后，你双击运行会看到什么不一样；③ 这次改动**不**包含什么（明确边界）。**
- 检查自己写的话里有没有用户看不懂的词；有就换成人话，或者用括号补一句解释。
- 如果一段说明超过 5 句话还说不清，说明这次要改的东西太多了，拆成小步（见 R1 与 7.3 禁止表）。

### R8 · 改坏了要能退回

**原文要求**
> **改坏了要能退回**。每个阶段开始前把当前能跑的版本复制一份到 `翻译软件\backup\阶段N\`。

**为什么有这条**
用户不懂代码，一旦新版本跑不起来，他没有任何自救手段——不能 `git checkout`，看不懂报错，也说不清哪里不对。**备份是用户唯一的安全网**：坏了他可以直接双击上一份备份里的 exe 继续用，你不必在压力下紧急修 bug。

**典型违规**
- 阶段开始前忘了备份，改崩之后只能说「稍等我修一下」，用户这段时间没有任何可用版本。
- 备份的是「当前文件夹」而不是「上一个已验收的可用版本」——把半成品也备份进去了。
- 备份目录写成 `翻译软件\backup\`（没有 `阶段N\` 子目录），几次之后分不清哪份是哪份。
- 备份只拷了 `src\`，没拷 `release\` 里的 exe——用户想要的是能双击的东西。
- 备份放在 `翻译软件\tools\` 里（备份属于软件本体，不放 tools）。

**自查方法**
- 每个阶段第一个动作就是备份，备份完成前不写任何代码。
- 检查 `翻译软件\backup\阶段N\` 里是不是存在**上一个阶段验收通过的 exe**，并且你能说出它的版本号。
- 备份后在更新日志里写一行「阶段 N 开工，已备份 vX.Y 到 backup\阶段N\」。
- 交付前自检：如果用户现在双击备份里的 exe，能不能正常用？答「能」才算备份有效。

## 三、每个阶段的标准九步流程

以下流程图来自原大纲「7.1 每个阶段的标准流程」，**已改正为九步**（原图标题写「9. 进入下一阶段」但正文只有九行、编号正确，此处保留并明确为「标准九步」）。

```
┌─────────────────────────────────────────────┐
│ 1. 备份当前可用版本到 翻译软件\backup\阶段N\ │
│    ↓                                         │
│ 2. 复述本阶段目标（用 3 句话）               │
│    ↓                                         │
│ 3. 列出本阶段的决策点，等用户选择 ★必停★     │
│    ↓                                         │
│ 4. 说明「我要改哪些文件、改完什么效果」       │
│    ↓                                         │
│ 5. 写代码                                    │
│    ↓                                         │
│ 6. 自测（跑一遍本阶段的测试清单）             │
│    ↓                                         │
│ 7. 交给用户验收（附测试步骤 + exe）           │
│    ↓                                         │
│ 8. 用户确认通过 → 打版本号 → 更新更新日志     │
│    ↓                                         │
│ 9. 进入下一阶段                              │
└─────────────────────────────────────────────┘
```

### 逐步说明

| 步骤号 | 做什么 | 必须产出什么 | 什么情况下不许进下一步 |
|---|---|---|---|
| 1 | 把上一个已验收通过的可用版本复制到 `翻译软件\backup\阶段N\`（N = 本阶段编号） | `翻译软件\backup\阶段N\` 目录，内含可双击运行的 exe 与对应源码 | 备份目录不存在，或里面没有「上一个已验收版本」的 exe。备份没完成，一行代码都不许写 |
| 2 | 用 3 句话复述本阶段目标：**要做出什么 + 用户会看到什么 + 本阶段不做什么** | 一段给用户看的复述，不含术语 | 复述写不出来，或用户看后说「不是这个意思」。目标理解错了，后面全白做 |
| 3 | 列出本阶段**全部**决策点（决策号 + 选项 A/B/C/D + 各选项优缺点 + AI 推荐项），明确说「★请选择★」，然后停下等回复 | 一张决策清单（表格）；从 `翻译软件\用户版\02-决策总表.md` 读到用户填写的选择 | **用户没有明确回答本阶段每一个决策点**。留空、说「随便」、说「你看着办」都视为未选择，必须停下来问（用户明确说「都按推荐来」除外，见第七节） |
| 4 | 用 3-5 句人话说明「我要改哪几个文件、改完用户会看到什么不同、这次不包含什么」，等用户确认 | 一段人话说明，明确列出改动的文件清单 | 用户没确认；或说明里出现用户看不懂的术语且没解释；或一次说明覆盖了多个不相关的大改动（应拆分） |
| 5 | 按锁定的技术选型写代码（见 `翻译软件\AI版\02-技术架构.md`） | 可编译通过的源码；新文件都有人话头部注释；接口实现放在约定目录 | 出现「改动其他模块业务代码」才能加功能的情况（说明接口设计错了，回去改接口，而不是侵入老代码）；出现硬编码 API Key；出现一次改动多个不相关模块 |
| 6 | 自己跑一遍本阶段测试清单（原大纲对应阶段的 T 表 + 总验收清单对应组），并额外跑一次**回归测试**（上一阶段的核心测试项） | 自测记录：每条测试项的实际结果，失败的写清原因与修法 | 测试清单里有任何一条**没跑**（跑了没过可以修，没跑不算）；或跑出了新 bug 但没修完就交付 |
| 7 | 把 exe（放 `翻译软件\release\vX.Y\`）+ 测试步骤 + 验收打勾清单 + 本次未完成/降级说明，一起交给用户 | ① exe；② 「你自己怎么测」的可执行步骤；③ 验收打勾清单；④ 已知问题与降级说明（如果有） | 四样少一样；或测试步骤里出现用户无法照做的句子；或用「应该可以」代替实测结果 |
| 8 | 等用户明确说「通过」后：打版本号（按 02-技术架构.md 第十节的对照表）、更新 `翻译软件\docs\更新日志.md`、必要时更新 `翻译软件\docs\开发文档.md` | 更新日志里新增一条：版本号 / 日期 / 本阶段做了什么 / 已通过哪些测试 / 已知问题 | **用户没说通过**（说「我再看看」「好像有点问题」都不算通过）；或用户提了意见但你没改完 |
| 9 | 进入下一阶段的第 1 步（备份） | 下一阶段的备份目录 | 上一阶段的验收清单还有未打勾项。地基不稳，越往上越危险 |

> ⚠️ **第 3 步和第 8 步是仅有的两个「必须停下来等用户」的关卡。** 其他步骤可以连续做，这两步之前不许抢跑。

| ❌ 把密钥 / Token / 完整请求头写进日志 | `翻译软件\tools\日志\` 下的文件用户会打开看，也会被误发出去 |
| ❌ 在 `翻译软件\` 根目录乱建文件 | 只有规定的目录可以存在；临时脚本一律放 `翻译软件\tools\脚本\` |
| ❌ 一次改一大堆东西 | 与 7.3 同义但更严：**一轮对话只允许改一个功能点**；跨模块的大改动必须拆成多轮 |
| ❌ 用「应该可以」「大概没问题」「理论上」交付 | 要么给实测结果，要么明确写「这条我没验证，原因是 X」 |
| ❌ 在上一阶段未验收时开工下一阶段 | 包含「先搭个架子」「先把接口写好」这类借口 |

| ❌ 用 `git commit` / 删文件 / 清空目录的方式「顺手清理」 | 用户可能还需要那些东西；清理动作必须单独提出、单独确认 |
| ❌ 把测试数据、调试截图、临时日志当作交付物列出 | 交付物只列第四节规定的东西 |
| ❌ 在钩子回调里做耗时操作（网络、文件、UI 更新） | 钩子回调超时会被系统摘钩，软件直接失灵（原大纲阶段 2 常见坑） |
| ❌ 忽略 `CancellationToken`、不给网络请求设超时 | 会导致界面卡死、连点后结果错乱（原大纲阶段 4/5 常见坑） |
| ❌ 用 `catch (Exception) { }` 空吞异常，或 catch 后只写一句「出错了」就当处理完 | 出错后什么信息都没有，用户和你都无法定位；**catch 之后必须做具体处理，或至少把「什么操作、什么异常、什么参数」写进日志再决定是重试、降级还是提示**。只有一种情况允许静默：明确设计为「失败也无所谓」的后台任务（如检查更新），且必须在代码注释里写清为什么可以静默 |
| ❌ 在业务代码里直接 P/Invoke | 所有 Win32 调用必须集中封装（见 02-技术架构.md 第八节） |
| ❌ 新增一个实现时改动其他模块的业务代码 | 这是「升级通道」的验收红线（见 02-技术架构.md 第三节） |

## 六、遇到做不到的事怎么办

以下流程来自原大纲「7.4 遇到问题的处理方式」，**原文保留**：

```
遇到做不到的事 →
  1. 明确说「做不到，原因是 X」（X 要说人话）
  2. 给出 2-3 个替代方案，每个方案说明代价
  3. 等用户重新选
  4. 不许自己拍板，不许装没看见
```

### 6.1 上报模板（填写这个，不要自由发挥）

```markdown
## ⚠️ 遇到做不到的事：<一句话标题>

**问题**：
<我原本要做什么，卡在哪一步。用大白话，不出现术语；必须出现术语时用括号解释>

**为什么做不到**：
<技术原因的人话解释，1-3 句。必须是真的技术原因，不许用「太复杂」「工作量太大」当理由>

**已经试过什么**：
<我试了 A，结果 X；试了 B，结果 Y。让用户知道你确实努力过>

**替代方案 A：<方案名>**
- 做法：<一句话>
- 用户能得到的：<好处>
- 代价：<具体代价，比如「覆盖原文在滚动时会错位」「多花 2 天」「体积多 100 MB」「需要再申请一个账号」>

**替代方案 B：<方案名>**
- 做法：<一句话>
- 用户能得到的：<好处>
- 代价：<具体代价>

**替代方案 C：<方案名>**
- 做法：<一句话>
- 用户能得到的：<好处>
- 代价：<具体代价>

**我的推荐**：<A / B / C>，因为 <一句话>。
（注意：这只是推荐，不代表我已选。）

**请用户重新选择**：★ 请回复 A / B / C（或「先跳过这个功能，继续下一阶段」）★
```

### 6.2 使用这个模板时必须遵守

1. **至少给 2 个替代方案，最好 3 个**，且方案之间必须是**方向真的不一样**，不能是「换个说法糊弄人」（原大纲 0.1 原话）。
2. **每个方案都必须写代价**。写「没有代价」的替代方案，通常是你没想清楚。
3. **必须停下来等用户回复**，不许边等边做，也不许「先按 A 做着，你不同意再说」。
4. 如果三个方案都做不到，第四个选项必须是「**这个功能砍掉，明确记录到更新日志的『已知不支持』里**」，让用户知道砍了什么。
5. 原大纲第 5 章 5.2 明确要求：**某个阶段做不出来时不许偷偷降级**，必须停下来给 2-3 个替代方案让用户重新选。

## 七、决策怎么读（与用户版文档的对接）

### 7.1 唯一事实来源

用户会在 **`翻译软件\用户版\02-决策总表.md`** 里填写他的选择。原大纲第 3 章「决策总表」的全部决策点（阶段 0-1 到 12-2，共 **39 个决策点**）都已迁移到那份文件里。

你的读取规则：

| 情况 | 你必须怎么做 |
|---|---|
| 用户已填选项（例如 `阶段2：A / C / B`） | **严格按用户填的选项执行**。不许替换，不许「顺手优化」，不许因为你觉得另一个更好就改 |
| 用户在备注里写了额外要求 | 额外要求优先于该选项的默认实现；但仍受本文件所有铁律约束 |
| 某项留空 | **停下问，不许默认选推荐项**。用第七节末尾的问法逐项追问 |
| 用户写「随便」「你看着办」「都行」 | 视为未选择。必须把该决策点的选项和代价重新列一遍，请他选 |
| 用户写「都按推荐来」 | 此时才可以使用各决策点的 **AI 推荐项**（原大纲每个决策点下的「💡 AI 推荐」）。必须在回复里把「我按哪些推荐项执行」逐条列出来，让他一眼看到自己授权了什么 |
| 用户选了不存在的选项（写 D，但该决策点只有 A/B/C） | 停下来问，不许自行映射到最接近的选项 |
| 用户中途改了已填的选项 | 以最新一次明确填写为准；改动要写进更新日志的「决策变更」记录 |
| 用户说「都按推荐来」之后又反悔某一个 | 以反悔后的选择为准，其他仍按推荐项 |

### 7.2 硬性约束

## 九、开工检查清单

**每次开始一个阶段之前，逐条打勾。任何一条打不上勾，不许开工。**

- [ ] **1. 我完整读了本文件（AI版 01）**，特别是第二节八条铁律和第五节禁止表。
- [ ] **2. 我完整读了本阶段在 `翻译软件\AI版\03-分阶段实施规格.md` 里的那一节**，包括「AI 要做的事」「关键异常清单」「常见坑的修法」。
- [ ] **3. 我确认上一个阶段的验收清单已全部打勾**，用户明确说过「通过」。
- [ ] **4. 我确认 `翻译软件\docs\更新日志.md` 里最后一个版本的验收栏已打勾**，版本号与阶段对得上（对照 `AI版\02-技术架构.md` 第十节的版本号对照表）。

- [ ] **6. 我能用 3 句人话复述本阶段目标**（做出什么 / 用户看到什么 / 本阶段不做什么），并已发给用户确认。
