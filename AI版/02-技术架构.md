# AI 版 02 · 技术架构

> 版本：v1.0 ｜ 面向：执行本项目的 AI
> 本文件定义「怎么搭」，不定义「什么时候搭」（那是 03-分阶段实施规格.md 的事）。
>
> 适用平台：Windows 10 / 11（64 位，x64）
> 最终成品：一个 `.exe` 双击即用的划词翻译软件
> 核心链路：`Ctrl + Alt + 鼠标左键拖拽框选` → `取词（剪贴板优先 / Windows OCR 兜底）` → `翻译（DeepSeek 主通道 / 免费谷歌·必应兜底）` → `译文显示（悬浮窗 / 角落面板 / 覆盖原文）`

## 一、技术选型总表

> **读表须知（很重要）**：
> - 标注「**用户已确认**」的，直接执行，不要再问。
> - 标注「⚠️ **AI 推荐值，尚未经用户确认**」的，**开工前必须先问用户**（写进 `用户版\02-决策总表.md` 等他填）。
> - 标注「由**决策 N-M**决定」的，以用户在该决策点的实际选择为准，本表的推荐值只在用户回答「都按推荐来」时生效。
> - **本节任何一项都不许 AI 擅自更换**；确需更换必须先出方案让用户重新决策（见下方流程）。

| 项目 | 选型 | 锁定原因 | 备注 |
|---|---|---|---|
| 语言 | **C#** | 用户已确认；Windows 桌面 + Win32 互操作生态最完整 | 使用 C# 13 / 14 语法（随 .NET 10 SDK 提供）；不许混入 Python / C++ / JS 主逻辑 |
| 运行时 | **.NET 10 LTS** | ⚠️ **AI 推荐值，尚未经用户确认**（见**决策 0-2**）。推荐理由：Windows 官方方案，打包 exe 最省事；官方支持到 2028 年 11 月，一次装好管三年 | 目标框架 `net10.0-windows10.0.19041.0`；**必须装 SDK，不是 Runtime**。若用户 0-2 改选 .NET 8 LTS，目标框架相应改为 `net8.0-windows10.0.19041.0` |
| 界面框架 | **WPF** | ⚠️ **AI 推荐值，尚未经用户确认**（见**决策 1-1**）。推荐理由：本软件最核心的「半透明悬浮窗」「覆盖原文」全是窗口特效，WPF 是 WinForms / Avalonia 里唯一能轻松做到的 | **WPF 与 `PublishTrimmed` 裁剪不兼容**，打包方案里绝对不能开裁剪（见第十节）。若用户 1-1 改选 WinForms 或 Avalonia，**第三节的四个接口契约和第九节性能预算仍然成立**，只需替换表现层实现 |
| 全局监听 | **低级鼠标/键盘钩子**（`WH_MOUSE_LL` + `WH_KEYBOARD_LL`） | 组合键 + 拖拽这种连续动作只能靠钩子捕获，普通 `RegisterHotKey` 只能识别「按下了」，识别不了「按住不放 + 拖鼠标 + 松开」 | 手写 P/Invoke 还是用现成库由**决策 2-1** 决定；无论选哪个，对外都必须藏在 `IInputHook` 后面，业务代码不许直接碰钩子 |
| 取词 | **剪贴板优先 + OCR 兜底**（混合） | 能选中的地方又准又快（100% 准确率 + 毫秒级），选不中的地方靠 OCR 补上；这是成熟划词翻译软件（有道、欧路）的标准做法 | 具体形态由**决策 3-1** 最终确认；无论哪种，必须走 `ITextCapture` 接口 |
| OCR | **Windows.Media.Ocr**（Windows 自带 OCR） | 免费、离线可用、无需申请账号、无需下载模型、速度快（几十毫秒）、中英日韩都支持、微软官方维护 | 依赖系统装了对应语言的「光学字符识别」语言功能；首次启动要检测并给图文引导；具体引擎由**决策 3-2** 最终确认 |
| 主翻译 | **DeepSeek API** | 用户已确认；中文理解最好、按量付费单价极低、接口与 OpenAI 兼容（代码好写） | 端点 `https://api.deepseek.com/chat/completions`；prompt 必须要求「只输出译文」 |
| 兜底翻译 | **免费谷歌端点 + 免费必应端点** | 用户已确认；不需要 Key、质量好、速度快 | **非官方接口，随时可能失效**——必须在文档和交付说明里如实告知用户，不许承诺永久可用；坏一个还有另一个 |
| 历史存储 | **SQLite** | 历史会越攒越多，一开始就选对省得以后迁移；支持复杂查询和全文搜索；记录百万条也不卡；工业标准，只有约 1 MB | 具体方案由**决策 6-2** 最终确认（推荐 C）；数据库文件位置必须与**决策 8-2** 一致 |
| 配置 | **加密 JSON**（DPAPI 加密敏感字段） | JSON 人可读、好排查、缺字段好补默认值；API Key 用 Windows 自带的 DPAPI 加密，只有本机本用户能解开 | 具体存放位置由**决策 8-2** 决定（推荐 `%APPDATA%` + `portable.txt` 便携模式）；Key 保存方式由**决策 8-3** 决定（推荐 B：DPAPI） |
| 打包 | **单文件自包含 exe** | 用户已确认；硬性要求是「双击就能用」，这是唯一真正满足的方案 | `-r win-x64 --self-contained true -p:PublishSingleFile=true`；体积约 60-150 MB；**不许开裁剪** |

### ⚠️ 关于更换选型

**如果实现中确有必要更换上表任何一项，必须先出方案让用户重新决策**，流程固定为：

1. 明确写出「要换的是哪一项、现在是什么、想换成什么」。
2. 写出原因（必须是技术原因，不许用「太复杂」「工作量太大」当理由）。
3. 写出代价（体积变化、性能变化、需要新增的账号/依赖、对已选决策的连带影响）。
4. 给出至少 2 个不动这个选型的替代方案。
5. 停下等用户明确回复。

**不许**换完之后再告知，**不许**边换边做，**不许**用「顺手优化」当理由。更换一旦确认，必须同步更新本表 + 更新日志。

### 2.2 依赖方向（只许向下，不许向上，不许横穿）

| 规则 | 说明 |
|---|---|
| 表现层 → 应用层 → 能力层接口 → 基础设施层 | 唯一允许的调用链方向 |
| 表现层**不许**直接引用基础设施层 | 设置窗口要读配置，必须通过应用层的 `ISettingsService` 拿 |
| 表现层**不许**直接引用能力层实现类 | 悬浮窗要显示译文，数据由应用层喂进来；悬浮窗不许自己 `new DeepSeekEngine()` |
| 能力层实现**不许**互相引用 | `OcrTextCapture` 不许认识 `FloatingWindowPresenter`；要串起来由应用层串 |
| 应用层**不许**出现具体类型名 | 只允许出现接口名；见到 `DeepSeekEngine` 出现在 `TranslationCoordinator` 里就是设计错误 |
| 基础设施层**不许**引用上面三层 | 依赖反了就编译不过去，这是好事，不要用「加个引用」绕过去 |
| 跨层通信一律用接口 + 数据对象（DTO） | 不许用全局静态变量、不许用 `public static` 的「大杂烩」类 |

### 2.3 一次完整翻译的跨层流水（说明分层怎么落地）

```
① 用户在浏览器里按住 Ctrl+Alt 拖鼠标
        │  （钩子回调 → 立刻 PostMessage 丢给主线程，回调内不做任何耗时操作）
        ▼
③ Input 能力层：LowLevelMouseHook + LowLevelKeyboardHook 捕获事件 → SelectionStateMachine（应用层）判断状态
        │  状态：空闲 → 按下(Ctrl+Alt+左键) → 拖拽中 → 抬起
        ▼
① 表现层：SelectionOverlayWindow 画半透明遮罩 + 选框（纯展示，鼠标穿透）
        │
        ▼  松手
② 应用层：CaptureCoordinator 决定先试剪贴板、超时 200 毫秒再转 OCR
        │
        ▼
③ 能力层：ClipboardTextCapture 试 Ctrl+C 读剪贴板 → 失败 → OcrTextCapture 截图识别
        │  返回：TextCaptureResult { 文本, 是否来自OCR, 置信度, 文字块坐标列表 }
        ▼
② 应用层：TranslationCoordinator 按「主引擎 → 兜底 1 → 兜底 2」顺序尝试（带取消令牌）
        │  失败即降级，成功后记录用了哪个引擎、耗时、消耗字符数
        ▼
③ 能力层：DeepSeekEngine / GoogleFreeEngine / BingFreeEngine 之一返回 TranslationResult
        │
        ▼
② 应用层：DisplayRouter 按配置（决策 5-x / 6-1 / 7-x）选一个 IDisplayPresenter
        │  同时通知 HistoryStore 落库（如果历史开关打开）
        ▼
① 表现层：FloatingWindowPresenter / OverlayPresenter 把译文画出来
```

## 三、四个核心接口契约

**这是全场最重要的部分。** 四个接口位于 `src\Core\Abstractions\`。阶段 10「升级通道」的验收标准只有一条：

> **新增一个实现只允许新增文件，不许改动其他模块的业务代码。**

下面的签名是**接近真实 C# 的契约定义**，包括注释。实现时类名/方法名必须与此一致（命名空间按实际项目调整）。

### 3.1 通用数据对象（`src\Core\Abstractions\Models\`）

```csharp
namespace TranslatorApp.Core.Abstractions.Models;

/// <summary>
/// 翻译结果。由 ITranslationEngine 返回，交给应用层决定怎么用。
/// </summary>
public sealed record TranslationResult
{
    /// <summary>译文文本。失败时为空字符串。</summary>
    public required string TranslatedText { get; init; }

    /// <summary>实际使用的引擎名（"DeepSeek" / "GoogleFree" / "BingFree" / "Local"）。
    /// 调度器降级之后，这里填的是真正出结果的那个引擎，不是首选引擎。</summary>
    public required string EngineName { get; init; }

    /// <summary>本次翻译耗时（毫秒），含网络往返。</summary>
    public required int ElapsedMilliseconds { get; init; }

    /// <summary>本次消耗的字符数（按原文长度计）。查不到就填原文长度。</summary>
    public required int ConsumedCharacters { get; init; }

    /// <summary>是否来自本地缓存（true 表示没产生新费用）。</summary>
    public bool FromCache { get; init; }

    /// <summary>源语言实际识别结果（"zh" / "en" / "auto" 解析后的值）。</summary>
    public string? DetectedSourceLanguage { get; init; }
}

/// <summary>
/// 译文的显示样式提示。由能力层给建议，表现层可以不听（配置优先）。
/// </summary>
public sealed record TextStyleHint
{
    /// <summary>建议的字号（像素）。覆盖原文形态由背景分析与布局共同决定。</summary>
    public double? FontSize { get; init; }

    /// <summary>建议的文字颜色（#AARRGGBB）。深色背景要给浅色字。</summary>
    public string? Foreground { get; init; }

    /// <summary>建议的背景色（#AARRGGBB）。覆盖原文形态取样填充时使用。</summary>
    public string? Background { get; init; }

    /// <summary>建议的行数（按原文行数对齐）。null 表示整段显示。</summary>
    public int? LineCount { get; init; }
}

/// <summary>
/// 取词结果。由 ITextCapture 返回。
/// </summary>
public sealed record TextCaptureResult
{
    /// <summary>取到的文本。已做过去多余空行、合并错误断行、去首尾空格。
    /// 没取到文字时为空字符串（不是 null）。</summary>
    public required string Text { get; init; }

    /// <summary>文本是否来自 OCR（true = 识别出来的，可能有错字；
    /// false = 剪贴板拿到的，原文本身就是文字）。</summary>
    public required bool FromOcr { get; init; }

    /// <summary>OCR 置信度，0.0-1.0。剪贴板取词时固定为 1.0。</summary>
    public required double Confidence { get; init; }

    /// <summary>文字块坐标列表（屏幕物理像素）。覆盖原文形态靠它按行对齐。
    /// 剪贴板取词拿不到文字块坐标时为空列表。</summary>
    public required IReadOnlyList<TextBlockBounds> Blocks { get; init; }

    /// <summary>实际使用的取词方式名（"Clipboard" / "WindowsOcr" / "Hybrid"）。</summary>
    public required string CaptureName { get; init; }

    /// <summary>耗时（毫秒）。</summary>
    public required int ElapsedMilliseconds { get; init; }

    /// <summary>识别到的语言（"zh" / "en" / 未知时 null）。中文字符占比 &gt; 30% 判为中文。</summary>
    public string? DetectedLanguage { get; init; }
}

/// <summary>
/// 一块文字在屏幕上的位置（屏幕物理像素，已做 DPI 换算）。
/// </summary>
public sealed record TextBlockBounds
{
    public required int X { get; init; }
    public required int Y { get; init; }
    public required int Width { get; init; }
    public required int Height { get; init; }

    /// <summary>这一块在第几行（从 0 开始）。OCR 分行结果，用于按行对齐。</summary>
    public int LineIndex { get; init; }

    /// <summary>这一块对应的文字（可能为空，只要坐标时留空）。</summary>
    public string? Text { get; init; }
}

/// <summary>
/// 屏幕上的一个矩形区域（屏幕物理像素）。
/// </summary>
public sealed record ScreenRect
{
    public required int X { get; init; }
    public required int Y { get; init; }
    public required int Width { get; init; }
    public required int Height { get; init; }

    /// <summary>这个矩形属于哪块显示器（多显示器时用来决定窗口出现在哪个屏）。</summary>
    public string? MonitorDeviceName { get; init; }

    /// <summary>该显示器的 DPI 缩放比例（1.0 / 1.25 / 1.5 / 2.0）。</summary>
    public double DpiScale { get; init; } = 1.0;
}

/// <summary>
/// 能力层统一的失败原因。不许用裸 Exception 表达「可预期的失败」。
/// </summary>
public enum FailureKind
{
    None = 0,
    NetworkUnreachable,     // 网络不通
    Timeout,                // 超时
    AuthFailed,             // Key 无效 / 未填
    QuotaExceeded,          // 额度耗尽
    RateLimited,            // 被限流（429）
    ServiceError,           // 服务端错误（5xx）
    NoTextFound,            // 没识别到文字
    ClipboardBusy,          // 剪贴板被占用
    LanguagePackMissing,    // OCR 语言包缺失
    ModelNotInstalled,      // 本地离线包未安装
    NotSupported,           // 该场景不支持（如独占全屏游戏）
    Cancelled,              // 被取消令牌取消
    Unknown
}

/// <summary>
/// 统一的失败描述。失败必须能生成一句中文人话给用户看。
/// </summary>
public sealed record FailureInfo
{
    public required FailureKind Kind { get; init; }

    /// <summary>给用户看的中文提示，例如「API Key 无效，请到设置里检查」。</summary>
    public required string UserMessage { get; init; }

    /// <summary>给日志看的技术细节（**绝不许包含 API Key、Token、请求头**）。</summary>
    public string? TechnicalDetail { get; init; }

    /// <summary>是否值得换下一个引擎重试（超时/限流/服务端错误 → true；Key 无效 → true 也合理，因为兜底不需要 Key）。</summary>
    public bool ShouldFallback { get; init; }
}
```

### 3.2 `ITranslationEngine` —— 翻译引擎

```csharp
namespace TranslatorApp.Core.Abstractions;

/// <summary>
/// 翻译引擎统一接口。
///
/// 【为什么这样设计】
/// 用户已选定「DeepSeek 主通道 + 免费谷歌/必应兜底」，将来还可能加本地离线引擎、
/// Claude、GPT、百度。如果每个引擎都被调度器直接 new 出来、直接调用，那么每加一个引擎
/// 就要改调度器 → 改一处可能弄坏另一处。把「翻译」抽象成一个接口之后，
/// 调度器只认识接口，加引擎 = 加文件。
///
/// 【新增一个实现需要做什么】
/// 1. 在 src\Core\Translation\ 下新建一个 .cs 文件（例如 BaiduEngine.cs）。
/// 2. 类实现本接口，填好 Name / IsAvailableAsync / TranslateAsync / GetRemainingQuotaAsync。
/// 3. 在模块注册表里注册一行（新增注册行属于「新增装配代码」，不算改业务代码）。
/// 4. 不需要改：调度器、UI、配置结构、其他引擎。
/// 5. 自测：断网 / Key 错 / 超时 / 超长文本四种情况都要有中文提示。
///
/// 【计划内的实现类】
/// - DeepSeekEngine        主引擎（阶段 4）
/// - GoogleFreeEngine      免费兜底 1（阶段 4）
/// - BingFreeEngine        免费兜底 2（阶段 4）
/// - LocalTranslationEngine 本地离线兜底（阶段 11，可选，用 ONNX Runtime 或 CTranslate2）
/// - （未来）BaiduEngine / AzureEngine / ClaudeEngine / MockEngine（阶段 10 文档里要给一个完整例子）
/// </summary>
public interface ITranslationEngine
{
    /// <summary>引擎名，用于界面显示和日志。例如 "DeepSeek"、"GoogleFree"、"BingFree"、"Local"。
    /// 必须是英文标识，不要在这里写中文（中文显示名由 UI 层映射）。</summary>
    string Name { get; }

    /// <summary>该引擎当前是否可用（Key 填了吗？网络通吗？离线包装了吗？）。
    /// 这个属性要快（&lt; 10 毫秒），不许在这里发网络请求。要做真实连通性检查请用
    /// <see cref="GetRemainingQuotaAsync"/> 或设置页的「测试连接」按钮。</summary>
    bool IsAvailable { get; }

    /// <summary>剩余额度。能查到就返回具体数字（美元或字符数，由实现自己定义单位并在
    /// Description 里说明），查不到返回 null（界面显示「未知」）。绝不许因为查额度失败而抛异常。</summary>
    /// <param name="cancellationToken">取消令牌，必须传递到所有网络调用。</param>
    Task<QuotaInfo?> GetRemainingQuotaAsync(CancellationToken cancellationToken = default);

    /// <summary>异步翻译。这是本接口唯一的干活的成员。
    ///
    /// 约定：
    /// - 必须支持 <paramref name="cancellationToken"/>；被取消时抛 OperationCanceledException。
    /// - 必须设置超时（默认 10 秒，来自配置 翻译.超时秒数），超时抛 TimeoutException 或返回失败。
    /// - 失败有两种表达方式：① 返回 null 并在 out 参数给出 FailureInfo；② 抛异常。
    ///   本项目的统一约定是：**可预期的失败用返回值表达**（见 TranslationAttempt），
    ///   **不可预期的异常才 throw**，由调度器统一 catch。
    /// - 译文必须只包含译文本身。prompt 里必须明确要求「只输出译文，不要任何解释、
    ///   不要『好的，以下是翻译结果：』这类废话，严格按原文翻译，不增不减」。
    /// - 实现类内部不许弹任何 UI、不许写任何用户可见的提示；错误原样交给调度器。
    /// - 日志里绝不许出现 API Key、Token、完整请求头。
    /// </summary>
    /// <param name="text">待翻译文本。长度上限由实现自己定，超出要截断并在 FailureInfo 里说明。</param>
    /// <param name="sourceLanguage">源语言，BCP-47 或项目内约定值："auto" 表示自动判断。</param>
    /// <param name="targetLanguage">目标语言，例如 "zh-Hans"、"en"。</param>
    /// <param name="cancellationToken">取消令牌。用户连续框选时，上一次请求必须被取消。</param>
    Task<TranslationAttempt> TranslateAsync(
        string text,
        string sourceLanguage,
        string targetLanguage,
        CancellationToken cancellationToken = default);
}

/// <summary>一次翻译尝试的结果：要么成功，要么带原因失败。不用异常表达可预期失败。</summary>
public sealed record TranslationAttempt
{
    /// <summary>成功时的结果；失败时为 null。</summary>
    public TranslationResult? Result { get; init; }

    /// <summary>失败时的原因；成功时为 null。</summary>
    public FailureInfo? Failure { get; init; }

    public bool IsSuccess => Result is not null;
}

/// <summary>额度信息。</summary>
public sealed record QuotaInfo
{
    /// <summary>剩余量。null 表示未知。</summary>
    public double? Remaining { get; init; }

    /// <summary>单位说明，例如 "CNY"、"字符"。</summary>
    public string Unit { get; init; } = "";

    /// <summary>给用户看的一句话，例如「余额约 ¥8.32」。</summary>
    public string Description { get; init; } = "";
}
```

```csharp
/// <summary>
/// 取词方式统一接口：把「屏幕上的一个矩形区域」变成「一段文字」。
///
/// 【为什么这样设计】
/// 取词有两条互不相通的技术路线：剪贴板（模拟 Ctrl+C，准且快，但只对能选中文字的
/// 软件有效）和 OCR（截图认字，通用但慢且有错字）。将来还可能加别的（读取 PDF 文字层、

/// 「用哪一种、失败了换哪一种」这件事完全由应用层决定，取词实现自己不关心。

/// 【新增一个实现需要做什么】
/// 1. 在 src\Core\Capture\ 下新建一个 .cs 文件（例如 UiaCapture.cs）。
/// 2. 实现本接口，填好 Name / IsAvailableAsync / CaptureAsync。
/// 3. 在模块注册表里注册一行。
/// 4. 不需要改：调度器（CaptureCoordinator）、UI、配置结构、其他取词实现。

///
/// 【计划内的实现类】
/// - ClipboardTextCapture  剪贴板取词（阶段 3）：保存原剪贴板 → 发 Ctrl+C → 200 毫秒内读新内容 → 还原原剪贴板
/// - OcrTextCapture        Windows.Media.Ocr 截图识别（阶段 3）：含放大+灰度预处理、

/// - 混合模式（用户选 3-1 的 C 时）**不需要单独的 HybridCapture 类**：由应用层的 CaptureCoordinator
///   按「先调 ClipboardTextCapture，200 毫秒没结果就调 OcrTextCapture」的顺序编排即可。
/// </summary>
public interface ITextCapture
{
    /// <summary>取词方式名，例如 "Clipboard"、"WindowsOcr"、"Hybrid"。英文标识，中文名由 UI 映射。</summary>
    string Name { get; }

    /// <summary>该方式当前是否可用。要快（&lt; 10 毫秒），不许在这里截图或调 OCR。
    /// 例：OCR 实现检查「系统是否装了对应语言的 OCR 语言包」。</summary>
    bool IsAvailable { get; }

    /// <summary>异步取词。
    ///
    /// 约定：
    /// - <paramref name="selection"/> 是屏幕物理像素的矩形，实现内部负责与自己需要的坐标系换算。
    /// - 必须支持取消；用户中途按 Esc 时要能立刻停下。
    /// - 没取到文字时返回 TextCaptureResult.Text = ""（空字符串），**不要抛异常**；
    ///   要通过 FailureInfo 说明原因时用返回值里的失败信息（见 CaptureAttempt）。
    /// - **剪贴板实现必须做到：无论成功失败，都要把用户原来的剪贴板内容还原回去**。
    ///   这条是阶段 3 的硬指标（原大纲测试项 T3-6「剪贴板不被破坏」）。
```

### 3.5 `IFeatureModule` —— 功能模块

```csharp

/// <summary>
/// 功能模块统一接口：让「哪些功能开着」变成配置里的一句话。
///
/// 【为什么这样设计】
/// 用户选的是「配置开关起步、插件机制预留」（阶段 10 决策 10-1 的推荐）。要做到
/// 「加功能不用改老代码」，必须让每个功能都能被统一地启动和关闭，并且能声明依赖。

/// - OfflinePackModule   离线语言包管理（阶段 11）：下载、MD5 校验、解压、删除
/// - TrayModule          托盘常驻（阶段 1）

{

    string Name { get; }

    /// <summary>是否启用。来源 = 配置文件里的功能模块开关。禁用时必须能被安全跳过。</summary>
    bool IsEnabled { get; }

    /// <summary>依赖的其他模块名。启动时按依赖顺序初始化；
    /// 如果某个依赖被禁用，本模块必须**拒绝启动并给出明确中文提示**，不许硬着头皮跑然后崩。
    /// 例：OfflinePackModule 依赖 LocalTranslationEngine 可用。</summary>
    IReadOnlyList<string> DependsOn { get; }

    /// <summary>异步初始化。要求：
    /// - 不许阻塞启动流程（阶段 10 硬指标：更新检查带来的启动耗时增加 &lt; 200 毫秒）。
    /// - 任何失败都必须被吞掉并记日志，**绝不许因为某个模块初始化失败导致软件启动不了**。

    /// - 必须释放非托管资源、取消订阅事件、关闭数据库连接、停掉定时器。
    /// - 不许抛异常（退出流程里抛异常会让进程卡住）。</summary>
    Task ShutdownAsync(CancellationToken cancellationToken = default);
}
```

### 3.6 四个接口的设计约束（写实现前必须想清楚的五件事）

| 约束 | 说明 |
|---|---|
| **接口只放「做什么」，不放「怎么做」** | 参数用通用类型（string / enum / record），不许出现 `HttpClient`、`SqliteConnection`、`Window` 这类实现细节。参数一旦写具体，将来就换不动了（原大纲阶段 10 常见坑第一条） |
| **一律异步 + 一律接受 `CancellationToken`** | 翻译、取词、显示都是异步的；用户连续框选时上一次必须能被取消，否则会出现原大纲阶段 5 测试项 T5-11 描述的「结果交错混乱」 |
| **可预期的失败用返回值，不可预期的异常才 throw** | 网络不通、Key 错、额度不足、没识别到文字，这些都是**正常会发生的事**，用 `FailureInfo` 表达，并且每个 `FailureKind` 都必须能生成一句中文人话 |
| **实现类不许自己弹 UI、不许自己决定策略** | 引擎不许弹「额度不足」的窗；取词不许自己决定「先剪贴板还是先 OCR」；显示形态不许自己决定「该不该关掉别人」。策略全部归应用层 |
| **接口一旦被两个以上实现使用，就不许再改签名** | 要加能力就加新的可选成员或用扩展方法；改签名会让所有已有实现一起坏掉，等于把「升级通道」拆了 |

### 3.7 「只允许新增文件」的验收方式（阶段 10 的硬指标）

阶段 10 测试项 T10-2 / T10-3 就是用这两个动作验收的，你必须能当场做到：

| 验收动作 | 通过标准 | 你要怎么证明 |
|---|---|---|
| 照着 `docs\如何添加新功能.md`，加一个「假引擎」（比如把文字倒序返回） | **只加了一个新文件**，没有改动其他模块的业务代码 | 列出本次改动的文件清单：只有 `src\Core\Translation\ReverseEngine.cs` 新增，加注册表里一行装配代码 |
| 照着文档加一个新显示形态（比如「底部横幅」） | 同上 | 同上：只有 `src\UI\BottomBanner\` 新目录 + 注册表一行 |
| 在设置里禁用「覆盖原文」模块 | 该功能消失，其他功能正常 | 不崩、不报错、有明确提示 |
| 把禁用的模块重新启用 | 功能恢复 | 不需要重启软件（热更新优先） |

### 4.2 三条硬性目录纪律

1. **`翻译软件\` 根目录只允许出现**：`制作大纲.md`、`用户版\`、`AI版\`、`src\`、`docs\`、`release\`、`backup\`、`assets\`、`tools\`。多一个文件都算违规（原大纲阶段 0 测试项 T0-4 就是在查这件事）。

### 5.3 文件组织规范

| 规则 | 说明 |
|---|---|

### 5.4 编码硬约束（每条都会被验收）

| 编号 | 约束 | 为什么 | 怎么验收 |
|---|---|---|---|
| C1 | **异步方法一律 `Async` 结尾且接受 `CancellationToken`** | 用户连续框选时必须能取消上一次请求，否则出现「结果交错混乱」 | 搜一遍所有 `async Task` 方法，逐个确认参数里有 `CancellationToken` |
| C2 | **所有网络调用必须设超时**（默认 10 秒，从配置读） | 网络不好时界面会卡死（原大纲阶段 4 常见坑） | 检查每个 `HttpClient` 调用点，必须有超时或取消令牌 |
| C3 | **所有外部输入必须校验** | 外部输入 = 配置文件、API 响应、剪贴板内容、OCR 结果、文件内容、命令行参数、用户输入 | 逐个入口确认：null 检查、长度上限、枚举合法性、JSON 解析失败有兜底 |
| C4 | **禁止万能 try-catch**：catch 后必须做具体处理（重试/降级/提示/记录），或至少把「什么操作、什么异常、什么参数」写进日志 | 空吞异常等于把 bug 藏起来 | 搜 `catch`，每一处都要能说出「catch 到之后做了什么」；只有「失败也无所谓」的后台任务（如检查更新）才允许静默，且必须写注释说明 |
| C5 | **禁止幽灵代码**：没有调用的方法、注释掉的代码块、永远为 false 的分支，一律删除 | 幽灵代码会让下一个人以为它有用途（铁律 R6 的精神） | 搜注释掉的代码块、搜只被定义没被引用的 `private` 方法 |
| C6 | **禁止假注释**：注释必须和代码一致；不许写「处理逻辑」「工具」「入口」这种等于没说的注释 | 注释和代码不一致比没注释更害人 | 抽查 10 处注释，逐条核对代码 |
| C7 | **每个模块头部必须有人话注释**，回答三个问题：这个模块干嘛的 / 和谁交互 / 要改它该动哪里 | 铁律 R6 | 抽查任意 `.cs` 文件，1 分钟内能说出它做什么 |
| C8 | **禁止魔法数字**：超时、像素阈值、重试次数、字号上下限等一律定义为具名常量或配置项 | 改参数时找不到地方 | 搜代码里的裸数字（`200`、`10`、`3000`），逐个确认是否是具名常量 |
| C9 | **禁止把密钥写进代码或日志** | 铁律 R3/第五节补充禁止项 | 搜 `sk-`、搜日志语句里是否拼接了 Key / Token / 请求头 |
| C10 | **所有 Win32 调用必须集中在 `Core\Native\NativeMethods.cs`** | 见第八节 | 搜 `[DllImport]`，只允许出现在这一个文件里 |
| C11 | **不许在 UI 线程做耗时操作** | 会卡界面 | 检查截图、OCR、网络、SQLite 查询是否都在异步路径上 |
| C12 | **钩子回调内处理时间 < 5 毫秒** | 超时会被系统摘钩，软件直接失灵 | 回调里只允许做「读状态 + PostMessage」，不许有 IO、网络、UI 更新 |
| C13 | **路径拼接一律用 `Path.Combine`**，不许用字符串 `+` | 中文路径、空格路径会出错（原大纲阶段 9 常见坑） | 搜 `+ "\\"` |
| C14 | **时间统一存 UTC，显示时转本地时区** | 否则历史记录时间会错（原大纲阶段 6 常见坑） | 检查数据库写入与显示格式化的位置 |
| C15 | **CSV 导出必须带 UTF-8 BOM** | 否则 Excel 打开乱码（原大纲阶段 6 常见坑） | 导出后用 Excel 打开验证 |

### 5.5 模块头注释模板（每个 `.cs` 文件开头都要有）

```csharp
// ============================================================================
//  模块：DeepSeekEngine —— DeepSeek 主翻译引擎
//
//  【干嘛的】
//  把一段文本通过 https://api.deepseek.com/chat/completions 翻译成目标语言。
//  它是 ITranslationEngine 的主实现，正常情况下由 TranslationCoordinator 首选调用。
//
//  【和谁交互】
//  上游：TranslationCoordinator（应用层）调用 TranslateAsync。
//  下游：Core\Http\HttpClientFactory 发请求；Core\Config\ConfigStore 读 API Key
//        （Key 是 DPAPI 加密存储的，本模块只拿到解密后的内存字符串，用完不缓存）。
//  不认识：任何 UI、任何取词实现、其他翻译引擎。
//
//  【要改它该动哪里】
//  - 想改翻译质量/口吻 → 改 BuildPrompt()，注意必须保留「只输出译文」的约束。
//  - 想改超时       → 改配置项 翻译.超时秒数，不要在这里写死。
//  - 想改错误话术   → 改 MapFailure()，每个 FailureKind 都要有中文人话。
//  - 想换端点/模型  → 改常量 DefaultEndpoint / DefaultModel（或改成配置项）。
//
//  【注意事项】
//  - 日志里绝不许出现 API Key。
//  - 必须支持 CancellationToken；用户连续框选时上一次请求要被取消。
```

### 7.2 三条不可违反的配置铁律

| 铁律 | 要求 | 验收方式 |
|---|---|---|
| **① 缺字段必须能启动** | 任何字段缺失、为 null、类型不对，都要用上表默认值补齐；**不许因为配置里少一个 `"字号"` 就启动失败**。实现方式：定义一个 `AppConfig` 类，所有属性都给默认值，反序列化用「宽松模式」（忽略未知字段、缺字段保留默认值），反序列化后跑一遍 `Validate()` 修正越界值 | 手工把配置文件删掉一半字段，双击 exe 必须正常启动，且缺失项按默认值生效（对应原大纲测试项 T8-10） |
| **② 配置文件损坏必须能自动恢复默认值** | JSON 语法错误、文件被截断、全是乱码、文件被占用读不出——任何一种都必须：① 备份坏文件到 `config.json.bad.<时间戳>`（放 `翻译软件\tools\日志\` 或配置目录）；② 用默认值启动；③ 给用户一句中文提示「配置文件已损坏，已重置为默认设置」 | 手工把配置文件写成 `{{{ 非法 JSON`，双击 exe 必须正常启动并给出提示（对应原大纲测试项 T8-10）；同时坏文件被备份下来，不是直接删掉 |
| **③ API Key 必须 DPAPI 加密** | 用 `ProtectedData.Protect(bytes, null, DataProtectionScope.CurrentUser)` 加密后 Base64 存进 `apiKeyProtected`；**绝不许明文存 JSON、绝不许写进日志、绝不许硬编码**。读配置时解密失败（换电脑、换用户）→ 当成「未填 Key」，提示用户重新填写 | 打开 `config.json` 用记事本看：**看不到 `sk-` 开头的明文**（对应原大纲测试项 T8-12）；把配置文件拷到另一台电脑，Key 解不开并提示重新填写（T8-13） |

### 7.3 配置读写实现要求

- **写配置必须防抖**：拖动滑块等连续改动，要等改动停止 500 毫秒后才落盘，不许每动一下就写文件（原大纲阶段 8 常见坑）。
- **写配置必须原子**：先写临时文件再替换，避免写一半断电导致配置损坏。
- **配置改动要能热更新**：通过「配置变更事件」通知各模块刷新，尽量做到改快捷键不重启软件（原大纲阶段 8 制作步骤第 6 条）。
- **配置读写的所有异常都要被兜住**：配置读取出错导致启动崩溃，是原大纲阶段 8 明确列出的坑（症状是「双击没反应」，用户完全无从排查）。
- **配置文件里不许出现任何明文密钥**：包括 API Key、Token、用户名密码。

## 八、关键 Win32 互操作清单

> **总规则：这些调用必须集中封装在一个 `NativeMethods` 类里（`src\Core\Native\NativeMethods.cs`），不许散落在业务代码中。**
> 业务代码只允许调用 `Core\Native\` 里包装好的方法（例如 `NativeWindowHelper.MakeClickThrough(hwnd)`），**不许出现 `[DllImport]`**。

| API 名 | 用途 | 用在哪一阶段 | 注意事项 |
|---|---|---|---|
| `SetWindowsHookEx` | 安装低级鼠标/键盘钩子（`WH_MOUSE_LL` / `WH_KEYBOARD_LL`），拿到全系统的鼠标键盘动作 | 阶段 2 | 钩子回调必须极快（< 5 毫秒），超时会被系统摘钩（软件直接失灵）；回调里只允许读状态 + `PostMessage` 丢给主线程；要处理 32/64 位与「运行一段时间后失效」的问题；必须能被 `UnhookWindowsHookEx` 干净卸载 |
| `CallNextHookEx` | 把钩子事件继续传给下一个钩子链（不调用会导致其他程序收不到鼠标键盘事件） | 阶段 2 | **必须调用**；不调用等于把全系统的输入劫持了，会造成别的软件失灵——这是最严重的低级错误之一 |
| `UnhookWindowsHookEx` | 卸载钩子 | 阶段 2 | 程序退出、模块禁用、钩子重装前都要调；不卸载会留下失效的钩子句柄，且可能阻止程序进程完全退出 |
| `GetAsyncKeyState` | 实时查询某个键是否按住（判断 Ctrl / Alt / Shift 是否处于按下状态） | 阶段 2（**必用**） | 即使用钩子方案也建议用它来判断修饰键状态（比自己在钩子里维护状态机更不容易错）；注意它的返回值最高位是「当前是否按下」，要 `& 0x8000` 判断；**不要用它做整体轮询监听**（那是决策 2-1 的 C 方案，费电、会漏事件） |
| `GetGUIThreadInfo` | 拿到当前前台窗口的 GUI 线程信息（含焦点窗口、光标所在窗口、可选中区域信息） | 阶段 3（辅助） | 用途：判断框选位置所属的窗口/控件，辅助「该不该发 Ctrl+C」的判断；结构体定义要按 64 位对齐；多显示器下坐标要换算 |
| `RegisterHotKey` | 注册系统级固定快捷键（仅当用户选择「双击 Ctrl 翻剪贴板」或需要一个即时触发键时使用） | 阶段 2（可选） | **只能识别「按下了」，识别不了「按住不放 + 拖鼠标 + 松开」**，所以拖拽框选必须靠钩子；注册失败要检查返回值并提示「该快捷键已被其他程序占用，请换一个」；退出时要 `UnregisterHotKey` |
| `WS_EX_TRANSPARENT` | 让窗口鼠标事件穿透（点这个窗口等于点在它下面的东西上） | 阶段 2（框选遮罩）、阶段 7（覆盖原文） | 覆盖原文形态**必须**加，否则会挡住下面的网页点击（原大纲阶段 7 常见坑）；框选遮罩加了它，鼠标事件才能正常传给下面的程序；**注意：加了穿透后窗口自己也收不到点击，需要交互时必须临时去掉**（原大纲阶段 5 常见坑「复制按钮点不动」就是踩了这个） |
| `WS_EX_LAYERED` | 分层窗口（支持整窗透明度、逐像素透明度） | 阶段 5、阶段 7 | 与 `WS_EX_TRANSPARENT` 配合使用；WPF 的 `AllowsTransparency=true` 底层也依赖它；注意某些老显卡/远程桌面下性能下降 |
| `SetWindowPos` | 设置窗口位置、大小、Z 序（置顶） | 阶段 2、5、6、7 | 置顶用 `HWND_TOPMOST`；多显示器与高 DPI 下坐标必须是**物理像素**；窗口出现前先设好位置，避免「先闪到 (0,0) 再跳过去」 |
| `Graphics.CopyFromScreen` | 截取屏幕指定区域为位图（取词 OCR 的图像来源；也是覆盖原文取样背景色的来源） | 阶段 3（必用）、阶段 7 | 高 DPI 下要注意 `Graphics.CopyFromScreen` 用的是**物理像素**，而 WPF 的坐标默认是设备无关像素，两者必须换算（原大纲多处提到的高 DPI 坐标错位坑）；多显示器要传对原点偏移；截完必须 `Dispose`，否则内存持续增长（阶段 3 测试项 T3-8 查这个） |
| `ProtectedData.Protect` / `ProtectedData.Unprotect`（DPAPI） | 加密 / 解密 API Key（只有本机本用户能解开） | 阶段 4（首次读 Key）、阶段 8（设置页填 Key） | 作用域用 `DataProtectionScope.CurrentUser`；加密结果 Base64 后存 JSON；**解密失败要当成「未填 Key」**，不许崩溃；需要引用 `System.Security.Cryptography.ProtectedData` 包；**绝不许把解密后的 Key 写进日志或缓存到磁盘** |
| `PostMessage` | 从钩子回调里把「有事件发生了」丢给主线程处理 | 阶段 2（必用） | 钩子回调里**唯一**被允许的「往下走」的方式；不许在回调里直接干活（IO / 网络 / UI 更新都会导致超时摘钩） |
| `GetSystemMetrics` / `MonitorFromPoint` / `GetDpiForWindow`（辅助） | 拿屏幕尺寸、判断某点在哪块显示器、拿窗口 DPI | 阶段 2、5、7 | 多显示器 + 混合缩放（一台 100%、一台 150%）下必须靠这些 API 才能算对坐标；定位窗口要按**工作区**（扣掉任务栏）计算，不能用整个屏幕（原大纲阶段 5 常见坑） |
| `Shell_NotifyIcon`（不用第三方托盘库时） | 托盘图标（如果不引入 `Hardcodet.NotifyIcon.Wpf` 或 WinForms 的 `NotifyIcon`） | 阶段 1 | 自己封装的话要处理：图标句柄释放、任务栏重启后重新注册（`TaskbarCreated` 消息）、右键菜单弹出位置 |
| `RegisterApplicationRestart`（可选） | 崩溃后自动重启（提升稳定性） | 阶段 9 之后（可选） | 加分项，不是必需；要配合全局异常处理，避免无限重启循环 |
| `SetProcessDpiAwarenessContext` / 应用清单 `PerMonitorV2` | 声明进程的 DPI 感知模式 | 阶段 1（**必须**在阶段 1 就配好）、阶段 2 起全程生效 | **必须用 `PerMonitorV2`**；不声明会出现「选框画的位置和鼠标对不上」（原大纲阶段 2 常见坑）；配置方式是在 `app.manifest` 里声明，不是代码里调 API；阶段 9 打包后要再验一次 |

### 8.1 `NativeMethods` 封装规范

| 要求 | 说明 |
|---|---|
| **只有一个文件** | 所有 `[DllImport]` 只允许出现在 `src\Core\Native\NativeMethods.cs`。搜到第二处就是违规 |
| **结构体要成对定义** | `POINT` / `RECT` / `MSLLHOOKSTRUCT` / `KBDLLHOOKSTRUCT` / `GUITHREADINFO` 等结构体定义在 `src\Core\Native\Structs.cs`，字段顺序与 C 定义严格一致，注意 64 位下的对齐 |
| **常量要具名** | `WH_MOUSE_LL = 14`、`WM_LBUTTONDOWN = 0x0201`、`GWL_EXSTYLE = -20`、`WS_EX_TRANSPARENT = 0x00000020` 等一律在 `src\Core\Native\Constants.cs` 里具名定义，不许在业务代码里写 `0x20` |
| **业务代码只调包装方法** | 例如业务代码调 `NativeWindowHelper.MakeClickThrough(hwnd)`，而不是自己算 `SetWindowPos` 的 exStyle |
| **每个包装方法都要有中文注释** | 说明「干嘛的 / 参数含义 / 失败会怎样 / 用在哪一阶段」 |
| **失败要检查** | 大部分 Win32 API 靠返回值判断成功失败，必须检查并记日志（例如 `RegisterHotKey` 返回 false = 快捷键被占用） |
| **句柄要释放** | 钩子句柄、GDI 对象、位图、图标句柄都要在 `Dispose` 里释放，否则长时间运行内存持续增长（违反第九节预算） |

## 九、性能与资源预算

> 这些数字不是「尽量达到」，而是**验收指标**。任意一项超标，都要在交付说明里写清原因和打算怎么改，不许沉默交付。

| 指标 | 目标值 | 超标怎么办 |
|---|---|---|
| 空闲 CPU 占用 | **< 1%**（鼠标不动、没有翻译任务时） | 检查是不是用了轮询方案（决策 2-1 的 C 方案会持续吃 CPU）；检查是否有定时器频率过高（把「每 10 毫秒查一次」改成事件驱动）；检查是否有 UI 动画在空转；用任务管理器 / 性能计数器定位到具体线程 |
| 空闲内存占用 | **< 250 MB** | 检查是否缓存了过多翻译结果/截图位图未释放；检查 `Graphics`、`Bitmap`、`Image` 是否都 `Dispose`；检查是否有事件订阅没取消（事件是 WPF 内存泄漏的头号来源）；检查 OCR 引擎是否被重复初始化（应该初始化一次复用） |
| 启动时间（第二次起） | **< 2 秒** | 检查启动路径上是否有同步网络请求（更新检查必须异步且延后 3 秒）；检查是否在启动时加载大模型/大数据库；检查是否在启动时扫描目录；用 `dotnet-trace` 或自己打点定位 |
| 启动时间（单文件首次） | **< 5 秒**（首次要把自己解压到临时目录，慢一点正常） | 若超过 5 秒：尝试关掉 `EnableCompressionInSingleFile`（去掉压缩，体积变大但启动变快）；检查是否有杀软实时扫描拖慢解压；确认不是每次都当成「首次」（解压缓存被清理会导致反复变慢） |
| 剪贴板取词耗时 | **< 300 毫秒**（从松手到拿到文字） | 检查剪贴板等待超时是否设得太长（默认 200 毫秒）；检查是否在取词前后做了多余的 UI 操作；检查「还原原剪贴板」是否同步阻塞；剪贴板被占用时要重试 3 次、间隔 50 毫秒，不许无限重试 |
| OCR 识别耗时 | **< 1.5 秒**（含图像预处理） | 检查是否每次都在重新初始化 OCR 引擎（必须初始化一次复用）；减少预处理强度（二值化 + 分行约 200 毫秒以上，按需开启）；限制框选区域尺寸上限（超大区域先缩小再识别）；把 OCR 放到后台线程，别阻塞 UI |
| 翻译请求超时 | **10 秒**（配置项 `翻译.超时秒数`，可调 3-60 秒） | 超时后必须立刻降级到下一个引擎，并把「已降级」状态告诉用户；不许出现「转圈转一分钟」；网络极差时优先切本地离线引擎（若已安装） |
| 连续运行 8 小时内存增长 | **< 50 MB** | 检查钩子/事件订阅是否累积；检查历史记录的 UI 列表是否虚拟化（10000 条记录不虚拟化必然爆内存）；检查缓存是否有上限（翻译缓存必须有条数上限，否则 8 小时会堆满）；每 2 小时主动记录一次内存快照做对比 |
| 钩子回调处理时间 | **< 5 毫秒** | 回调里只允许「读键状态 + 判断状态机 + `PostMessage`」；任何 IO、网络、UI 更新、日志写盘都必须挪到主线程；超时的后果不是变慢，而是**被系统摘钩、软件直接失灵**（原大纲阶段 2 明确警告过） |
| 空闲时网络请求 | **0 次/分钟**（除每 30 分钟一次的主引擎回探，和用户手动触发的检查更新） | 检查是否有定时器在偷偷轮询；回探频率不许调高；回探必须静默失败 |
| 历史窗口打开（10000 条数据） | **< 1 秒** | 必须分页/虚拟化；SQL 要建索引（时间、是否收藏）；搜索走 FTS5 或至少给搜索字段建索引，搜索 < 500 毫秒（对应原大纲测试项 T6-7） |
| 磁盘占用（不含离线包） | **< 100 MB**（配置 + 数据库 + 日志） | 数据库必须有自动清理且**确认它真的在跑**（写日志验证，原大纲阶段 6 常见坑「记录无限增长」）；日志必须轮转（单文件上限 + 保留份数） |
| 程序体积（单文件 exe） | **60-150 MB**（取决于决策 9-2） | 不许开 `PublishTrimmed`（**WPF 不支持裁剪，会直接编译失败或用不了**）；可用 `PublishReadyToRun` + `EnableCompressionInSingleFile` 压到 60-80 MB；离线模型不许打进主 exe（按决策 11-2 走可选下载） |

### 9.1 每次阶段交付前必须实测的三项

1. **空闲 CPU 与内存**（任务管理器，程序空转 5 分钟后读）
2. **本阶段涉及的核心耗时**（剪贴板取词 / OCR / 翻译 / 启动，用日志里的耗时字段读）
3. **连续运行 30 分钟的内存变化**（阶段 12 会延长到 8 小时）

实测结果写进交付说明。**没测过就不许写「性能没问题」。**

## 十、版本号与发布约定

### 10.1 版本号规则（原大纲 2.4，原文保留）

`主版本.次版本.修订号`，例如 `1.2.3`

- 主版本 +1：大改，可能不兼容旧配置
- 次版本 +1：加了新功能
- 修订号 +1：只修 bug

每个阶段完成打一次版本号，记在 `翻译软件\docs\更新日志.md`。

> ⚠️ **版本号比较必须按数字段比较，不许按字符串比较**（否则 `1.10` 会被认为小于 `1.9`，这是原大纲阶段 10 明确列出的坑）。实现一个 `VersionComparer` 工具类统一处理。

### 10.2 各阶段版本号对照表

| 阶段 | 名称 | 版本号 | 产物目录 |
|---|---|---|---|
| 0 | 开工准备 | — （不打版本号，只建环境与目录） | — |
| 1 | 最小骨架 | **v0.1** | `翻译软件\release\v0.1\` |
| 2 | 组合键 + 拖拽监听 | **v0.2** | `翻译软件\release\v0.2\` |
| 3 | 取词 | **v0.3** | `翻译软件\release\v0.3\` |
| 4 | 翻译内核 | **v0.4** | `翻译软件\release\v0.4\` |
| 5 | 显示 A：悬浮窗（**里程碑：核心功能闭环达成**） | **v1.0** | `翻译软件\release\v1.0\` |
| 6 | 显示 B：角落面板 + 历史记录 | **v1.1** | `翻译软件\release\v1.1\` |
| 7 | 显示 C：覆盖原文 | **v1.2** | `翻译软件\release\v1.2\` |
| 8 | 设置中心 | **v1.3** | `翻译软件\release\v1.3\` |
| 9 | 打包发布 | **v1.4** | `翻译软件\release\v1.4\` |
| 10 | 升级通道 | **v1.5** | `翻译软件\release\v1.5\` |
| 11 | 本地离线兜底 | **v1.6** | `翻译软件\release\v1.6\` |
| 12 | 总验收交付 | **v2.0** | `翻译软件\release\v2.0\` |

**规则**：

- 阶段 5 结束时的 `v1.0` 是**第一个正式版本号**，用户从这一刻起拥有了「能用的翻译软件」。
- 阶段的版本号与阶段号严格对应，**不许自行跳号或改号**；中途修 bug 用修订号（如 `v1.0.1`），不许占用别的阶段的号。
- 每次打版本号必须同步做三件事：① 产物放进对应 `release\vX.Y\`；② 更新日志新增一条；③ 必要时更新 `docs\开发文档.md`。

### 10.3 发布脚本与产物位置

**发布脚本固定放在 `翻译软件\tools\脚本\发布.ps1`**（**不能放 `翻译软件\` 根目录**，这是原大纲阶段 9 验收清单里明确查的一条）。

脚本内容以原大纲阶段 9 给的命令为基础：

```powershell
# 翻译软件\tools\脚本\发布.ps1
# 用途：把 src\TranslatorApp 发布成单文件自包含 exe，输出到 翻译软件\release\vX.Y\
# 用法：pwsh -File "翻译软件\tools\脚本\发布.ps1" -Version v1.4
# 注意：WPF 不支持 PublishTrimmed（裁剪），本脚本绝对不能加 -p:PublishTrimmed=true

param(
    [Parameter(Mandatory = $true)][string]$Version   # 例如 v1.4
)

$repoRoot = Split-Path -Parent (Split-Path -Parent $PSScriptRoot)   # 翻译软件\
$outDir   = Join-Path $repoRoot "release\$Version"

dotnet publish "$repoRoot\src\TranslatorApp\TranslatorApp.csproj" `
  -c Release `
  -r win-x64 `
  --self-contained true `
  -p:PublishSingleFile=true `
  -p:PublishReadyToRun=true `
  -p:EnableCompressionInSingleFile=true `
  -p:IncludeNativeLibrariesForSelfExtract=true `
  -p:Version=$Version `
  -o $outDir
```

**产物位置**：`翻译软件\release\vX.Y\`（每个版本一个独立目录，方便用户回退到旧版本）。

**发布后必须验证的四件事**：

1. 在**有开发环境的电脑**上双击能跑。
2. 复制到**另一台没装过开发工具的电脑**上双击能跑（原大纲阶段 9 的唯一核心指标 T9-2）。
3. exe 文件属性里有正确的产品名、版本号、版权信息；资源管理器里显示的是自定义图标（不是默认空白图标）。
4. 中文路径 + 带空格路径下运行正常（例如 `D:\我的 软件\翻译软件.exe`）。

### 10.4 单文件打包的三个已知坑（必须提前防）

| 坑 | 症状 | 处理 |
|---|---|---|
| 配置文件找不到 | 启动报错或配置读不到 | 单文件模式下 `AppContext.BaseDirectory` 指向**临时解压目录**，取真实 exe 路径必须用 `Environment.ProcessPath`；`portable.txt` 的检测也必须基于真实 exe 目录 |
| 首次启动慢 | 要等 5-10 秒 | 关掉 `EnableCompressionInSingleFile`（体积变大、启动变快）；或接受首次慢、第二次快的正常现象（写进说明书，免得用户以为卡死） |
| 杀软误报 | 刚编译出来就被删 | 单文件被误报的概率明显高于文件夹形式；按决策 9-4 的方案处理（提交申诉 + 说明书里教用户加白名单，分 Defender / 360 / 火绒三种）；**除非要发给很多人用，不用买代码签名证书** |

### 10.5 更新检查（阶段 10）

- 在 GitHub Releases（或其他静态位置）放一个 `version.json`：

  ```json
  { "版本": "1.5.0", "下载地址": "https://...", "更新说明": "...", "发布日期": "..." }
  ```

- 软件**启动 3 秒后**（不拖慢启动）异步去拉这个文件。
- 有新版就弹托盘气泡：「发现新版本 v1.5，点击查看」；版本相同则**不提示**。
- **断网时必须静默跳过**，绝对不能因为检查更新失败导致软件启动不了（原大纲阶段 10 常见坑）。
- 设置里能关掉更新检查（配置项 `高级.检查更新`）。
- 版本号比较用 10.1 提到的方式（按数字段比，不许字符串比）。
