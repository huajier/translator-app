## §2 ⑧ 是假证据（硬问题）

### 证据一：数字对不上

```
[2026-11-03 13:45:33.209] 翻译：成功，275 字 → 译 280 字，用时 381 ms
```
- 真 Bing 翻 275 字英文，实测 **1721~2873ms**（`_f2_长文本_out.txt`，15 次）。
- 这里 **381ms**。差 5~7 倍。
- 275 → **280** 字：`【假译文】` 恰好 5 个字符，**275 + 5 = 280，一个字不多一个字不少**。

### 证据二：截图里能直接看见

`tools\日志\取证截图\t3a补_20261103_134524.png` 的译文块第一行：
```
【假译文】The ancient gate stood silent at the edge of the valley.
```
（我裁剪放大确认过，不是 OCR 误读）

### 证据三：脚本自己写着

`tools\脚本\验收-T3a补-时序.py:117`
```python
setcfg(True, "http://127.0.0.1:%d" % PORT)     # PORT = 5099
```

### 为什么这不算「小抄」

`⑧` 这一条**唯一的目的**就是证明 P0-F1（冷启动认字慢 → 翻译被饿死）修好了。
用假服务器验：假服务器 2ms 返回，**不管预算怎么设都不会饿死**。
**这个测试条件本身消灭了它要测的东西。** 换成真 Bing（P50 2070ms 长文本）才有意义。

### 要求

用 **`translateEndpoint = ""`（真 Bing）** 重跑一次冷启动，必须：
1. 打完 exe **冷启动**（不是热身后的第二次）；
2. 日志里 `翻译：成功` 的译文长度 **不等于** 原文 + 5；
3. 耗时量级与 `_f2_长文本_out.txt` 一致（1700ms 以上），**不许出现 300ms 级**；
4. 截图里译文块**不含 `【假译文】`**；
5. 如果真 Bing 超了 2500ms 硬闸**那也是有效结果**——如实报「冷启动第一次超时了」，不许拿假服务器掩盖。

## §3 新发现三条

### P1-G1 翻译失败时译文区整块收起，卡片会跳一下（本轮引入，但不严重）

**先纠正我自己**：我在初稿里写「『翻译中…』被截断成『翻译中文』」，**那是我看错了，截图里没有这回事**。
截图那一帧是成功态，译文块显示的是假服务器回显。**这条按事实重写。**

实读代码（`DebugToastWindow.xaml.cs:549`）：

```csharp
HideTranslation();          // ← :549 先整块收起

if (translation is null || Failure is None or Disabled) return;   // :553-558 正常态

// 失败：只往 DetailText 追加一句
string msg = translation.Failure.ToUserMessage();
if (msg.Length > 0) DetailText.Text += Environment.NewLine + msg;   // :561-562
```

**行为**：译文区先显示「翻译中…」（撑开约 200px + 分隔线），失败时整块收起，原因挤到最下面那行小字里。

**严重性：比我先想的小。** 原因**确实显示了**（`DetailText += msg`），用户不会「不知道为什么没译文」。
真正的问题只是**布局跳动**：卡片先长高 213px，再缩回去。

**这条降级为 P1，不是 P0。** 改不改都行，改的话顺手：失败时别 `HideTranslation()`，
把译文区文字换成失败原因、保留可见，卡片就不会跳。

**为什么还是要记**：因为它暴露一个模式——**我们每加一个译文区状态，就有多一条路径会整块收起**。
下一轮如果有人再往译文区加东西（比如「重试」按钮），先想清楚失败态长什么样。

### P1-G2 真机认字 P95 是 656ms，不是 259ms

方案 13.6 表里写「原文可见（认字）P50/P95 = 45 / **259 ms**」。那是**回放**的数字（图片已在内存里）。
我从 `app-20261103.log` 抽 **3088 条真机取词**：
```
真机取词 n=3088  min=15  P50=47  P95=656  max=7844
```
**P95 是 259 的 2.5 倍，max 7844ms。**
方案那张表把回放数字列成「原文可见」，会让用户以为真机也 259ms。**要么标「回放」，要么补真机一列。**

### P1-G3 长文本真 Bing 耗时「含不含取票」没交代

`_f2_长文本_out.txt` 里 15 次都是 1721~2873ms。但真机冷启动第一次要先 `GET /translator` 取票（424ms）。
**这 2873 是不是已经含了取票，看不出来。** 如果没含，真机冷启动最坏是 424 + 2873 = 3297ms。
必须在证据里写清楚：**每次是否重新取票、timer 从哪一行开始记**。

## §4 关于用户的「框歪」—— 现在有图了，能下结论

### 4.1 这轮框**没有歪**

截图对比：
- 左上是脚本自己开的文字窗口（`100~1000 × 100~520`）
- 右下是卡片，原文识别结果：
  ```
  The ancient gate stood silent at the edge of the valley. Nobody in the village
  remembered who had carved the runes, or why the stone still hummed whenever the moon rose.
  Children were warned to keep their distance, and hunters took the long road around the hill even in snow.
  ```
- 脚本断言：`开头20字在=True 结尾20字在=True 长度 285 / 原文 275 = 104%` ✅

**内缩 60px 那招生效了。** 之前日志里满屏的 `⚠️ 选区的左边、右边和下边正好顶在文字上` 在这条里**没有出现**。

### 4.2 但「框歪」的历史原因已经查清

回看旧日志（`10:40` 那批）每次都在报警，因为框 `150~950` 而文字窗口 `100~1000`，**右边只差 50px**。
现在 `160~940`（四周留 60px）就干净了。**这证明「框歪」跟看不见没有关系，纯粹是坐标贴太近。**

### 4.3 识图能干什么、不能干什么（用户 m01109 澄清：架构师与执行 AI 都已开识图）

**先纠正我上一段的结论。** 我原来写「不需要给 AI 开识图」，**这句话错了**。用户已经给两边都开了。
错在哪：我把「识图用来预测」和「识图用来验证」混成一件事，只否掉了前者就下了全否的结论。

**必须分清这两件事：**

| 用法 | 判断 | 理由 |
|---|---|---|
| 看图**猜**框选坐标该是多少 | ❌ 差 | 坐标系是确定的，眼睛估出来还是猜，估完照样可能歪。内缩 60px 才是解法。 |
| 看图**验证**结果对不对 | ✅ 好 | 切没切字、译文块是不是空的、卡片有没有出屏幕——**这些日志断言查不出来，眼睛一眼就能看出**。 |

**这一轮正好有个铁证**：⑧ 交的证据里，译文块第一行写着
`【假译文】The ancient gate stood silent...`。
**执行 AI 只要看一眼自己存的那张截图，当场就能发现自己在拿假服务器充真 Bing。**
它没看（或者看了没当回事），于是把一个假结论交上来了。

→ **所以识图对执行 AI 的第一价值不是「框得准」，是「别自己骗自己」。**

### 4.4 从这轮起加一条验收规则：截图必须人眼/机器眼过一遍

脚本自动存的图（`tools\日志\取证截图\t3a补_*.png`）**不许只存不看**。

- 执行 AI 每交一轮真机验收，**必须先打开自己存的截图看一遍**，确认：
  1. 译文块里是**中文**，不是原文回显、不是 `【假译文】`；
  2. 原文没有被切掉首尾；
  3. 卡片四边都在屏幕内。
- 汇报里要写一句「**已看图确认**」，写不出这句就等于没验。

**这条比任何日志断言都便宜**：图已经自动存了，多看的成本是零，漏看的成本是这一整轮白干。
