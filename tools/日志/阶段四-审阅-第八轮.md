## 0. 结论先行

**A（MyMemory）在隐私上不可接受；B（Bing 网页翻译）在速度上必须改预算。**
两者都不能「原样照抄就上线」。下面逐条摆证据，最后给两条必须用户拍板的点。

我的沙箱 TLS 全死（第六轮 §3），只能用宿主 `web_fetch` 抓 **A**。B 我一条也验不了 —— 下面的 B 数据全部来自执行 AI 汇报，**我没亲手验过，标为「未独立复核」**。

### A 的两个**汇报里没有**、我自己抓到的严重问题

**问题一：发出去的每一句，都被写进了它的公共翻译记忆库。**
证据：上面每一条响应里 `matches[0]` 的 `segment` 就是我刚发的原文，`translation` 就是它刚给的译文，`created-by:"MT!"`，而 `create-date` **就是我发请求的那一分钟**（`2026-11-02 04:43:43`、`04:44:03`、`04:44:17`、`04:44:35`）。
→ `id:0` 这一条不是「它事先有的记忆」，是**它把我刚发的东西存下来了，再当作「记忆命中」返回给我**。
→ MyMemory 的主域 `/doc/usagelimits.php`、`/doc/spec.php`、`/tos` 我全部抓不到（`TypeError: fetch failed`），**公开范围我无法核实**，但「原文会被存下来」这件事已被实测确认。

**问题二：记忆库命中优先，命中了错的也照抄。**
证据：`q=BACK&en|zh-CN` → 「后退」（游戏 UI 里 BACK 是「返回」），`match:1`；同一响应第二条候选才是「返回」，但它返回的是「后退」。
`q=test` → `test`（没翻）。执行 AI 报的 `yes→yes`、`no→no`、`hello world→hello world` 我复核属实。

**问题三（执行 AI 报的）：`autodetect` 对极短词失准。**
`yes` 判成 `en` 却原样返回；`no` 判成 `es` 原样返回。**显式 `en|` 也一样会回显**（我实测德文串 `Drücke E, um mit dem Terminal zu interagieren.` 配 `en|zh-CN` → 原样返回德文）。
→ **「译文 == 原文」必须由我方无条件判为失败，不能信它自报的 200。** 这一条是 T3a 的硬要求。

## 2. A 路线的四个硬伤

| # | 硬伤 | 严重度 |
|---|---|---|
| A1 | **原文进公共翻译记忆库**（实测，见 §1 问题一） | 隐私，不可逆 |
| A2 | 记忆库命中优先，错译静默通过（BACK→后退，test→test） | 质量，用户看不出错 |
| A3 | **500 字符硬上限**，HTTP 200 + body 报 403；超了必须切段 | 功能，需分段逻辑 |
| A4 | 多行整块可用（✅ 好消息），但一句超 500 就要切成多请求，行对齐会乱 | 功能，需对齐逻辑 |

## 3. B 路线的两个硬伤

| # | 硬伤 | 严重度 |
|---|---|---|
| B1 | **P50 768ms / P95 966ms**（执行 AI 测，我没复核）+ 认字 P95 309ms → **常态必然破 D4 的 800ms** | 预算，必须改 |
| B2 | 依赖抓 `cn.bing.com/translator` 页面的 `IG` 与 `params_AbusePreventionHelper`，**页面结构一变全线挂** | 脆弱，无法预防 |

B 的优点也确认：结构就是 Azure 的 `[{"translations":[{"text","to"}],"detectedLanguage"}]`，`to=zh-Hans` 生效，`usedLLM=true`，质量明显好于 A，5000 字符也能翻（只是 9.4 秒）。

## 4. 架构师裁决倾向

**推荐 B 为主、A 只作为「B 挂了时的明示降级」，而不是默认**。三条理由：

1. **A1 是隐私问题，不是质量问题。** 这个工具的核心能力是「框选屏幕上任意区域」。用户框到的可能是游戏、可能是聊天窗口、可能是邮件。A1 意味着**框到什么都永久进第三方公共库**。这条不能靠提示语解决 —— 用户点了同意，第二天框了个含密码的窗口就完了。
2. **A2 是「看起来成功但是错的」。** 比翻译失败更糟：失败用户会重框，错译用户会读进去。
3. **A3/A4 让 A 的代码比 B 还复杂**（分段 + 行对齐 + 回显判定），省下的那 300ms 不划算。

**但 B1 必须处理**：如果走 B，D4 的「单次 ≤800ms」在物理上做不到。
不能既要求 B 的质量，又要求 800ms —— 这是让执行 AI 去完成一个不可能的任务，最后它一定会偷偷放宽口径糊弄过去。

## 5. 必须用户拍板的两个点

**问 1（隐私）**：A 会把你框到的原文永久存进它的公共翻译库（实测确认）。你是接受「只在游戏里用、不上传敏感窗口」，还是干脆不走 A？

**问 2（速度）**：B 质量好但慢，一屏文本从框完到看到译文大约 **1.0~1.3 秒**（现在认字 0.3 秒 + 翻译 0.8~1.0 秒）。你能接受这个等待，还是宁可它快一点、质量差一点？

## 6. 用户拍板（2026-11-02）

| 问题 | 回答 | 落成规则 |
|---|---|---|
| 公共记忆库 | **「只用 Bing，不接 MyMemory（推荐）」** | **A 路线整体废弃**。不写 `MyMemoryProvider`，不写任何降级到 A 的分支。第八轮 §2 的 A1~A4 只作为历史证据保留 |
| 速度 | **「先按 1500ms 做，等你真用几天再回来调」** | D4 的「单次 ≤800ms」**对翻译路径作废**，改为：端到端（框→出卡）P95 ≤ 1500ms；硬闸 2500ms |

**D4 修正记录**：原「单次 ≤800ms」是阶段三只认字时的指标，阶段四引入联网翻译后不成立（Bing 纯翻译 P50 768ms / P95 966ms，我未独立复核）。新指标＝**端到端 P95 ≤1500ms**，理由＝用户明确接受，且这是 Bing 通道下唯一可达的数。

## 7. T3a 裁决：放行，但有五处与方案原文不同

| # | 方案原文 | 裁决 |
|---|---|---|
| 1 | Azure 协议（POST JSON + `Ocp-Apim-Subscription-Key`） | 改 **Bing `ttranslatev3` 表单协议**，无密钥 |
| 2 | `ITranslationProvider` 接口留两个实现 | **只留接口，只写 `BingFreeProvider` 一个实现**。MyMemory 不写（隐私）、Azure 不写（无密钥） |
| 3 | `TranslationCache` 独立文件 + SHA256 + 30 天 TTL + 500 条 + 2 秒防抖落盘 | **砍成内存 `Dictionary`，200 条上限，不落盘、不做 TTL**。键直接用规范化后的原文。理由：跨重启复用是方案自加的需求，用户没提；落盘那套占掉的文件比它省下的还多。升���路径：真需要跨重启时再加，键和现在一样 |
| 4 | 500 字符超限要分段 | **Bing 无此限制**（实测 5000 字符可翻）。**不做分段**。超时（2500ms 硬闸）就显原文 + 超时文案，不截断 |
| 5 | 「译文 == 原文」要判失败 | **Bing 上不加这条**。A 的回显 bug 是 A 的 TM 机制，Bing 无证据。等 T6 真机抽检出现再补，现在加是凭空防御 |

**另加一条硬要求（第八轮 §1 的教训）**：`statusCode` 与 HTTP 状态**都要判**。Bing 恒回 HTTP 200，错误藏在 body 的 `statusCode` 里；MyMemory 同样恒 200。这个项目的每条联网通道都必须假定「HTTP 200 不代表成功」。

**顺带修的线上 bug**：`src\UI\Shared\DebugToastWindow.xaml.cs:447-455` `ChannelNameOf` 缺 `"RapidOCR"` 分支，主通道的英文原名会被原样印在卡片上（第一轮 P1 起就没修）。T3a 顺手补一个 `case`。
