## 2 P1-K1 段数上限有漏洞（必须修，一行）

`src/Core/Translate/LongTextTranslator.cs:215`：

```csharp
if (text.Length / SegmentChars > MaxSegments)
    threshold = (int)Math.Ceiling(text.Length / (double)MaxSegments);
```

**整数除法把 8.xx 段截成 8**，于是 3332~3599 字这一档不抬阈值，实际切出 **9 段**。
我按 C# 逻辑复刻算法验算（每行 100 字）：

```
3130 字 -> 阈值 400 -> 8 段
3231 字 -> 阈值 400 -> 8 段
3332 字 -> 阈值 400 -> 9 段 ← 超过上限
3433 字 -> 阈值 400 -> 9 段 ← 超过上限
3534 字 -> 阈值 400 -> 9 段 ← 超过上限
3635 字 -> 阈值 455 -> 8 段
```

它自己的注释写的是「保证最多 8 次网络往返」，**代码和注释对不上**。
修法（一行）：

```csharp
if (text.Length > SegmentChars * MaxSegments)
```

这样 3332 字触发抬阈值到 ⌈3332/8⌉ = 417，切出 8 段。

**为什么值得单独开一轮修**：这不是理论边界。用户 m02194 原话「我会故意框很长做压力测试」，
3300~3600 字正好是「一整屏长段落 + 一点余量」的量级。多一段 = 多一次网络往返 ≈ 多等 0.5~2 秒，
而且是在最慢的那条路径上多等。一行代码换 2 秒，划算。

## 3 P1-K2 400 字阈值的体验账（不修，但要跟用户说清）

用 S1 三个真 Bing 实测点拟合单段耗时：**t ≈ 507 + 4.84 × 字数**

| 每段字数 | 预计单段 | 占 5000ms 硬闸 | 首段出字时间 |
|---|---|---|---|
| 400 | 2441 ms | 49% | 2.4 秒 |
| 700 | 3892 ms | 78% | 3.9 秒 |
| 800 | 4376 ms | 88% | 4.4 秒 |

同一段 1214 字：

| 阈值 | 段数 | 预计总耗时 |
|---|---|---|
| 400（现用） | 4 段 | 7899 ms |
| 800 | 2 段 | 6885 ms |

→ **400 字让用户多等 1 秒，但第一段早 2 秒出字。**
用户 m02291 拍板选串行 + 逐段显示，核心理由就是「早看到东西」。
所以 400 是对的，**不改**。但 7683ms 这个总数要明告用户：以前 4.9 秒直接失败，
现在 7.7 秒一定成功 —— 拿 2.8 秒换「不再白等」。
