## §3 新发现的两条 P0

### P0-F1 冷启动第一次框选，必定拿不到译文

- **证据（方案 12.4.1 自己写的）**：「首次框选时 RapidOCR 引擎初始化 + 小框 3 倍重试占掉 **1900~2100ms**，翻译只剩 300ms 预算，必然报『超过硬闸（这段只剩 300 ms 预算）』，卡片上没有译文。」
- **我从日志复核，比它说的更糟**：`app-20261103.log` 真机四条
  ```
  10:40:01 → 10:40:03   总耗时 1922 ms   （进程内第一次）
  10:40:14 → 10:40:15   总耗时 1016 ms
  10:40:21 → 10:40:21   总耗时  579 ms
  10:40:28 → 10:40:32   总耗时 4031 ms   （换了个大框 950×360，又慢回去了）
  ```
  **1922ms 和 4031ms 都超过 2500ms 硬闸**，`budget = 2500 - e2eMs` 直接 ≤ 0，翻译**一个请求都不发**。
- **用户视角**：装好软件 → 第一次框选 → 看到原文 + 一行「翻译超时」→ **以为翻译功能是坏的**。
  这不是边缘情况，是**每个用户的第一印象**。每次重启进程后的第一次框选都会这样。
- **根因**：硬闸语义错位。现在 `HardTimeoutMs = 2500` 被当成「从框选到看见卡片总共 2500ms」，
  于是「认字慢」和「翻译慢」共用同一个 2500 预算池。**认字慢不该饿死翻译**——它们是两件独立的事，
  用户能接受「第一次启动慢一点」（那也是我们自己的模型加载），不能接受「翻译没生效」。
- **改法（最小正确解）**：
  ```csharp
  // 翻译至少给这么多预算，不管认字花了多久。
  // 理由：认字慢是我们自己模型加载的锅，不该让用户看到「翻译没生效」。
  // 1500 ≈ 真 Bing P50 1040 + 余量；认字再慢也保证翻译有一次机会。
  public const int MinTranslateBudgetMs = 1500;
  int budget = Math.Max(MinTranslateBudgetMs, HardTimeoutMs - (int)e2eSw.ElapsedMilliseconds);
  ```
  代价：冷启动第一次框选端到端最长 ≈ 2100 + 1500 = 3.6 秒。
  **但这个交换必须做**——「第一次就看不到译文」比「第一次慢 1 秒」严重得多。
- **要求**：改完必须真机验「打完 exe 冷启动第一次框选能看到译文」，**不能用热身过的第二次冒充**。
  P0-E2 的验收是靠 warm=True 热身规避的，这次不许绕。

### P0-F2 「端到端 P95 ≤1500ms」这个指标已经名存实亡，得重新拍

- **事实**：真 Bing 单项 P50 1040 / P95 1240ms（`_p0e4_out.txt` 六次实测）。
  认字 P95 309ms（阶段三收口数据）。**1040 + 309 = 1349ms**，已占满 1500 的 90%；
  P95 叠加 **1240 + 309 = 1549ms**，**直接超**。
- 而这只测了 `Hello world` / `line 1 test` 这类**极短串**。300 字整块的翻译耗时**根本没测过**。
- 更关键的是：**§S2 那张表里 P50 46 / P95 221 是假服务器数字**，和真 Bing 并排放，
  中间没有一道分隔线说明「这一半是真的、那一半是假的」。用户看到会以为真机也 200ms。
- **这不是执行 AI 的错**，是我上一轮没把口径写死。现在补：
  1. 方案里所有耗时表**必须两列分家**：`假服务器（本地，仅供回归）` / `真 Bing（联网，用户实际体验）`。
     两列不许写成同一张表的相邻格。
  2. 「端到端 P95 ≤1500ms」对**真 Bing** 已不可达，需要用户重新拍一个数（见 §5 待问）。
  3. 长文本（≥200 字）的真 Bing 翻译耗时，**必须补测**。现在是空白。

## §4 用户问的「AI 框歪」+「要不要开识图」

### 4.1 我这边的事实

我试了 `read_image`（读 `tools\日志\取证截图\sel_20261014_091520_107.png`），报：
```
Error: cannot read ... as an image: model "deepseek-v4.1-flash" does not declare image input;
switch to an image-capable model to read images
```
**我确实看不见图。** 但这只解释了「我看不到结果」，**不解释「框歪」**。

### 4.2 开了识图也治不了框歪

框歪的根因不是「看不见」，是**测试脚本用写死的坐标去框一段它自己都不确定在哪的文字**。

看 `_p0e2_验收.py` 的做法：
```python
# 造字窗口（SHOW_PS）
$f.Left = 100; $f.Top = 100; $f.Width = 900; $f.Height = 420

# 框选坐标（写死）
args = ["150", "150", "950", "450"]
```
**这个做法是对的**——脚本自己开的窗口、自己写的文字，坐标是它自己定的、精确已知的。
`P0-E2` 能取到 1342 字、断言全 PASS，靠的就是这个，**不是靠视觉**。

**但即使这样，日志里每次真机框选都还在报警：**
```
⚠️ 选区的左边、右边和下边正好顶在文字上，很可能切到了半个字，
   结果可能少一两个字，建议把框放宽一点再试
```
为什么？因为 `SHOW_PS` 的文字窗口是 `100~1000 × 100~520`，而框是 `150~950 × 150~450`——
**右边界 950 离文字窗口右边界 1000 只有 50px，而 `TextBox` 里的长句会一直排到右边缘**。
框压着文字了。这是「框内缩不够」，不是「看不见」。

**所以：给 AI 开识图 → 它能看到框歪了 → 但它还是只能猜一个新坐标去改 → 还是可能歪。治标。**

### 4.3 真正的解法（三条，都不需要识图）

**① 脚本造的字，框选区比文字区内缩一圈。**
```python
# 文字窗口 100~1000 × 100~520，就往里缩 60px 再框
$f.Left = 100; $f.Top = 100; $f.Width = 900; $f.Height = 420
args  = ["160", "160", "940", "480"]     # 四周都留 60px 余量
```
保证框全、必然不切字、必然不带进窗口边框。

**② 验收必须断言「认出来的内容对不对」，不能只断言卡片高度。**
现在 `_p0e2_验收.py` 只有两条断言：
```
断言1 译文真画上去(开>关)：PASS
断言2 限高生效(增量 <= 220px)：PASS
```
**两条都只看卡片尺寸，一条都没看认出来的字。** 框歪了、只认到半句话、认成乱码——照样两条 PASS。
必须加：
```python
assert LONG_TEXT[:20] in ocr_text      # 开头认得对
assert LONG_TEXT[-20:] in ocr_text     # 结尾认得对（这条专门防框歪切掉尾巴）
assert len(ocr_text) >= len(LONG_TEXT) * 0.95   # 没丢大段
```

**③ 需要视觉的场景，让程序自己截图存档，人看，不用 AI 看。**
`tools\日志\取证截图\` 已经有这个机制（`sel_*.png`）。真出现框歪，人打开图看一眼就定位了，
比我猜坐标快得多。**要加的不是「AI 识图」，是「每次真机验收自动存一张截图 + 认出来的原文」**，
这样人和我都能事后核对。

## §6 需要用户拍板的一件（已发问）

`HardTimeoutMs=2500` 现在同时管「认字慢」和「翻译慢」，导致冷启动第一次框选没译文。
