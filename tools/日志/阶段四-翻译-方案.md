## 2. 配置

settings.json（`%APPDATA%\TranslatorApp\settings.json`）新增 5 个键，全部走 `AppSettings` 现有的 Load/Save 双写模式（漏写 Save 会被下次保存抹掉——S4 已踩过）：

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `translateEnabled` | bool | **false** | 总开关，默认关（隐私见 §5） |
| `translateApiKey` | string | `""` | 微软 Translator 密钥 |
| `translateRegion` | string | `"global"` | 资源区域；global 资源可不填 |
| `translateTargetLang` | string | `"zh-Hans"` | 目标语言 |
| `translateEndpoint` | string | `https://api.cognitive.microsofttranslator.com` | **可改**，验收测试指到本地假服务器（见 §7） |

密钥优先级：环境变量 `TRANSLATOR_API_KEY` > settings.json。**唯一写了密钥的地方要脱敏**：日志里只打前 4 位 + 长度。

**免费额度（官方文档，2026-10-31 实测抓取）**：
- F0 免费层：**200 万字符/月**，标准翻译与自定义训练合计。
- 每小时 200 万字符上限，建议每分钟不超过约 33,300 字符（滚动窗口）。
- **每个请求最多 50,000 字符**；按字符计费，不按请求数。
- 官方延迟：100 字符以内通常 **150~300ms**，最长容忍 15s。
- 我们一条整块最坏 300 字符 → 单次远低于限额，2M/月约够 6000+ 次整块翻译，日常够用。

**超时与重试**：
- `HttpClient.Timeout` 不设（改用 `CancellationTokenSource`），单次预算 **2.5s**——目标 800ms 是常态值，2.5s 是硬闸，超过就当失败、只显示原文。
- 429 / 500 / 503 / 408 → 重试 **2 次**，退避 300ms、900ms（合计最多 3 次请求）。
  （408 官方含义是「资源缺失 / 自定义翻译系统未就绪」，**不是网络超时**，见 9.20；我方超时只由 2.5s 预算触发。）
- 401 / 403 → **不重试**，直接进「密钥无效 / 额度用尽」，并且**冷却 60 秒**内不再发请求（避免每次都等超时）。
- 400 → 不重试（请求本身有问题，重试只会烧额度）。

## 3. 缓存

**键的定义**（2026-11-02 按 9.12 修正，原文是 `+ "|" + from + ">" + to`）：

```
cacheKey = SHA256( normalizedText + "|" + targetLang )
```

- `normalizedText`：`Trim()` + 连续空白折成一个空格 + 换行统一为单个空格（**不是** `TextNormalizer.Normalize`，那是判分口径，不许给它加职责）。
- **`from` 不进键**：不传 `from`，让 Azure 自动检测（理由是本地 `LanguageDetector` 只有三档，见 9.12）。同一段文字 + 同一目标语言 → 译文唯一。
- **`targetLang` 必须进键**：换母语就要重翻，不进键会命中旧语言的译文。
- **区域不进键**：同一句英文在屏幕左上和右下应该翻成一样的东西，把区域塞进键只会让命中率变低。区域作为缓存条目的**附加字段**存下来，给「同区域复框」统计用，不参与查找。
- 中英文对（`zh>zh-Hans` 之类）直接跳过翻译，记 `Disabled`，不进缓存。

**存储**：`%APPDATA%\TranslatorApp\translate-cache.json`
- 结构：`{ "version": 1, "entries": { "<hash>": { "src": "...", "dst": "...", "to": "zh-Hans", "at": "2026-10-31T13:00:00Z", "hits": 3 } } }`
- 上限 **500 条**，超了按 `hits` 升序 + `at` 升序淘汰（LRU 近似）。
- 失效：**TTL 30 天**（重启不失效）；`version` 变了整份丢弃（换引擎/换模型时用）。
- 写入：内存命中立刻返回；磁盘写**防抖 2 秒**合并，程序退出时 `OnExit` 强制刷一次。
- 命中耗时目标 **<10ms**（纯内存查表）；实测 `tools\临时\` 里有现成的计时代码可复用。

## 4. 失败态（不许白屏）

原则：**认字成功就必须显示原文**；翻译失败只在详情行加一句，绝不覆盖原文。

| 情况 | 卡片上显示 |
|---|---|
| 正常 | 原文（蓝）+ 分隔线 + 译文（白） |
| 无网络 / DNS 失败 | 原文 + 详情行末尾「没连上网，只显示原文」 |
| 超时 | 原文 + 「翻译超时，只显示原文」 |
| 403（读 `error.code` 再定：`403001` = 免费额度用尽） | 原文 + 「翻译额度用完了，只显示原文」 |
| 401 密钥无效（`401000` 凭据缺失/无效、`401015` 格式不对） | 原文 + 「翻译密钥无效，请检查设置」 |
| 408（`408001` 自定义系统未就绪） | 原文 + 「翻译服务暂时用不了，只显示原文」——**不是超时**，见 9.20 |
| 返回空串 | 原文 + 「没翻出内容，只显示原文」（且**不写缓存**） |
| 认字本身失败 | 维持现状（`ToUserMessage()`），不涉及翻译 |

实现：`UpdateWith(result, translation)` 里判断 `translation?.Failure`，追加到 `DetailText`（现有代码 `:412` 已经在末尾追加 S4 提示，同一位置再追加一句，用 `\n` 分隔）。译文字段为空时整块隐藏，不留空行。

`HttpListener` 在 `localhost:5099` / `127.0.0.1:5098` 都抛 `System.PlatformNotSupportedException`「此平台上不支持该操作」；
`[System.Net.HttpListener]::IsSupported = False`；环境 Win10 19045 / PS 5.1.19041.7291。
`TcpListener 127.0.0.1:5097` 往返正常。所以用 `System.Net.Sockets.TcpListener` 手写最小 HTTP（零新依赖，仍是一个 `.ps1`）：

1. 单线程 `AcceptTcpClient` 循环足够（测试工具，不并发）。
2. 读请求头到 `\r\n\r\n`，再按 `Content-Length` 读 body。
3. 回包两处必须对，否则客户端挂死或 JSON 解析失败：
   - `Content-Length` 用 **UTF-8 字节数**（不是 `string.Length`）；
   - `Content-Type: application/json; charset=utf-8`。
4. 端口 **5099**，占用就 +1 重试，**实际端口打进输出**。

模式：`ok` / `401` / `403`（响应体带 `error.code`）/ `408` / `429` / `empty` / `timeout`（拖过 15 秒）/ 非 JSON，
按查询参数或环境变量切。验收用 `Invoke-RestMethod` 逐个打一遍，状态码与响应体抄进汇报【数字】。

**验收补充（2026-11-02）**：
- `Invoke-RestMethod` 遇非 2xx 会**抛异常**且**拿不到响应体**，必须用 `[Net.HttpWebRequest]` 或
  `$_.Exception.Response.GetResponseStream()` 读 —— 我们要验的正是响应体里的 `error.code`。
- `ok` 模式必须返回**中文译文**（不是 `"OK"`），否则测不出 `Content-Length` 那个坑。
- 必须有一轮 `timeout` 模式 + 客户端 **2.5s 预算**，证明超时能被打断（§2 的硬闸）。
- 服务器要在**独立进程**里起（本机 `Start-Job` / 后台作业在脚本内起不来，实测 20 秒也探不到端口）；
  验收脚本只探 5099..5106 端口，别去 Parse 服务器打印的中文端口号（PS 5.1 会乱码）。

## 11. 审阅修正（第八轮，T3a 落盘 2026-11-03）

第八轮裁决把 T3 拆成 T3-spike / T3a / T3b / T3c，并**整体废弃 A 路线（MyMemory）**。
本节只记 T3a 实际落地时与原文不同的地方，以及验收数字。

### 11.1　路线：只用 Bing，不接 MyMemory

`GET https://edge.microsoft.com/translate/auth` 实测恒 404（15 个变体全 404），Edge 免密钥通道那条路不通。
MyMemory 实测有硬上限 **500 字符**（501 字符即 403，HTTP 仍 200）、`autodetect` 会**空转**（`yes→yes`、`hello world→hello world`，`responseStatus` 还是 200）。
Bing 网页翻译 `POST /ttranslatev3` **无长度上限**（5000 字符通）、结构与 Azure 一致、有 `detectedLanguage`，胜出。
→ **不写 `MyMemoryProvider`，不写任何降级到 A 的分支。** 只留 `ITranslationProvider` 接口 + `BingFreeProvider` 一个实现（接口留着是因为免密钥通道没进公开文档，随时可能改）。

### 11.2　速度指标变更：≤800ms 对翻译路径作废

D4「单次 ≤800ms」原指认字。加上翻译后改为**端到端（框→出卡）P95 ≤ 1500ms，硬闸 2500ms**。
Bing 实测 10 次 P50 768~800ms / P95 966ms，800ms 单段预算装不下。

### 11.3　缓存：一个 Dictionary，不落盘、不做 TTL

`TranslationService` 里 `Dictionary<string, TranslationResult>` + `Queue<string>` 做 FIFO，上限 200 条。
`cacheKey = 规范化原文 + "|" + translateTargetLang`。**不传 from**（用户要「除中文外全翻」，本地 `LanguageDetector` 只有中文/俄文/拉丁三档，硬传 from 会把「全翻」砍成三种）。`detectedLanguage` 记进 `TranslationResult`，不进键。
命中要记**本次命中耗时**（`hitSw`），不是当初那次网络耗时 —— 后者会把「这次有多快」测成「上次有多慢」。

### 11.4　不做分段、不加「译文==原文」判定

Bing 无长度限制，超时就显原文，不分段。空转无证据（MyMemory 才空转），等 T6 抽检。

### 11.5　`statusCode` 与 HTTP 状态都要判

Bing **HTTP 恒 200**，错误全在 body 的 `statusCode`：`205`=token 失效、`400`=参数不合法、`403`=额度、`429`=限流。
`205` → 强制刷新 token 重试**一次**，二次仍 205 报 `AuthFailed`。token 只存内存，**绝不落盘**。

### 11.6　硬闸要扣掉认字已花的时间

`sig` 实测：连「拒绝连接」的回环端口，单次 TCP 尝试本身就要 **2060ms**。
原 `CancelAfter(2500)` 从翻译入口起算，认字花掉的不在闸内 → 端到端 max 冲到 2930ms。
改成三段：
- `RunCaptureAsync` / `RunAsync` 开头起一个 `Stopwatch`，预算 = `HardTimeoutMs - 已用`；
- `budget <= 0` 时不发网络，直接 `Timeout` + 「到这一步已用 N ms，端到端预算用完」；
- `TranslationService.TranslateAsync(text, budgetMs, ct)` 里 `CancelAfter(budgetMs - CancelOverheadMs)`，`CancelOverheadMs = 120`（取消不是瞬时的，正在 connect 的 socket 要等内核收回，实测 24~60ms）。
→ 修完 S3 的 max 从 2930 → 2395ms，进闸。

### 11.8　验收脚本的两个坑（脚本已删，教训留这）

1. **换 `-TokenSalt` 重启验不到 205**：每次回放都是新进程，内存里没有旧 token，第一次取票就是新的。要验 205 得靠假服务器 `-RotateAfter N`（成功 N 次后自己换票），同一进程下一次请求才 205。

### 13.1　显示时序改成两段（撤销第九轮 P1-C2）

第九轮 P1-C2 曾要求「原文和译文必须一次 `UpdateWith` 画完，不许先画原文再补译文」。第十一轮用户拍板撤销，理由：`UpdateWith` 每次进来都会 `_closeTimer.Stop(); Interval = 3s; Start();` 重置计时器，所以译文落地时用户**重新拿到完整 3 秒**，不存在「译文刚出来卡片就关了」。

新时序（`src/TranslatorApp/App.xaml.cs` 的 `RunCaptureAsync`）：

```
认字完成
  → card.UpdateWith(result, null, translating: true)    ← 原文 + 「翻译中…」
  → await TranslateAsync(...)
  → card.UpdateWith(result, translation)                ← 原文 + 真译文
```

翻译没启用时**只调一次**，和阶段三完全一致，不多一次重绘。

`UpdateWith` 第三个参数 `bool translating = false`；`ApplyTranslation` 最前面接 `if (translating)` 分支，只动 `TransScroll` + `TransSep`（显示「翻译中…」，中文省略号不是三个点），**不碰原文和详情行**。

**代码里留了长注释**（`src/UI/Shared/DebugToastWindow.xaml.cs`），写明「旧的『必须一次 UpdateWith』已撤销，不要看到第九轮 P1-C2 的记录就改回一次调用」。旧记录还在 `tools\日志\阶段四-审阅-第九轮.md`，注释是给后来翻旧账的人看的。

### 13.2　翻译态用 8 秒计时器，不是 3 秒

原文画出来后 3 秒就关窗，而翻译最坏要 2.5 秒，余量只剩 0.5 秒 —— 用户大概率看到「翻译中…」然后卡片没了。

改 `UpdateWith` 末尾：

```csharp
_closeTimer.Interval = translating ? PendingCloseDelay : TimeSpan.FromSeconds(CloseDelaySeconds);
```

## 15. 第十三轮：硬闸 2500 → 5000（2026-11-03）

### 15.1　为什么改

`src/Core/Translate/TranslationService.cs:34` 的 `HardTimeoutMs` 从 `2500` 改为 `5000`。四条理由：

1. **2500 是 2026-11-02 拍的，那会儿卡片的显示方式不一样。** 当时译文到了才显示卡片，用户盯着空白等，2.5 秒是「不许盯空屏超过 2.5 秒」的容忍线。
2. **2026-11-03 用户把显示时序改成两段**（原文先出 → 「翻译中…」 → 译文到了再补），用户从「盯空白」变成「读原文」，多等两秒不难受。同一个数字，前提换了，含义就换了。
3. **实测账算不过来。** 冷启动第一次必然含取票 424 ms + 翻译 1721~2873 ms = **2145~3297 ms**；旧硬闸扣掉 `CancelOverheadMs`(120) 后只剩 **2380 ms**，落在中位数偏下 → 六到八成超时。这不是程序 bug，是**阈值定在旧前提上**。
4. **5000 的三条依据**：实测最坏 3297 ms 留 1.5 倍余量；必须小于 `PendingCloseDelay` 8000 ms（否则译文还没回来卡片先关），5 秒后仍剩 3 秒能看；用户已有原文可读 +「翻译中…」在转，5 秒是能接受的等待上限。

**代价**：有网但极慢时从「2.4 秒放弃」变成「最长等 5 秒」。断网不受影响（连接失败比硬闸快，S3 实测 P50 2086 ms）。

### 15.2　明确不做的四件事

| 不做 | 原因 |
|---|---|
| token 预取 | 只省 424 ms（2380→2960），还是超 3297；要加启动异步 + 预取失败处理，换不来收益 |
| 动 `PendingCloseDelay`（8 秒） | 8 秒是为「翻译最坏 5000」留的余量，正好够 |
| 动 `CloseDurationSeconds`（3 秒） | 阶段三定的，是另一件事 |
| 动「常态 ≤1500 ms」目标值 | 那是**常态目标**，不是硬闸，两个数不是一回事 |
