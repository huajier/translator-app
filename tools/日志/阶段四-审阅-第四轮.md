# 阶段四 审阅 · 第四轮（T2 复核 + T3 前置裁决）

日期：2026-11-02　审阅对象：`d8d8dee`（阶段四-T2-假译服务器）

## 0. 结论

T2 的**产物质量**没问题（8 种模式我真打了，全对，Content-Length 字节数也对）。
但**假服务器讲的协议不是微软的协议**——它只认 `GET`，而真 Azure 只收 `POST`。
T3 的 Provider 若照着假服务器写，本地全绿、真机全红。**这一条必须修完才能进 T3。**

## 1. 我实测的（不是转述）

启动 `tools\脚本\假译服务器.ps1`，用独立脚本（已删）逐个打：

```
ok          HTTP 200  ContentLength=116  实际字符=106  UTF8字节=116  => OK
ok-空text   HTTP 200  ContentLength=138  实际字符=110  UTF8字节=138  => OK
empty       HTTP 200  ContentLength=96   字符=96                      => OK
badjson     HTTP 200  非 JSON 文本，44 字节                            => OK
401/403/408/429/未知mode  状态码与 error.code 均按预期                => OK
```

**中文回包 → Content-Length 用字节数**这一条经得起检验，`【假译文】Hello` 这类混合串也没问题。这块做对了。

## 2. P0-D1（硬阻断）：协议不对——真 Azure 只收 POST，假服务器只认 GET

**实测**：我按官方文档的调用形态发一次真请求到假服务器：

```
POST /translate?api-version=3.0
Body: [{"Text":"Hello"}]
Headers: Ocp-Apim-Subscription-Key / Ocp-Apim-Subscription-Region
→ HTTP 405  {"error":{"code":"405","message":"only GET"}}
```

**官方文档（本次已抓到，链接见 §6）**：
- 请求：`POST https://api.cognitive.microsofttranslator.com/translate?api-version=3.0&to=zh-Hans`
- 必填 query：`api-version`、**`to`**
- 必有头：`Ocp-Apim-Subscription-Key`（区域资源再加 `Ocp-Apim-Subscription-Region`）、`Content-Type: application/json; charset=UTF-8`
- 请求体：**JSON 数组** `[{"Text":"..."}]`（注意官方示例里既有 `Text` 也有 `text`，解析要不区分大小写）
- 响应：`[{"detectedLanguage":{...},"translations":[{"text":"...","to":"zh-Hans"}]}]`

假服务器现在是 `GET + ?text=查询串`，**没有 body、没有头、不校验 key、不解析 `to`**。
后果：T3 若照假的写，`--回放` 全绿，真联网第一次就 405。

**改法**：假服务器改成认 `POST`：
1. 读请求头，校验 `Ocp-Apim-Subscription-Key` **存在且非空**，缺了就回 `401` + `error.code=401000`（见 P1-D2）。
2. 按 `Content-Length` 读 body，解析 JSON 数组，取第一项 `Text`/`text`（大小写都认）。
3. `mode` 从 query 取（这是测试专用开关，微软没有，保留无妨），`to` 也从 query 取并**回显到响应里**，让程序能验证自己传对了目标语言。
4. 回包结构严格照官方：`detectedLanguage` 只在没传 `from` 时给（我们现在恒不传，所以恒给）。
5. 保留 `GET` 兜底只为人眼看一眼（浏览器直接点），但**`GET` 不算验收通过**。

## 3. P0-D2：假服务器回的错误码是编的，官方表里没有

我抓到了官方错误码表（§6 链接）。现对照：

| 假服务器现在返回 | 官方是否有 | 改成 |
|---|---|---|
| `401001` | ❌ 官方只有 `401000`、`401015` | **`401000`**（凭据缺失或无效） |
| `403001` | ✅ 就是「免费额度用尽」 | 保持 |
| `408`（三位） | ❌ 官方是 `408001`/`408002` | **`408001`**（自定义系统未就绪） |
| `429001` | ✅ 官方有 `429000/429001/429002` | 保持 |
| `400036`（用于未知 mode） | ⚠️ 官方含义是「目标语言缺失或无效」 | 未知 mode 用 **`400075`** 或 `400000` |

**为什么较真**：T3 的 Provider 会按 `error.code` 分派文案（403001 → 额度用尽）。
拿一个不存在的码去调，等于把分派表写在空气上，真机一来就落 default。

## 4. P1-D1：408 在微软这不是「超时」，别把文案写错

官方对 408 的描述是「请求无法完成因为某个资源缺失；带自定义 category 时通常是自定义翻译系统还没就绪，等一两分钟后重试」。
**它不是网络超时。** 我们真正的超时是自己在 `CancellationTokenSource` 上设的 2.5s（方案 §2:49），跟 HTTP 408 无关。

改方案 §4 那张表：408 归到「服务暂时不可用，稍后重试」，重试策略照旧；「翻译超时」只由我方 2.5s 预算触发。
另：`error.code` 的结构是 **3 位 HTTP 状态 + 3 位细分**，分派时按整串匹配，别只取前三位。

## 5. P1-D2 / P1-D3：两处「测试会撒谎」的口子

**P1-D2**：假服务器现在不校验密钥头。T3 万一忘了送 `Ocp-Apim-Subscription-Key`，本地测试照样全绿。
→ 校验头存在且非空，缺了回 `401000`。这是唯一能在本地暴露「忘了带头」的办法。

**P1-D3**：`timeout` 模式睡 20 秒，而服务器是单线程——这一轮测试会**整体卡 20 秒**（汇报里也承认「只能最后测」）。
→ 延迟改成可配：`?mode=timeout&ms=6000`，默认 6000。够超过 2.5s 硬闸，又不至于让 T3 的整套测试停半分钟。

## 6. 正面的：9.12「不传 from」被官方文档确认

官方原文：「If the `from` parameter isn't specified, automatic language detection is applied to determine the source language.」
且「`detectedLanguage` 只在请求自动检测时才出现在响应里」——与我们「恒不传 from、把 detectedLanguage 记进结果不回写缓存键」的设计完全对上。

同一页也确认了免费额度用尽就是 **403 + 403001**（不是别的码），方案 §4 的映射方向正确。

## 7. T2 收口标准（改完自证，不用我再看一遍脚本）

1. `POST` + JSON body + 密钥头 → `200` 且响应含 `detectedLanguage` 与 `translations[0].text`、`translations[0].to`。
2. **不带密钥头** → `401` + `error.code=401000`。
3. 带 `to=zh-Hans` → 响应 `to` 回显 `zh-Hans`；带 `to=de` 回显 `de`。
4. 8 种 mode 的错误码换成 §3 表里的官方值。
5. `?mode=timeout&ms=6000` 能在 6 秒内放开，不再固定 20 秒。
6. 全部结果抄进汇报【数字】，一行一个：请求形态 / 状态码 / `error.code` / 耗时。
