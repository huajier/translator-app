## 1. 裁决：免密钥通道是唯一同时满足两个阶段的方案

用户以为自己要「内置一个密钥」，实际上内置密钥恰好在第二阶段（公开分发）最差：

| 方案 | 自己用 | 公开分发 | 结论 |
|---|---|---|---|
| 内置我的 Azure 密钥 | 能用 | 密钥必然被挖 → 额度烧光 → 微软封号 → **所有人一起失效** | ✗ 两阶段冲突 |
| 每个用户自己填密钥 | 要注册要绑卡 | 要注册要绑卡 → 没人会装 | ✗ 门槛太高 |
| **免密钥通道（Edge）** | 能用，零配置 | **每个用户各自消耗自己的额度，程序里没有可偷的东西** | ✓ 两阶段都成立 |
| 自建后端代理 | 要服务器要钱 | 要服务器要钱 | ✗ 成本不合理 |

**关键认知**：内置密钥的「分发」问题不是靠加密解决的，是靠「根本没有密钥」解决的。
免密钥通道天然适合分发——把密钥这个攻击面直接删掉了。

**所以：不申请 Azure，不内置任何密钥。** 用户省掉了绑信用卡那一步。

## 2. 必须保留的一层：Provider 接口不能省

免密钥通道是**微软给自家浏览器用的，没有写进公开文档**。它随时可能改或关。

所以 `ITranslationProvider` 接口必须留：
- 今天只有一个实现 `EdgeFreeProvider`
- 哪天它关了，加一个 `AzureTranslatorProvider` 类，上层一行不动
- **但今天不写 Azure 那个类**——没人有密钥，写了也没法验，是纯负债（YAGNI）

### T3-spike（先做，30 分钟，不碰 `src\`）

新建 `tools\脚本\探针-免密钥通道.ps1`（**必须带 BOM**，否则 PS 5.1 中文全坏——T1a 已踩过），要回答六个问题：

1. `GET https://edge.microsoft.com/translate/auth` 返回什么？（是纯文本 JWT 还是 JSON？状态码？长度？）
2. 那个 token 的 payload 里有没有 `exp`？有效期多久？
3. 拿着 token `POST https://api-edge.cognitive.microsofttranslator.com/translate?api-version=3.0&to=zh-Hans`
   + `Authorization: Bearer <token>` + `Content-Type: application/json; charset=UTF-8` + body `[{"Text":"Hello"}]`
   → 通不通？返回结构是不是和 Azure 一致（`[{detectedLanguage, translations:[{text,to}]}]`）？
4. 不传 `from` 有没有 `detectedLanguage`？
5. 连续打 10 次，有没有限流（429）？单次耗时多少？
6. 401 长什么样？（token 过期时的表现，决定刷新策略）

**验收**：六问全部有实测数字，随便一条不通就停，回头找架构师。

### T3a（spike 通过才做）

只有 `EdgeFreeProvider` + `TranslationService` + `TranslationCache` + `TranslationResult` + `TranslationFailure`。
HTTP 用 `HttpClient` + `SocketsHttpHandler`（第五轮 §2：禁 `HttpWebRequest`，Expect 100-continue 每次白等几百毫秒）。
endpoint 是回环时 `Proxy = null`（第三轮 P1-C1）。

**token 缓存**：token 存内存，按 `exp` 提前 60 秒刷新；收到 401 强制刷新重试一次，第二次还 401 就报 `AuthFailed`。
token **绝不落盘**——它本来就能随时重新换，存下来只是多一个泄露面。

**设置项简化**：因为不要密钥了，settings.json 从 5 键降到 2 键
（`translateTargetLang`、`translateEndpoint`）。`translateApiKey` / `translateRegion` 不加。
`translateEndpoint` 仍保留，指假服务器做自动化验收。

### T3b（照旧）

主窗口设置区：开关 + 目标语言下拉。**不再需要密钥输入框和区域输入框**，比原计划少一半活。

### T3c（可选，仅在 T3-spike 第 3 问失败时）

免密钥通道走不通 → 回退 Azure 方案 → 那时才需要用户去申请密钥，才需要 DPAPI 加密（第六轮 §1 已备好方案）。

## 4. 第二阶段的三个真风险（现在说，不等到上线）

用户说「最后要放网上给别人下载」，这条路有三个坑，都不是技术能解决的：

1. **非官方接口，公开使用违反微软服务条款**。自己用没人管，做成公开软件可能收到下架通知。
2. **量大了会被封 IP 段**。免密钥通道按来源 IP 限流，用户多了会成片失效。
3. **没有 SLA，随时可能变**。凌晨改协议，用户第二天全不能翻。

**这三条的意思是**：第二阶段真正可行的形态大概率是「**软件免费 + 用户自己填密钥**」，
或者「接受随时可能失效的免密钥通道，并明确告知用户」。
现在不用决定，但 T3 的接口设计要为这个留门——这也是 §2 说 Provider 接口不能省的原因。
