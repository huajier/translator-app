## 一、这个版本做了什么（大白话）

以前框一块屏幕，程序只知道位置。现在程序会把那块内容**读成文字**显示出来。

现在的分工是：**按语言走不同的认字引擎**——

- **中文**走 Windows 自带的认字（快，实测够用）；
- **英文和俄文**走 Tesseract（慢一点，但准得多）。

> 为什么这么分？因为 2026-10-09 用户说明真实用途是**主要翻英文和俄文**，
> 复测发现英文两者差 36 分。详见第十三节。

## 二、怎么用（一步一步）

1. 双击 `release\v0.3\TranslatorApp.exe`（**整个文件夹都要留着，不能只拷 exe**）。
2. 程序启动后缩到右下角托盘，屏幕中间出现一块半透明的取词框。
3. 屏幕上会浮出一条提示，写着「按住 Ctrl+Alt 再按住鼠标左键拖动即可框选」。
4. **按住 `Ctrl` 和 `Alt`**（左手两个键一起按住别松），
   鼠标移到想取字的区域，**按住鼠标左键拖出一个矩形**。
5. 松开左键 → 屏幕上弹出一张小卡片，上面显示认出来的文字。
6. 看完按 `Esc` 关掉卡片。

## 三、六种框选情况分别会怎样

| 你怎么操作 | 会发生什么 |
|---|---|
| 正常拖出一个框 | ✅ 弹出卡片，显示识别出的文字 |
| 框到一半按 `Esc` | ✅ 「框选取消：按下 Esc」，什么都不会发生 |
| 框到一半松开 `Ctrl` 或 `Alt` | ✅ 「框选取消：中途松开了 Ctrl 或 Alt」 |
| 只点一下（不拖） | ✅ 无动作（框太小不算数） |
| **不按** `Ctrl+Alt` 直接拖鼠标 | ✅ 无动作（所以你正常拖拽、复制、点链接都不会被干扰） |
| 框到一半按鼠标右键 | ✅ 「框选取消：按下右键取消框选」 |

这六项每轮都会重新验一遍。

## 四、认字是怎么做的

框里的画面截下来之后：

1. 先让 **Windows 自带引擎**认一遍（只转灰度，最快，10~30 毫秒）；
2. 顺便判断**这是什么语种**（汉字 / 西里尔字母 / 拉丁字母）；
3. 如果**不是中文**，再补跑一次 **Tesseract**（约 200 毫秒），用它的结果。

**所以中文那一条路完全不受影响，不会变慢。**

## 七、为什么产物变成一个文件夹了

原来是一个 exe 走天下。引入 Tesseract 之后做不到——
它的 .NET 封装靠「程序集所在目录」拼原生 DLL 的路径，
单文件打包下这个路径是空的，直接崩。

我试过用绝对路径预加载原生库绕过，**没用**（压根没走到加载那一步就崩了）。
所以构建脚本改成 `PublishSingleFile=false`。
**把整个 `v0.3` 文件夹拷走就能用，只拷 exe 不行。**

## 十一、验收怎么做

**结论：让用户自己框，AI 只读记录比对。**

用户 2026-10-09 提出的原话：

> 「你这样自己测太慢了，而且还容易出错……你把需要测的步骤给我列出来，
> 然后我来操作，提取出文字了软件里应该有记录的，你读取记录比对文本，
> 这样就能分析出来了。」

**这条意见是对的。** 我用脚本模拟鼠标点击有两个根本缺陷：

1. 只能测我「想」让用户做的事，测不出真实操作里的意外；
2. **模拟坐标经常偏**，框到的是别的地方。

本轮至少三次「结果不对」其实都是我框错了区域，不是软件有问题。
而且**用户在实测中抓出了一个我自己测不出来的 bug**（见第二十二节）。

配套三件工具：

| 文件 | 作用 |
|---|---|
| `tools\素材\验收材料.html` | 11 段**已知原文**的文字，按 A1~D1 编号 |
| `release\v0.3\logs\取词记录-*.txt` | 软件自动存下每次取词结果 |
| `tools\脚本\比对取词记录.ps1` | 一键算每段准确率、指出第一个不一样的字 |

**算分口径（固定，不再改）**：

1. **空格保留参与比对**——用户在意的「乱加空格」必须如实扣分。
   若先删空格再比，`quick b rown fox` 会和 `quick brown fox` 同分，
   **最烦的问题就被自己掩盖掉了**。
2. 大小写不敏感。
3. 换行、连续空格、首尾空白不算错。
4. 编辑距离算相似度。

---### 关于「加 Tesseract」这件事的经过（2026-10-08）

用户拍板「不用测了，直接加 Tesseract」。我装了、也实测了。
**但那一次实验本身有致命缺陷，结论不能采信**——原因见第十二节。
先保留当时得到的两个事实：

1. **Tesseract 的 .NET 封装在单文件打包下直接崩。**
   报错 `ArgumentNullException: path1`，发生在**拼路径**那一步：
   它靠「程序集的 `Location`」找原生 DLL，而单文件打包下 `Location` 是**空字符串**。
   我试过用绝对路径**预加载原生库**绕过——**没用**，它压根没走到 `LoadLibrary` 就崩了。
   构建脚本已改为 `PublishSingleFile=false`；产物从「一个 exe」变成「一个文件夹」。
2. 用户随后拍板：**Tesseract 留着，但默认关掉**。
   开关在 `%APPDATA%\TranslatorApp\settings.json` 里写 `{ "useTesseract": true }`。

## 十二、「正确率低的可怜」——用数字回答「是不是到极限了」（2026-10-09）

用户问：**「你这个已经是引擎极限了吗，实在不行换引擎」**。

这个问题**不能靠看图回答**——看图只能看出「好/不好」，看不出「还能提升多少」。
所以搭了个实验台（`src\Core\Capture\EngineBenchmark.cs`，命令行 `--引擎对比`）。

### 实验怎么做的

1. 用程序**自己画出 6 类场景的图**，原文是**已知的**（标准答案）；
2. 字号取 **14 / 18 / 28 像素**三档；
3. 4 个引擎（Windows 自带 + Tesseract 三档模型）× 5 种预处理逐个去认；
4. 认出来的字和标准答案**逐字比对**，算 0~100 的准确率。

> ### ⚠️ 第一版实验栽了个坑，必须记下来
>
> 第一次画图时字号用了 **48 像素**，测出来「Windows 自带全面碾压」。
> **但 48 像素的字大得离谱，OCR 认起来太轻松**，
> 而用户实际框选的是**屏幕正文，只有 12~18 像素**。
> 小字才是 OCR 真正的战场，也是「放大 2 倍」这个功能存在的意义。
>
> **换成真实字号之后，结论直接翻转。**
>
> **教训：测不准的时候，先怀疑测量仪。**

### 准确率总表（越高越好）

| 字号 | Windows<br>原样 | Windows<br>放大2倍 | **Windows<br>2倍+二值化** | Tess-best<br>放大2倍 | Tess-标准<br>放大2倍 |
|---|---|---|---|---|---|
| **14px（屏幕正文）** | 54.0 | 64.7 | **65.0** ·10ms | **72.3** ·229ms | 72.3 ·356ms |
| 18px | 57.3 | 75.2 | **83.3** ·15ms | 73.3 ·218ms | 73.0 ·354ms |
| 28px | 79.2 | 80.8 | **83.3** ·20ms | 68.3 ·237ms | 72.2 ·372ms |
| **全字号平均** | 63.5 | 73.6 | **77.2** ·15ms | 71.3 ·228ms | 72.5 ·361ms |

### 两个结论

**1. 真正的元凶是预处理，不是引擎。**

加一道 **Otsu 自动阈值二值化**（把图压成纯黑白），
Windows 自带整体从 73.6 → **77.2**，而且**更快**（15ms）。

生僻字那一项最能说明问题：**14px 下别的配置全是 0 分**，
只有「2倍+二值化」拿到 **38 分**。

原理：所有 OCR 引擎内部都默认「黑字白底、对反差敏感」，
屏幕上的橙底绿字、深底浅字让它很难受；
直接压成黑白，等于**替引擎把前景背景的界线划好**，它就只剩认字这一件事了。

**2. Tesseract 只在小字时领先，领先幅度不足以换引擎。**

14px 下 Tess-best 72.3 vs Windows 65.0（领先 7.3 分），但**慢 23 倍**（229ms vs 10ms）；
18px、28px 反而全面落后；整体平均也落后。而符号、生僻字它同样不行。

## 十三、顺带查出一个真 bug：「两遍择优」的判据本身是错的

原判据是「第二遍字多就用第二遍」，后来改成「谁分高谁上」，**两次都不对**：

- **认错得离谱的结果往往字更多。**
  `2 ik ES 28 BS HER` 有 13 个有效字符，比正确的 `鑫淼懿囍` 还「多」，
  于是错的赢了对的——这是用户说「错字多」的由来之一。
- **改成评分择优后，小字时两遍字数一样多、空格分布也一样，分数打平**，
  而「打平就保留第一遍」恰好保留了更差的那版（14px：原样 54.0 分 vs 二值化版 64.7 分）。

> **根子在于：没有标准答案时，长度和排版反映不出「不错」被认成「错」这种替换错误。**

**最终判据：默认信第二遍（放大2倍+二值化），只有它明显坏了才退回第一遍。**
三道闸任一触发才退回：

1. 第二遍读不出有效文字（空、纯符号、乱码）；
2. 第二遍字数少于第一遍的一半（多半是图处理过头了）；
3. 第二遍的「像不像人话」分数被第一遍甩开 30 分以上。

**理由是有数据撑的**：二值化版在三个字号上**全部**赢原样。
既然如此就不该再去猜哪遍更好——**猜错反而更糟**（上面第 2 条就是活生生的例子）。

## 十七、🔴 方向性修正：用户说明真实用途是**英文和俄文**（2026-10-09）

用户原话：

> 「翻译软件主要是翻译英文与俄文，中文提取差可以接受，
> 但是英文也会出错这是不能接受的，长英文的识别率差的可怜，
> 经常性识别成乱码，稍微带一点符号就乱成一团，还有就是乱加空格，
> 这样识字都不通关就别想着翻译了。」

**这一句话推翻了前面所有工作的前提。**
前面（含 Tesseract 对比、二值化、质量评分择优）全部围绕**中文**展开，
而中文恰好是用户**明确说「可以接受」**的那一项。

### 三个症状的实测复现

同一次真实框选的日志（改动前）：

```
Use ChatGPT | ChatG PT Learn / CnatGPT is a n AI agent tn 钔 you
communicate witn in natural language Start witn a question,
a n idea, rougn n01 巳 s a 0 r a task
```

- `ChatG PT` —— 词被劈开（对应「乱加空格」）
- `CnatGPT`、`witn`、`rougn n01 巳 s a 0 r a task` —— 乱码（对应「长英文识别成乱码」）
- `钔`、`巳` —— **中文引擎把英文认成了汉字**
- `me@example.com` / `50% off` 这类符号一出现就崩（对应「带一点符号就乱成一团」）

### 两个根本原因

**原因一：一律用中文引擎认所有文字。**

`OcrEngineFactory.TryGetEngine` 里写着：

> 「中文引擎对英文照样能认，反之不成立，所以中文永远排前面。」

于是框英文时用的也是 `zh-Hans-CN` 引擎。
**这句话当时没有实测支撑**，而 Windows 的识别引擎本来就是按语言分别训练的。

**原因二：俄文本机根本没装识别包。**

实测 `OcrEngine.AvailableRecognizerLanguages` 只有 `en-US` 和 `zh-Hans-CN`，
`TryCreateFromLanguage(new Language("ru-RU"))` **返回 null**。
**也就是说俄文在 Windows 自带引擎上根本走不通**，以前一直没发现。

### 英文/俄文对照实验（已知原文，逐字打分；空格如实计入，不放过「乱加空格」）

| 引擎 | 英文平均分 | 俄文 | 耗时 |
|---|---|---|---|
| **Tess-fast（原样）** | **94.7** | **100** ✅ | 212ms |
| Win-英文引擎 | 63.3 | 装不上 ❌ | 20ms |
| Win-中文引擎（曾上线） | 58.9 | 装不上 ❌ | 17ms |
| **改动前的整条流水线** | **58.2** | 装不上 ❌ | 26ms |

**英文差 36 分。** 这不是「还能优化」的区别，是「能不能用」的区别。

### 最终分工

**中文走 Windows 自带，英文和俄文走 Tesseract。**

依据：中文那条路上 Tesseract 实测更差、而且 Windows 自带更快；
英俄这条路上 Tesseract 高出 36 分且俄文只有它能认。

实现方式：**先让 Windows 快速认一遍（10~30ms）判断语种，不是中文才补跑 Tesseract**。
所以**中文那一路完全不受影响，不会变慢**。

### 真实屏幕验证（三语同页，逐个框选）

## 十九、语种判定补上俄文（2026-10-09）

### 为什么必须补

`LanguageDetector` 原来只有「中文 / 外文」两类，**俄文一律被判成「外文」**。
表面上只是显示难看，真正的问题是：**「外文」在代码里就等于「英文」**，
`TargetOf()` 是「源语言是中文就译成外文，否则译成中文」——
所以俄文会被送去**英→中**翻译，也就是**把俄语当英语翻**。
结果会错得离谱，而且错得很隐蔽（输出是通顺的英文，只是意思完全不对）。

### 改法

改成按**文字体系**分三类，判定顺序是**中文 → 俄文 → 拉丁**：

| 输入 | 改之前 | 改之后 | 翻译目标 |
|---|---|---|---|
| `今天天气不错` | zh | zh | en |
| `The quick brown fox` | en | en | zh |
| `Ошибка 404 (страница не найдена): файл config.txt не найден` | **en（错）** | **ru** | **zh ✅** |
| `Файл занимает 2,5 МБ` | **en（错）** | **ru** | **zh ✅** |
| `API 接口 v2.0 已发布` | zh | zh | en |
| `404 --- *** ???` | unknown | unknown | — |

### 两个阈值不一样，这是有意的

- 中文 **30%**（规格第 8 条定死，不许改）
- 俄文 **15%**

**为什么俄文要低一些**：俄文技术文档里常夹英文词和文件名，例如
`Ошибка 404 (страница не найдена): файл config.txt не найден`
里 `config.txt` 就是一大段拉丁字母。阈值跟中文一样定 30%，这种最常见的俄文内容会被误判。
宁可灵敏一点，也不能踩中「俄文被当英文」那个坑。

### 显示名为什么写「外文（拉丁字母）」而不是「英文」

我们能可靠分辨的是**汉字 / 西里尔字母 / 拉丁字母**三套字母，
**但光看字母认不出语言**——法语、德语、西班牙语用的都是拉丁字母。
直接写「英文」会把它们骗成英文。在本软件的目标语种（中文/英文/俄文）范围内，
拉丁字母就等于英文，判断不会出错；但显示上留个余地更诚实。

### 单元级验证（10 组真实字符串，全部正确）

```
纯中文        → zh        翻译目标=en   中文（中文 100 %，西里尔 0 %）
纯英文        → en        翻译目标=zh   外文（拉丁字母）（中文 0 %，西里尔 0 %）
纯俄文        → ru        翻译目标=zh   俄文（中文 0 %，西里尔 100 %）
俄文夹文件名  → ru        翻译目标=zh   俄文（中文 0 %，西里尔 80 %）
俄文夹数字    → ru        翻译目标=zh   俄文（中文 0 %，西里尔 100 %）
俄文长段      → ru        翻译目标=zh   俄文（中文 0 %，西里尔 100 %）
中英混排      → zh        翻译目标=en   中文（中文 60 %，西里尔 0 %）
中英各半      → zh        翻译目标=en   中文（中文 36 %，西里尔 0 %）
纯符号        → unknown   翻译目标=zh   未识别（没有文字）
空串          → unknown   翻译目标=zh   未识别（没有文字）
```

真实屏幕验证：`取词成功：通道=Tesseract 字数=592 语言=俄文（中文 3 %，西里尔 43 %）`

## 二十、验收方式改了：由**用户操作、AI 读记录**（2026-10-09）

### 用户提出的问题

> 「你这样自己测太慢了，而且还容易出错，你这样，你把需要测的步骤给我列出来，
> 然后我来操作，提取出文字了软件里应该有记录的，你读取记录比对文本，
> 这样就能分析出来了。」

**这条意见指出了一个我一直没意识到的问题。**
我一直在用 `模拟操作.ps1` 脚本模拟鼠标点击，它有两个根本缺陷：

1. **只能测我「想」让用户做的事**，测不出用户真实操作里的意外情况；
2. **模拟坐标经常偏**，框到的是别的地方——
   本轮至少三次「测出来的结果不对」其实是我框错了地方，不是软件有问题。

于是大量时间花在「这是不是同一块区域」上，而不是「软件对不对」。

### 新分工

**用户负责「框到哪」，AI 负责「结果对不对」。**

配套做了三件事：

1. **新增 `CaptureRecord`**：每次取词把结果**一字不截**地存到
   `release\v0.3\logs\取词记录-yyyyMMdd.txt`。
   为什么必须另存而不能只靠普通日志：普通日志的「最终原文」**截断到 300 字**，
   格式又是给人看的，没法逐字比对。
2. **新增验收材料** `tools\素材\验收材料.html`：11 段已知原文的文字（英文 5 / 俄文 3 / 中文 2 / 中英混排 1），
   覆盖短句、长段、带符号、技术串、小字。
   **每段的正确内容都是已知的**，这样才能客观打分。
3. **新增比对脚本** `tools\脚本\比对取词记录.ps1`：
   一键读记录、比对标准答案、算每段准确率、指出第一个不一样的字。

### 算分口径（固定下来，不再改）

这一条必须写死：**不同轮次必须用同一套算法**，
否则分数没法横向比较。之前就吃过亏——一次按「删掉所有空格再比」、
一次保留空格，两次的分自然对不上，只能回头重测。

1. **空格保留参与比对。** 用户在意的「乱加空格」必须如实扣分；
   若先删空格，`quick b rown fox` 会和 `quick brown fox` 同分，
   **最烦的问题就被自己掩盖掉了**。
2. 大小写不敏感（OCR 常把 I/l、O/0 认错，不该再罚一次大小写）。
3. 换行、连续空格、首尾空白不算错。
4. 用编辑距离算相似度，错一个字扣一点，比「全对才算对」有区分度。

脚本自检：`The quick brown fox jumps over the lazy dog` = **100%**；
把其中一个词拆成 `laZy d og` = **10%**（空格乱加如实扣分，口径正确）。

## 二十二、实测又抓出一个真 bug：「字数多者胜」对外文是错的

### 现象

A4（英文技术串）是唯一掉到 78 分的一段，日志写得很清楚：

```
通道: WindowsOcr
说明: 不是中文，但 Tesseract 认得更少（60 < 62），保留 Windows 自带
原文: HTTP/2.0 2024 一 05 一 01 API v 土 1 - 85 ％ CPU, RAM 16G 巳 ID # A17f 一 9 e-mail: dev@corp.io; see p · 42 ．
```

`-`→`一`、`3`→`土`、`B`→`巳`、`.`→`·`——
**中文引擎把符号认成了汉字**，这就是用户当初说的「稍微带一点符号就乱成一团」。

### 根因

我原来加的保护是「Tesseract 认得更少就保留 Windows 自带」。
**问题在于「有效字数」这个指标对外文根本不成立**：
中文引擎凭空造出来的汉字，在计数时和真汉字**一视同仁**，
于是字数虚高 62 > 60，把更好的结果挤掉了。

### 查证（用同一段文字做对照实验）

```
原文：HTTP/2.0 2024-05-01 API v3.1 - 85% CPU, RAM 16GB, ID #A17f-9x, e-mail: dev@corp.io; see p.42.

Tess-fast/放大2倍    100 分  ← 逐字正确
Tess-fast/原样        99 分
Windows 自带          78 分
```

**满分的结果被扔了，78 分的结果被留下。**

### 改法

**不是中文 → 一律用 Tesseract，除非它几乎什么都没认出来（有效字符 < 2）。**

理由不是拍脑袋：
- 整体数据：英文平均 94.7 vs 58.9，差 36 分；
- 这一段的直接对照：100 vs 78；
- 「谁字多谁上」在外文上**没有依据**，在中文上还有救，在外文上是有害的。

同时整体数据也印证了这条规则的正确性：D1（中英混排）走 Windows 自带拿到 93%，
它中文占 50%，`IsMostlyChinese` 判定为中文，不进 Tesseract 分支——
这条路径没受影响。

> **这次能抓到这个 bug，靠的是用户亲手框出的真实内容。**
> 我自己用脚本模拟点击时，从来没在正确的区域上框到过这段——
> 之前三次「结果不对」其实都是我框错了地方。**让用户操作是对的。**

## 二十六、🔴 用户第 3 轮反馈：**我的分数不可信，已停止用合成台下结论**

### 用户的原话

> 「你放屁呢，这正确率还是很低啊，你说 a4 百分百正确率，我这边实测它甚至没有识别全句子，
> 少了 p.42. 这一小段，其他的就不提了，尤其是俄文，
> 识别出来纯俄文字变成英文俄文混用了，这正确率太低了，根本达不到可以使用的地方，
> 更不用说实战测试还需要识别复杂背景上的文字。」

### 我查出来的原因：测量仪坏了，不是被测物坏了

拿同一句俄文、同一套模型、同一档设置，对比两种输入：

| 输入来源 | 结果 |
|---|---|
| **本程序自己画的测试图** | **100 分**，`Съешь` 完全正确 |
| **用户真实屏幕上的内容** | 89 分，`Съешь` → `Cbeuub` |

**同一个引擎差 11 分。**
原因是 GDI+ 画的字和浏览器 ClearType 渲染的字在抗锯齿、灰度过渡、字距上完全不同——
**我画的图比真实屏幕干净太多，所以分数虚高。**

> 这已经是本阶段第三次「测不准先怀疑测量仪」，
> 但前两次是**用错工具**，这次是**工具本身有系统性偏差**，性质更严重。
> 之前拿「英文平均 94.7 分」「俄文 100 分」汇报给用户，是**不负责任的**。

### 我的分数还掩盖了「能不能用」

`Съешь` → `Cbeuub` 只错一个词，编辑距离算下来是 89 分，看起来「还行」。
**但对翻译来说，一个俄文句子中间夹了个英文单词，结果就是彻底错的。**
我的算法**按「错了几个字」打分，而用户按「能不能看懂、能不能翻」判断**——
两者不是一回事。以后分数只能当参考，**能不能用由用户说了算**。

### 已做的修改：按语种只挂一种语言模型

用户反馈的「英文俄文混用」，根因很明确：

**西里尔字母表里的 С С Р Р О О М М Н Н Т Т Х Х У К В 和拉丁字母完全同形，
图像上没有任何特征能把它们区分开。**
引擎唯一能依据的只有「我现在在读哪种语言」。

原来三种语言一起挂（`chi_sim+eng+rus`），模型要在三套字表之间反复权衡，
遇到同形字就滑向体量更大的拉丁那套 → `Съешь` 变成 `Cbeuub`。

**改法**：调用之前语种已经判出来了，直接按语种取模型——
- 俄文 → **只挂 `rus`**
- 英文 → **只挂 `eng`**

只挂一种之后，模型**别无选择**，只能按西里尔字表走。

> ⚠️ **这一条目前只有理论依据，没有真实数据验证。**
> 我的测量工具已经不可信，**不能拿它来证明这个改动有效**。

### 二十八·2 🔴 未修问题一：R9 末尾漏识别

**现象**：原文 `Версия 1.2.3, ошибка 500, попробуйте позже`，
认成 `Версия 1.2.3, ошибка 500, попробуйте`，**末尾的 `позже` 整个丢了**。

**用户明确说过**：取词框选是框全的，少了就是没识别出来。
**已核对排除的因素**：
- 验收材料 HTML 里 `позже` 确实存在（`验收材料2-实战版.html:141`）
- CSS 里没有 `max-width`／`overflow:hidden`／`white-space`，文字在浏览器里完整显示
- 所以**不是框选问题，也不是验收材料问题，是识别问题**。

**诊断日志给出的事实**（四路二值化各自认出了什么）：
```
红通道 0.93 → Версия 1.2.3, ошибка 500, попробуйте   ← 少了 позже
绿通道 0.00 → 空
蓝通道 0.00 → 空
灰度   0.00 → 空
```
四路**全都**丢了它。

**同时**：历史上有一轮，**未经二值化的原图是认得出 `позже` 的**
（当时数字是乱的：`Версия 117.8, ошибка 500, попробуй ие позже`）。

**结论**：问题出在「放大 + 二值化」这一步，不是选路选错了。
**已试过且失败的三个办法**（每一个都把别的地方弄坏了，全部已回退）：
1. 换「找行方式」（SingleBlock／SingleLine）→ 无效，且另两路返回 0 字
2. 放宽各种门槛让兜底多跑几次 → E5 英文被换成 `ВАМ`、`p42`→`р.42`
3. 四边补白边（第一次按长边一成 → 图被撑变形，E2 只认出中间一段；
   第二次按高度的一小圈 → 无效，`позже` 仍然没回来）

理由：红通道上橙底 255、绿字 0，**即使不二值化对比也已经拉满**，

### 二十八·4 这一段反复出现的教训（写下来防止重犯）

1. **不要一轮里改好几处**。连着几轮都是「一处有问题、整轮报废」，
   一次只改一处，才能知道到底是谁的问题。
2. **候选越多，越容易混进「错但分高」的赢家**。
   实测出现过 `0.89 打败 0.87` 就把已经认对的换错了。
3. **置信度高 ≠ 内容对**。Z1 曾只认出 `SVMs`（4 个字）却有 0.76 的置信度。
4. **置信度管不了「有没有漏字」**。R9 少了半句，剩下部分照样有 0.93。
5. **兜底代码的门槛不能设太严**，否则它永远在最该来的时候不来。
6. **自己造测试图会骗人**。四周留了空，正好绕开了「文字贴边」这类问题；
   只有拿真实框选去试才会碰到。
7. **自造的判断指标要先验证再用来做决定**。
   原来的「Otsu 可分性」算出 3e11 这种数，还在橙底绿字时选中了最差的一路，已删除。

### 三十·2 根因：一条我自己加的配置，把词典功能废掉了

**我加的四条配置项里，有一条是自作主张：**

```csharp
SetVar(engine, "language_model_penalty_non_dict_word", "0.01", language);       ← 有害
SetVar(engine, "language_model_penalty_non_freq_dict_word", "0.01", language); ← 有害
```

**官方 ControlParams 页面只是「列出」这两个参数和默认值（0.15 / 0.1），
从头到尾没有建议改小。**

我当时的理由：`config.txt`、`HTTP/2.0`、`me@example.com` 不在词典里，
会被「纠正」成词典里的词，于是把惩罚压到 0.01 让它照原样输出。

**结果等于告诉 Tesseract「你输出什么词都不罚」——词典是它准确率的主要来源。**

**用户实测：中/英/俄三语一起崩**
```

rus+eng  0.32 → ETT REIN Ee WE RY от = о) feel 11] о) 0) С: ...
```

### 三十·3 另外两个「该做而没做」的漏洞

**① 最后一步完全没有质量门槛**
v0.3 每一步都在比分数、设门槛；v0.3.1 只检查「有没有 2 个有效字符」，
于是 **0.13 分的乱码被当成正式结果**显示给用户。

**② 第 1 级（中文）只查「像不像中文」，不查分数**
英文段落被中文模型读出来的东西，**往往正好是一堆形似汉字的乱码**，
中文占比 100%，判断器当场判成「是中文」，**第 2、3 级根本没跑**：
```
Tesseract 认完（chi_sim·6 文本块）：置信度 0.13
第 1 级（中文模型）就认出来了，置信度 0.13      ← 0.13 也收
最终原文：天沿轩这 :全人由国人 : 生 > 二河天 7
```

### 三十·4 本轮修的三处

| # | 改动 |
|---|---|
| 1 | **词典惩罚恢复官方默认**（0.15 / 0.1），并在代码里显式写出并注释「别再动」 |
| 2 | **加质量门槛 `MinimumAcceptableConfidence = 0.60`**：低于它就判乱码，不给用户看 |
| 3 | **第 1 级（中文）改成「分数和中文占比必须同时成立」**，缺一就往下一级走 |

**另外补一条退路**：三级阶梯都不理想时，
再用 **PSM「自动」（即 v0.3 用的那个）** 补一次，取分数更高的。
理由：PSM 6 是按「多行文字块」设计的，而取词框**绝大多数就是一行**，
版面假设不对会断崖式掉分（这正是当初判断失误的地方）。

### 三十·5 最重要的一条教训

> **为解决一个特例去动全局机制，是最贵的改法。**
>
> `config.txt` 那**一个**问题，代价是**全部语种的准确率**。
> 特例要修就单独修（比如识别后按模式修那一个词），
> **绝不要去动引擎的底层机制。**

**改法**（完全按用户要求「识别出结果后 3 秒后关掉」）：
| 阶段 | 倒计时 |
|---|---|
| 框选完成、**识别中** | **8 秒兜底**（卡片写「正在识别，请稍候…」，防引擎卡死后框关不掉） |
| **识别结果出来** | **从这一刻重新计 3 秒** |

⚠️ 实现要点：两个阶段共用同一个 `DispatcherTimer`，
`ShowFor` 把它设成 8 秒，**`UpdateWith` 必须显式改回 3 秒**（已写进代码注释）。

## 三十三、松键 bug 修复 + **判定标准由用户重新定义**（2026-10-09，待复测）

### 三十三·1 用户反馈

> 「我框选后松开 ctrl 或者 alt 键按道理来说应该不识别的，
>   但是松开左键后却识别出来了，这是个 bug，
>   还有我觉得你的分数判断有问题，在我的视角来看，
>   一个词的一个字母错了，那这一整个词就全错了，
>   这一个词错了，拿着一整句话就全错了，这个判定标准你参考下」

### 三十三·2 第一件事：松键 bug —— **上一轮我改过头了**

上一轮把「中途松开 Ctrl/Alt 就取消」整条删掉了，
结果**把「松键就该作废」这条规矩也一起丢了**。

**日志证据**：这轮取词记录里混进了 4 条废框：
```
KESL                    ← 该作废的框，照跑了
workbuddy cpenccée      ← 同上
（外加 2 条重复的正常段）
```

**正确的规矩是「判断的时机错了，判断本身没错」**：

| 阶段 | 行为 |
|---|---|
| 拖框过程中松 Ctrl/Alt | **不打断**（免得手指一抖就废掉一次拖框） |
| **松开左键那一刻** | 看组合键还在不在：**在 → 识别；不在 → 取消** |

四条取消途径一条不少：右键、Esc、框太小、**现在新增的「松键时组合键不在」**。

### 三十三·3 第二件事：**判定标准改成用户定的口径**

用户原话：
> 「一个词的一个字母错了，那这一整个词就全错了，
>   这一个词错了，拿着一整句话就全错了」

**规则**：
① 按空格切成一个个词
② 一个词里**只要有一个字符不同，这个词整词判错**（不给字符级部分分）
③ 一段里**只要有一个词判错，整段就判错**（不给句子级部分分）

**旧脚本用的是「编辑距离」，是错的**：
`see a` 按编辑距离能拿 **85 分**，看起来「基本对了」——
但用户要的是**翻译就全错了**。

### 三十三·4 顺带修了脚本自己的两个毛病

**① 按顺序硬配 → 改成按相似度配对，自动剔除废框**
   记录是用户一次一次框出来的，**多一次废框后面全部串位**，
   报告会变成「E2 应该是 the 实际是 machine」这种**纯属配错**的红，
   **比识别烂还误导人**。

**② 词与词之间改成按最长公共子序列对齐**
   E5 实际多了一个行首 `:`，按位置硬比会让**后面 11 个词全被判错**——
   看着像识别烂透了，其实只有冒号多余。对齐后**只错 2 个**。

⚠️ 对齐的回溯逻辑**第一次写反了**（`elseif ($skipW -ge $skipG)`），
把「多出来的 `:`」判成了「缺 http/2.0」，E5 错词数从 2 涨到 24，**比不改还糟**。
已改成「谁的剩余 LCS 更长就跳过谁」。

### 三十三·5 重新算分：**13/20 逐字全对**（比我上次报的 16 低）

**一句话：模型是在「原图」上比的，图却是「换了四路之后」才对的，两件事被混成一件了。**

### 三十九·4 🔴 用户报的 bug：遮罩晚铺 3 像素

> 「当你摁住 ctrl+alt+左键框选识别后不松开 ctrl 和 alt 再次摁左键再次框选，

**用户的判断完全正确。** 本程序有一条铁律：
`LowLevelMouseHook` **永远放行，一个鼠标事件都不吃**。
所以「不让下面的软件选中文字」**全靠遮罩窗口挡着**。

```

```

**「不松开 Ctrl+Alt 直接框第二次」时手停在原地不动，空档必然被撞上。**

→ 新增 `Armed` 事件：**左键一按下去、确认组合键按着，就立刻把遮罩铺上**（先不画选框）。

**三条错，全部出在同一个毛病：「择优的时候只比一个量」。**
- 四路只比分数 → 空格多被当成内容多
- 中文兜底只比分数 → 不是中文的结果被当成好结果
- 三十七轮那两条（打平也换）也是同一个毛病

**以后凡是「从几个候选里挑一个」，一律用帕累托规则，而且要比的内容必须先清洗过。**

### 四十·2 🔴 遮罩 bug：**我第一次诊断错了，第二次才对**

**用户的第二次反馈是关键**：
> 「bug 还在，**遮罩是出现了，但是鼠标也已经开始选中了**」

**这说明压根不是遮罩的问题——遮罩确实铺出来了，我上一轮那个 `Armed` 事件也确实生效了，
但鼠标还是被选中了。** 我第一轮的判断（「遮罩晚铺 3 像素」）是错的。

**真正的时序**：
```
用户按下左键
    ↓
钩子回调收到事件
    ↓
CallNextHookEx 放行  ←── 底下的软件**这一瞬间**就开始选中文字了
    ↓
通知主线程 → 主线程通知遮罩铺开   ← 遮罩铺好时，文字已经选中了
```
**遮罩是「事后响应」，追不上「已经发出去的事件」。**

**唯一的可靠办法：这一次左键按下根本不要交给底下的软件。**
钩子回调返回非零 = 吃掉，底下软件压根不知道发生过这件事。

### 四十·3 「一个鼠标事件都不许吃」这条铁律怎么办

**不是取消，是加一个例外**：

| 情况 | 怎么办 |
|---|---|
| 平时（点按钮、拖文件、拉滚动条、选中文字） | **永远放行，一件不变** |
| **Ctrl 和 Alt 都按着 + 左键按下** | **吃掉** |

理由：**Ctrl+Alt 按着的时候，这次点击本来就属于本程序**，
用户按这个组合键的目的只有一个——框选取词。底下软件收到这次点击**纯属误伤**。
而且 Ctrl+Alt+点击在 Windows 上没有任何标准含义。

**只吃左键按下**，移动和抬起照常放行：
- 只吃按下：文字选中是**从按下开始的**，不让它开始就够了；
- 不吃移动：不然用户平时按住 Ctrl+Alt 晃鼠标都会觉得卡。

## 四十二、「乱码就返回未识别到文字」——用户亲口提的要求（2026-10-10）

### 四十二·1 用户原话

> 「就不能识别出乱码的时候返回未识别到文字吗」

**这是用户第一次直接规定产品行为，不是我猜的。** 记录在案。

### 四十二·2 先用实测数据回答「能不能」，而不是拍胸脯

**① 置信度这条是真管用的**
```
🔴 乱码   rus 0.70 / 64字   rus+eng 0.70 / 64字   其余 0.27~0.59
✅ 认对   eng 0.45   rus 0.70   rus+eng 0.93
```
乱码最高 **0.70**，认对最高 **0.93**。

**② 但有两条路走不通，已经用数据否掉，写进代码注释里防止以后再走**

**❌ 靠文本形态判断乱码——不可靠**
符号占比实测：
```
正常技术文本  HTTP/2.0 2024-05-01 API v3.1 - 85% CPU, RAM 16GB   0.19
乱码          Масппе {гап|айоп сопуей$ {ех тот опе |апдцаде        0.16
```
**乱码的符号占比反而更低**，而且 `{ } | $ ©` 在正常代码和文档里本来就大量出现。
（`TextNormalizer.LooksLikeGarbage` 只看「符号占比 > 0.6」，
 而真正的 OCR 乱码恰恰是「大部分是字母、零星夹着怪符号」，**比例很低，它根本看不见**。）

**❌ 靠「两个引擎结果一致」判断可信——也不可靠**
那一段乱码里，`rus` 和 `rus+eng` 给出**一模一样的 0.70 / 64 字**，
一致度 **100%**，**结果还是错的**。**两个引擎会一致地错。**
（我三十七轮说过「打算用一致性判断」，**这一条被数据正式否掉了**。）

### 四十二·3 改了两处

**① 门槛从 0.60 提到 0.78**
当初定 0.60 的办法是「找认对和认错之间的空档，卡在中间」。
材料 3 之后空档里掉进来两个新样本，**全是乱码**，而 **0.70 正是从 0.60 底下钻过去的**：
```
认成乱码的：0.13  0.32  0.33  0.57  0.70  0.76
 ────────────────────────────────
                                    ↑ 0.76 ~ 0.81 又是空的
认对了的：0.81  0.85  0.86  0.87  0.88  0.93  0.94  0.95  0.96
```
**0.78 卡在新的空档里，还是那个办法。**

**② 低分时不再退回 Windows，直接返回「未识别到文字」**
以前是「保留 Windows 自带」。改掉的依据：
```
Tesseract  `Масппе {гап|айоп сопуей$ {ех…`   0.70
Windows    `@aIiJI config.txt He HaIIÅeH`     全乱
```
**退回去等于没挡，用户照样看到乱码。**

### 四十二·4 代价（用户自己认了）

偶尔会拒掉一些「其实还能看」的结果，换来的是**基本不出现整段乱码**。

### 四十二·5 仍然做不到的事（必须如实说）

**「看起来像文字的错字」，任何引擎都判不出来。**
比如 `Cbeub` 其实是 `Съешь`、`me@example.co` 其实是 `me@example.com`——
它们**都是合法的、看起来正常的字**，分数也很高（0.94）。
这一类只能靠用户自己核对，**软件没有任何办法自动发现**。

## 四十三、用户澄清「框了一半」+ 补上「框到半个字」的提醒（2026-10-10）

### 四十三·1 用户澄清：上次那个 0.57 是**框了一半**造成的

> 「其实是我把顶部的小黑子框了一半导致的，这样框不知道能不能识别出来」

**先分清两件完全不同的事，别混为一谈**：

| | 是什么 | 能不能认出来 |
|---|---|---|
| **框了一半的段落** | 一半的字**根本不在图里** | **认不出来，而且必然认不出来**——图里没有的东西任何引擎都读不出来 |
| **框到半个字** | 字被切掉一部分，但还在图里 | **能发现**，只是要专门去查 |

### 四十三·2 「框了一半」这次的处理反而变好了

上次那种情况：
```
Tesseract（chi_sim）0.57 → 这一切专| J亲六革路刚队急材衬宫人小由有加了息…   全乱
Windows            → 、 25 段，每段框一次，按 F S M X P C 的顺序 ·          能读
```
**上一轮的 0.78 门槛正好把它挡住 → 退回 Windows 那份虽然不全、但人能读的结果。**
这正是四十二节那个改动的价值。

### 四十三·3 🔴 「框到半个字」——这是置信度**完全帮不上忙**的一项

实测过的例子：
```
me@example.com   →   me@example.co
              置信度 0.94，比全对的那些还高
```
**因为「少一个字母」看起来仍然像一句正常的英文，
引擎不会觉得自己认错了，所以我们也就没有任何办法发现。**

四十二节那套（置信度 / 文本形态 / 双引擎一致）**在这一类面前统统失效**。

### 四十三·4 补的做法：**不猜，如实提醒**

我们**不知道**那个字本来是什么，**补不出来，也不该瞎猜**。
能做而且值得做的只有一件事：

**选区的边正好顶在笔画上时，在提示里明说。**

判断方法：正常框选时选区四边和文字之间总有点空隙；
而「半个字」意味着**笔画直接顶到了选区的边界**。
所以只要**最外面一列／一行像素里有笔画**，就说明边界切到了字。

提示语：
```
⚠️ 选区的左边正好顶在文字上，很可能切到了半个字，结果可能少一两个字，建议把框放宽一点再试
```

**只查左边和上边**：实测出问题的是右边界（`me@example.co`）和上边界（切到上一行）。
下边界切字切到的通常是**下一行**，那是「框多了」不是「框少了」，提示语不一样，先不动。

### 四十三·5 这一项的定位

**它是提醒，不是修复。** 框到半个字这种情况，
**除了提醒用户，没有任何办法能把那个字补回来**。
这一条要如实写在说明书里，别让人以为软件能自动补全。

## 四十四、C1 找到真根因：**四路里没有一路是反色的**（2026-10-10）

### 四十四·1 成绩 20/25（25 段，C1 这次测了）

上一轮的两个新功能**都在 C1 上触发了，而且都判断正确**：
```
C1  Machine translation converts text 行 0 m one language t0 another.
    Tesseract 置信度只有 0.70（低于 0.78，判定为乱码）      ← 四十二节的新门槛 ✅
    ⚠️ 选区的左边和上边正好顶在文字上，很可能切到了半个字   ← 四十三节的新提醒 ✅
```
**问题是 Tesseract 为什么只有 0.70。**

### 四十四·2 根因：**深底浅字（深色模式）没有被照顾到**

C1 的样式是 `background:#1e1e2e; color:#e8e8f0;`——**深底浅字**，
**实战里这就是深色模式的界面，太常见了。**

**Tesseract 期望的是「深字浅底」**，底色一深，它内部那套二值化就吃力，分数上不来。

而原来那四路是 **红、绿、蓝、灰**——红绿蓝三路只是**拆颜色**，
**四路里没有任何一路是把明暗翻转的**。所以深色模式一个都没被照顾到。

**修法：加第五路「反色」。**
深色模式一翻过来就变成 Tesseract 熟悉的「深字浅底」。

**为什么放进「五路」里交给置信度选，而不是直接判断「要不要翻」**
- 判断深底浅底要定阈值，**又一个要拍的数字**
- 多跑一路只是多花几十毫秒
- 而且**浅底深字那几路本来就比反色强，翻过来也不会误选——选不中等于没跑**

### 四十四·3 顺带记下：M2 这一轮出现了**回归**

```

    ⚠️ 已采用 Tesseract（置信度 0.90）
```
chi_sim 这次在**第三行多吐了一个孤零零的 `[`**（前两轮都是 0.93 干净输出）。

**这一类属于「看起来像文字的多余字符」，正好是四十二节说过的
「置信度、文本形态、双引擎一致全都失效」的那个盲区。**
本轮**没有改**——不是不想修，是**没有可靠判据**，硬改会伤到现在正确的那些。

### 四十八·3 🔴 真根因：判底色的采样点少得荒唐

```csharp

```
584×34 缩到 **16×1**，**整张图只用了 16 个像素**，
而且插值方式是 **NearestNeighbor（最近邻）——照抄一个像素，根本不做平均**。

**缩小 36 倍还用最近邻，等于「随便挑 16 个像素」。那不叫平均，那叫抽样。**

**推出来的过程**
```
用户框的是白底黑字 → 平均亮度应该很高（约 200）→ 不该反色
     ↓
但那 16 个采样点恰好都落在深色笔画上
     ↓
算出来的平均亮度很低 → 误判成「深底浅字」→ 整张反色
     ↓
白底黑字 变成 黑底白字 → 所有引擎一个字都认不出
```

**为什么五次一模一样**：每次框的位置都一样，**采样点也一样**，所以判断也一样。
**看起来特别像「稳定复现的缺陷」，其实是我自己算错的。**

### 四十八·4 改法

| | 原来 | 现在 |
|---|---|---|
| 缩到 | **16 像素**（16 个采样点） | **128 像素**（896 个采样点） |
| 插值 | **最近邻**（照抄，不平均） | **双三次插值**（GDI+ 缩小时做真正的加权平均） |

**16 → 128 不是拍脑袋**：
584×34 会缩成 128×7 = 896 个点，**足够代表整张图**；
再多只是白费时间。

### 五十·3 🔴 真根因：**反色的时候没管透明度**

```csharp
row[x*4+0] = (byte)(255 - row[x*4+0]);   // B
row[x*4+1] = (byte)(255 - row[x*4+1]);   // G
row[x*4+2] = (byte)(255 - row[x*4+2]);   // R
// 透明度不动  ←←← 问题在这里
```

`new Bitmap(w, h, Format32bppArgb)` 创建的位图**每个字节都是 0，包括第四个（透明度 A）**。
上面三行只翻了颜色，**没碰 A**，于是**整张图全透明**。

**后果链条**
```
整张图 A=0（全透明）
   ↓

   ↓

eng / rus / rus+eng / 四路 / chi_sim 全部置信度 0.00、0 字
   ↓
界面显示「未识别到文字」
```

**修法一行**：`row[x*4+3] = 255;`

### 五十·4 为什么别的函数没这个毛病

`ToGrayscaleOnly` 用 `Graphics` 画图，那条路**会自动把透明度处理好**。
**全项目只有 `Invert` 是手写 `LockBits` 逐字节写的，所以也只有它踩这个坑。**

> **教训一：查不动的时候，直接把现场留下来。**

## 五十一、C1 的**真正根因**：`Invert` 忘了先把原图拷进去（2026-10-10）

### 五十一·1 上一次那个「透明度」的判断**是错的**

上一轮从「文件小 + 图上看不到文字」推出「整张图全透明」，
**这个推断方向错了**——真正的原因在更前面一步。

### 五十一·2 像素级数字，一步定论

不再靠眼睛看图，**直接算亮度**：
```
原图    586×33  亮度 min=32   max=233  平均=62.0    ← 深底浅字，有内容
反色后  586×33  亮度 min=255  max=255  平均=255.0   ← 纯白，一个像素都不差
```
**`255 - 32 = 223`，绝不该是 255。**
说明**那三行减法压根没读到原图的像素**。

### 五十一·3 🔴 错在哪：`row` 指向的是**自己新建的那张空图**

```csharp
var result = new Bitmap(w, h, Format32bppArgb);
var data = result.LockBits(...);
row[x*4+0] = 255 - row[x*4+0];   // row 读的是 result 的缓冲区！
```

**从头到尾没有把 `source` 画进 `result`。**
`result` 是刚 `new` 出来的，**一个字节都没写过**，
所以缓冲区全是 0，`255 - 0 = 255`。

> **我一直在「一张空白画布」上做反色，出来的必然是纯白。**

### 五十一·4 修法

```csharp
using (Graphics g = Graphics.FromImage(result)) g.DrawImageUnscaled(source, 0, 0);
// 之后再逐字节翻颜色，并把 A 显式写成 255
```

**先用 Graphics 把原图拷进去，再翻。**
（顺带把上一轮加的 `A = 255` 保留——那是**另一个**独立的坑，
不是这次的全貌，但该修还是要修。）

### 五十一·5 🔴 五轮排查复盘

| 轮次 | 当时的判断 | 实际
|---|---|---|
| 44 | 四路里少了一路反色 | 加了第五路，**位置就错了** |
| 45 | 反色位置太晚，白边翻成黑边 | 挪到最前面，**方向对了但实现是错的** |
| 46 | 空框 | 五次一致，推翻 |
| 48 | 采样只用了 16 个像素 | **是真 bug，改得对**，但不是全貌 |
| 50 | 整张图全透明 | **推断错了**，真因在更前面 |

**根因是四十五节就写下的那个 `Invert` 函数**——
我写了它、**逐行读过它**、还给它配了长注释，

### 五十一·6 教训

> **一、写图像处理代码，`new Bitmap` 出来的位图是「空画布」，不是「原图的副本」。**
> `LockBits` 拿到的是**新图自己的指针**，不是输入图的指针。
> **手动逐像素操作之前，必须先把源图拷进去。**

> **二、改完 bug 要看「结果长什么样」，不是看「代码对不对」。**
> 代码读起来完全合理——命名清楚、注释详尽、逻辑通顺，
> **但它反的是一张空图。** 只有跑出来的数字能揭穿它。

> **三、统计量比肉眼可靠。**
> 「图看起来是白的」和「每个像素都是 255」是两回事。
> min/max/平均三个数字一打，**问题当场就缩到一行代码**。

## 五十八、C4 的局部阈值**第一版写错了，把 C4 弄得更糟**（2026-10-10）

### 五十八·1 实测：从 0.82 掉到 0.31

```
四路之一「局部阈值」：置信度 0.30，内容【   eee me ES EE SETS BEES Sg gk tee ee NS \ YA  HTTP/2:0:...  RAM. 46GB  Ve NA Se rr...】
「局部阈值」这一路确实更好（分数 0.30/0.81，有效字符 110/32 个），改用它
→ 最终 0.31，低于 0.78，判定为乱码
```
**用户看到的是一段乱码，比原来那个 `HT TP` 更糟。**

### 五十八·2 错在哪：「减去一个固定常数」这个做法本身

第一版写的是 `阈值 = 局部均值 − 12`：
```
局部均值 ≈ 237，减 12 得 225
条纹暗档  220 < 225   → 照样被判成笔画
```
**条纹根本没被抹掉**，碎成一片噪点，被读成了 `eee me ES EE SETS BEES`。

**那个「12」既不够大，也没有���何依据——纯粹是拍脑袋。**
而且帕累托规则看到「有效字符多（110 > 32）」就采纳了，
**又一次被「字数多」骗了**（和 F5 那次一个毛病）。

### 五十八·3 改用 **Sauvola**：同时看局部均值**和局部标准差**

```
阈值 = 均值 × (1 + k × (标准差 / 动态范围 − 1))
```

**能治条纹，靠的是「条纹区的起伏天生就大」：**

| 区域 | 均值 | 标准差 | 阈值 | 结果 |
|---|---|---|---|---|
| **条纹区** | 237 | **≈17** | **≈196** | 条纹暗档 **220 > 196** → **算背景** ✅ |
| **文字区** | ≈230 | ≈50 | ≈202 | 文字 **34 < 202** → **算笔画** ✅ |

**关键差别：偏移量不再是拍脑袋定死的，而是「这一块有多花」算出来的。**
一块区域越是明暗起伏，阈值抬得越高——**条纹正好是最起伏的那种**。

### 五十八·4 教训（很值钱）

> **「局部均值 − 常数」这种做法，只在对比度统一时成立。**
> 一旦背景本身有花纹（条纹、渐变、水印、摩尔纹），
> 常数就永远不够大——**因为「花纹」和「文字」的亮度差本来就小**。

> **遇到花纹背景，要用能感知「起伏程度」的判据，
> 而不是「比周围暗多少」。**

> **另外：帕累托规则又一次被「字数多」骗了。**
> 这是 F5 那次之后**第二次**同样的错。
> **「有效字符多」不等于「对」——乱码也能有很多字符。**
> 这一条要单独记下来，后面找机会统一处理。
