# 阶段三 S3 第三引擎选型对照（2026-10-27）

> 结论先说：**推荐 RapidOcrNet（RapidOCR 的 .NET 版，ONNX Runtime + PP-OCRv5 latin 模型）**。
> 硬门槛四项全过，且是四个候选里唯一「装完就能离线跑、不碰 Python、不碰 OpenCV、不超 50MB」的。

## 2. 为什么把 B/C 直接判死

- **B. PaddleOCRSharp**：nupkg 80.25 MB 全是模型（v5/v6/tiny/small/SLANet 一堆用不上的），
  **真正要的 `paddle_inference` 原生库根本不在包里**——它要你另外去 GitHub 下（CPU 版通常 40~60 MB）。
  光是「部署包不自洽」这一条就不合格：构建脚本要联网抓二进制，换机器可能挂。
- **C. Sdcb.PaddleOCR**：实测原生 `paddle_inference_c.dll` 88.72 MB + `mklml.dll` 88.36 MB + `mkldnn.dll` 45.83 MB，
  再加 OpenCvSharp 的 `OpenCvSharpExtern.dll` 65.40 MB —— 装完 **513 MB**，直接破 300 MB 上限。
- **D. PP-OCR ONNX 手工版**：体积和 P95 与 A 几乎一样，但 RapidOcrNet 已经把那 3000 行预处理（DBNet 后处理、
  透视裁剪、CTC 解码、字典映射）写好了，自己再写一遍纯属重造轮子。**用 A 就是 D，还省 3000 行。**

## 3. 推荐方案细节（A）

- 包：`RapidOcrNet` 4.2.0（Apache-2.0），依赖 `Microsoft.ML.OnnxRuntime`、`SkiaSharp`、`Clipper2`。
- 模型：包内自带 `models\v5\`（det 4.60 MB / cls 0.97 MB / **latin rec 7.54 MB** / latin 字典）。
- 调用：`using var ocr = new RapidOcr(); ocr.InitModels(); var r = ocr.Detect(路径, RapidOcrOptions.Default);`
- 备选模型：`RapidOcrModelSet.PPOCRv6Small`（多语种，~31 MB，要另下）——**先不用**，v5 latin 已经够。
- 不需要 GPU、不需要 Python、不需要 OpenCV（原生依赖只有 `onnxruntime.dll` + `libSkiaSharp.dll`）。

## 4. 引擎裸跑预览（**不是验收结论**，仅供选型参考）

把 80 张裁样的引擎原始输出直接喂现有量具（`比对回放.ps1 -按行`，无多路兜底、无极性切换）：

| 指标 | 现管线（Tesseract 5.5.3） | **RapidOCR 裸跑** |
|---|---|---|
| L_行 | 35/69 = 50.7% | **44/69 = 63.8%** |
| L_整块 | 9/52 = 17.3% | **30/52 = 57.7%** |
| 整行丢 | 49 例（64%） | **3 例（6%）** |
| 改字 | 28 例（36%） | 44 例（88%） |

**读法**：新引擎几乎不再「整行丢」，错法从「丢」变成「形近字」——这正是可以靠后续补丁（字典/后处理）收口的类型。
整块从 17.3% → 57.7% 是最大的变化。但**两者都远低于 95%**，选型通过 ≠ 验收通过。

## 5. 风险（按严重度）

1. **L_行 63.8% 仍远低于 95%**：换引擎是「把丢字变错字」，不是「一步到位」。后续至少还要吃一轮形近字/字典/极性补丁。
2. **像素字体两款**（Barony 34 行、Undertale 6 行）：PP-OCR 训练集里没有这种方块像素字，
   大概率要专属识别器或字符级校正。**不预设，等集成后数据说话**（用户 m01308 第 4 条）。
3. **L_整块 57.7% < 70%**：按方案还得做「提示重框/自动内缩」的产品交互。
4. **冷启动 +297 ms**：首次识别 ≤1.2s 的红线要重新实测（模型加载只在第一次）。
5. **体积贴近上限**：163.6 MB / 300 MB 还有余量，但再加模型（v6 31 MB）就会紧张。
6. **供应链**：包与模型都来自 NuGet，可离线固化；比 B 的「去 GitHub 下二进制」稳。
