# 框选手势 bug：假设与取证（S4-B 第 1 轮，只读）

## 复现循环红的结果（tools/脚本/真机回归-框选-new.ps1）

exe = `release/v0.3.4.3-nl/TranslatorApp.exe`，22 个检查项，FAIL 4。
所有 PASS 项说明：A/B/C/D/E 的「松键后是否触发识别」「overlay 数量」「CPU 回落」都是对的。

| 场景 | 检查项 | 期望 | 实际 |
|---|---|---|---|
| A 先松 Ctrl | moving after release must not re-show mask | True | **False** |
| A 先松 Ctrl | one drag builds the mask exactly once | 1 | **2** |
| B 先松 Alt | moving after release must not re-show mask | True | **False** |
| B 先松 Alt | one drag builds the mask exactly once | 1 | **2** |

即：**拖动中途松开 Ctrl 或 Alt 之后，遮罩被收掉了，但只要鼠标再动一下，遮罩又铺回来了。**
这就是用户说的「松开按键后选框还留在屏幕上」——不是收不掉，是收掉之后又被重新铺上。

---

## 五个假设（按可能性排序）

### H1 遮罩自己被「更新」逻辑重新铺回来 —— 最可能
`src/UI/SelectionOverlay/SelectionMaskWindow.xaml.cs:192`：
```csharp
public void UpdateSelection(RECT rect)
{
    if (!_overlayActive || !_mouseBlocking) BeginOverlay();   // ← 这里
    ...
}
```
松键时 `App.xaml.cs:508` `_maskWindow?.EndOverlay()` 把 `_overlayActive` 置 false。
但状态机**故意不打断拖拽**（`SelectionStateMachine.cs:313` 只在松开左键那一刻才判组合键），
所以 `_state` 仍是 `Dragging`，鼠标再动 → `OnMouseMove:255 DragUpdated` → `OnDragUpdated` → `UpdateSelection`
→ 发现 `_overlayActive == false` → **自动 BeginOverlay**，遮罩复活。
- 如果是它：改「松键后不再接受 DragUpdated」或「UpdateSelection 不自动重铺」，bug 消失。
- 改错方向会更严重：直接删掉 `UpdateSelection` 的自动重铺，正常框选的第一次铺罩会依赖 `OnDragStarted` 里的显式 `BeginOverlay`（那里有调），暂时看不出代价，但 `BeginOverlay` 的幂等语义会变。

### H2 状态机没在松键时退出 Dragging
`SelectionStateMachine.cs:118 HandleKey` 只处理 VK_ESCAPE，其余交给 `_hotkeys.ApplyKey`，**没有任何「松 Ctrl/Alt → 状态回 Idle」的分支**。
这是 2026-10-09 有意为之（`:282-312` 大段注释：「拖框过程中松 Ctrl/Alt → 先不打断」）。
- 如果是它：在 `HandleKey` 里加「组合键散了 → 若正在拖，取消」，bug 消失。
- 改错方向会更严重：这会把 2026-10-09 修好的「手指抖一下框就白拖」重新引回来。

### H3 「松键卡顿」= 松键瞬间的 EndOverlay 触发了窗口样式切换
`SelectionMaskWindow.cs:81 ApplyMouseBlocking` 每次调用都走 `SetWindowLongPtr` 改 `WS_EX_TRANSPARENT`，
而且**每次都写一行日志**（`File.AppendAllText`，持全局锁）。
一次框选里它被调用 4 次（铺满后 true / 释放 false / 再铺 true / 收尾 false）。
- 如果是它：把「样式没变就不改」加进去，卡顿消失。
- 改错方向会更严重：缓存 `_mouseBlocking` 判断写错会让遮罩失去「挡点击」能力（2026-10-09 用户报过下面软件能选中文字）。

### H4 空闲 CPU 10% 来自每张提示框的 100ms 定时器
`src/UI/Shared/DebugToastWindow.xaml.cs:85` `_hoverTimer = new DispatcherTimer { Interval = 100ms }`，
`:128` 在构造函数里无条件 `Start()`，每 tick 调 `IsCursorInsideCard()`（GetCursorPos）。
提示框 3 秒关闭才 Stop。
- 如果是它：改成只在鼠标进入卡片区域后才启动，空闲 CPU 回落。
- 改错方向会更严重：悬停暂停自动关闭的功能会失灵（用户可能靠它读完长文本）。

### H5 钩子回调的 PostMessage 风暴
`LowLevelMouseHook.cs:123` 每个 `WM_MOUSEMOVE`（每动 1 像素）都 `Enqueue + PostMessageForWake`，
主线程 `DrainHookEvents` 每收到一条消息就把整个队列取空并 `UpdateComboOverlay()`。
- 如果是它：把移动事件合并（同帧只处理最后一个），CPU 下降。
- 改错方向会更严重：合并过头会让选框跟手变差。

## 修复结果（2026-10-29，commit a359fd6，tag S4-B-手势取消）

### 改了什么
`src/Core/Input/SelectionStateMachine.cs:167` 之后新增 4 行（+21 行含注释）：

```csharp
if (!isDown && _state != SelectionState.Idle && !_hotkeys.IsComboDown)
{
    Cancel("拖框过程中松开了 Ctrl 或 Alt");
}
```

位置在 `_hotkeys.ApplyKey(virtualKey, isDown)`（`:134`）之后，
所以判断的是「更新后的组合键状态」。

### 为什么是根因而不是症状
H1 说的「遮罩被 UpdateSelection 自动重铺」是**症状**：
`SelectionMaskWindow.xaml.cs:194 if (!_overlayActive || !_mouseBlocking) BeginOverlay();`
只是执行了「有框要画」，它没有义务知道组合键状态。
真正的错在于状态机在松键后仍停在 `Dragging`（H2）——
2026-10-09 那条「松键不打断」的决策，把「遮罩该收」和「状态该退」混成了一件事。
修在状态机，所有调用 `DragUpdated` 的路径就都不会再发出去了。

- 用户报的 ④「空闲 CPU 10%」：本机测得 0%，**无法复现**，不修。
