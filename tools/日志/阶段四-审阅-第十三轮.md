## §2 那 4 次超时，到底是什么超时

**这是本轮最重要的一节。**

```
16:29:27.108 [WARN] 翻译失败：翻译超时，原文已保留（时间到了，还没译完，2384 ms）
```

`时间到了，还没译完` = `TranslationFailure.TimeOut`（硬闸到点掐断）。
**不是** `预算用完`——那个是旧 bug（`budget = 2500 - 认字耗时` 减成负数，一个请求都不发）。
旧 bug 已经在 `a8e3d0d` 修掉了，**这次 5 次全部发出了请求**（日志都有「已取到新 token」）。

**所以 P0-F1 修好了，但用户的第一次体验没变好。**

旧症状：认字 1922ms → budget ≤0 → **一个请求都不发** → 用户看到「翻译超时」
新症状：认字 1078ms → budget = 2500 足额 → 请求发出去了 → **但 2384ms 时还没译完** → 用户看到「翻译超时」

**症状一模一样，根因换了一个。** 这说明我上一轮的诊断只治了表面。

## §3 根因：2500 这个数，判断依据已经不存在了

### 3.1 2500 是怎么来的

`TranslationService.cs:34` 的注释写着：

```
/// <summary>单次翻译的硬闸（用户 2026-11-02 拍板：常态 1500ms，硬闸 2500ms）。</summary>
```

用户 2026-11-02 拍板 1500/2500 的时候，**卡片是「等译文到了才显示」的**——
用户盯着**一块空白**等，2500ms 是「不许让用户盯着空屏超过 2.5 秒」的容忍线。

### 3.2 现在的前提变了

用户在 m01019 改的口径：

> 「识别后先把原文识别出来，然后等待翻译就显示[翻译中...]，翻译出来后再显示全文。」

**用户从「盯着空白等」变成了「原文已在读、下面有个东西在转」。**
这时候多等 1 秒、2 秒，用户并不难受——**他在读原文**。

而且卡片不会关：`translating = true` 时 `_closeTimer.Interval = PendingCloseDelay`（8 秒）。

### 3.3 算账

| 阶段 | 耗时 | 出处 |
|---|---|---|
| 取 token（冷启动首次） | 424 ms | `_f2_真bing长文本.py` 实测授权页 |
| 翻译 275 字（不含取票） | 1721~2873 ms | `_f2_长文本_out.txt` 15 次 |
| **冷启动首次合计** | **2145~3297 ms** | — |
| 现在硬闸 | 2500 ms | `HardTimeoutMs` |
| 扣掉取消余量 | 2380 ms | `2500 - CancelOverheadMs(120)` |

**2380 < 2145~3297 的中位数。** 所以「5 次里 4 次超时」不是运气差，
**是 2380 落在了实际耗时的中间偏下位置，本来就该有六到八成超时**。

第二次起就快了（token 进程内缓存，`_tokenExpiresUtc` 提前 60 秒换新），
只有**冷启动第一次**吃这个亏——**而这恰是每个用户的第一次。**

## §4 裁决：硬闸 2500 → 5000

### 4.1 为什么不是「加预取」

执行 AI 提了两条路：「放宽硬闸」或「预取 token」。它问对了问题，我选前者：

- **预取**只能省 424ms。2380 → 2960 可用，但真 Bing 最坏 3297 **还是超**。
  而且要多写一段启动异步、要处理预取失败、要等真的有网。**加了复杂度，问题还在。**
- **放宽硬闸**一行改一个数，直接把 3297 装进预算（5000 留 1.5 倍余量）。

ponytail：能改一个常数解决的，不写一段异步。

### 4.2 改成多少

`HardTimeoutMs = 5000`。

依据三条：
1. 真 Bing 冷启动最坏 **3297ms**（实测，非估计），5000 留 **1.5 倍余量**；
2. 必须 **< PendingCloseDelay 8000ms**，否则翻译还没回来卡片先关了——
   5000 之后还有 3 秒让译文显示；
3. 用户已有原文可读 + 「翻译中…」在转，**5 秒是能接受的等待上限**，再长就该放弃了。

### 4.3 代价要写清楚

| 场景 | 改前 | 改后 |
|---|---|---|
| 冷启动第一次框选 | 2380ms 掐断，4/5 失败 | 最长 5000ms，正常 2145~3297 **能出译文** |
| 网络极慢 / 有网但很卡 | 2.4 秒放弃 | **最长等 5 秒**才放弃 |
| 断网 | 约 2.1 秒（连接快速失败） | **不变**（连接失败比硬闸快，`S3` 实测 P50 2086） |

**唯一的代价是「有网但极慢」时多等 2.6 秒。** 这个场景下：
用户能看到原文、能看到「翻译中…」在转、卡片不会关。**可以接受。**

### 4.4 不做的事

- **不做 token 预取**（省 424ms 但加复杂度，先不加；真用几天还嫌慢再说）
- **不动 `PendingCloseDelay` 8 秒**（译文落地时用 `CloseDelaySeconds` 3 秒是阶段三定的，
  属于另一件事，不在这轮扩大范围）
- **不动「常态 1500ms」这个目标值**（它是常态目标，不是硬闸；真 Bing 长文本达不到它，
  但短句能达到——`Hello world` 969ms、UI 短句更短）
