## 一、这个版本做了什么（大白话）

以前程序只能待着不动。现在你**按住 `Ctrl` + `Alt`，再按住鼠标左键拖动**，
屏幕上会盖上一层半透明灰罩，跟着鼠标画出一个亮色选框；松手选框消失，
程序把这个框的坐标记进日志，并在框的旁边弹一个小卡片把坐标显示出来，3 秒后自己关掉。

## 二之二、用户验收后追加的需求：框选时下面的窗口要「看得见但点不动」

> 2026-10-08 用户原话：「框选的时候还是能互动窗口，导致框选的时候可以正常拖动窗口，选择文字，
> 这个不行，我需要像截图一样框选时下方的窗口啥的不能互动但是看得见。」

### 原来的毛病出在哪

第一版把遮罩做成了**全程鼠标穿透**（规格「不许做的事」里写了「遮罩绝不能吃掉鼠标事件」）。
更要命的是**时机**：遮罩是在「左键按下之后」才弹出来的，
也就是说**点击先被下面的窗口吃掉了**，程序后知后觉盖上一层罩——
窗口在那一刻已经开始拖动了，罩子盖上去也拦不住。

### 改法（两处）

1. `SelectionMaskWindow`：`WS_EX_TRANSPARENT`（鼠标穿透）改成**按需切换**——
   没在框选时穿透，**正在框选时摘掉**，遮罩接管鼠标。
2. `App.xaml.cs`：**一按下 `Alt`（Ctrl 已按着）就立刻弹罩并接管鼠标**，
   不再等左键按下。这一步是关键：左键落在遮罩上，下面的窗口收不到点击。
   这就是所有截图工具的做法。代价是按住 Ctrl+Alt 的瞬间屏幕会闪一下灰罩，松开即消失。

### 怎么证明改对了（命中测试，最硬的证据）

不用模拟拖拽（**实测发现：模拟拖拽在本环境根本拖不动任何窗口**，按不按 Ctrl+Alt 都拖不动，
拿它当证据会得出错误结论），而是直接问 Windows「这个点的点击发给谁」。
同一个坐标 `(650, 226)`（记事本标题栏上），三次查询：

| 时刻 | 命中的窗口 | 鼠标穿透位 | 结论 |
|---|---|---|---|
| 平时 | `'无标题 - 记事本'` | 关 | 正常操作不受影响 ✅ |
| **按住 Ctrl+Alt** | **`'框选遮罩'`** | 关 | **点击被遮罩接管，下面的窗口点不动 ✅** |
| 松开 Ctrl+Alt | `'无标题 - 记事本'` | 关 | 遮罩无残留，一切恢复 ✅ |

> 注意 `WindowFromPoint` 在命中测试时会**跳过带 `WS_EX_TRANSPARENT` 的窗口**，
> 所以这个探针查的就是「鼠标穿透」这一位本身，测的正是用户抱怨的那件事。

### 顺带证明灰罩确实画出来了（像素比对）

同一坐标「按住 Ctrl+Alt」与「松开」的亮度差：

| 坐标 | 有罩 | 无罩 | 差值 |
|---|---|---|---|
| (1500, 300) | 亮度 163 | 亮度 255 | **-92** |
| (1800, 800) | 亮度 163 | 亮度 255 | **-92** |
| (300, 950) | 亮度 86 | 亮度 135 | -49（任务栏图标偏蓝，亮度算法不同） |

-92/255 ≈ 36%，正好等于遮罩色 `#5C000000`（36% 黑），**灰罩确认生效**。

> 这里也有个教训：**肉眼看截图会看错**。第一版遮罩截图的预览看着「好像没变暗」，
> 用像素一比才发现变暗了 92。截图经过压缩预览后对比度会失真，
> **凡是「看起来对不对」的问题，一律用数值说话，不要靠眼睛下结论**。

## 二之三、用户第二次验收后追加的需求：再次框选时不要看见上一次的框

> 2026-10-08 用户原话：「框选完成后再次框选的时候上一次的框会短暂出现零点几秒。」

### 一开始查错了方向

第一反应是「选框没隐藏干净」，于是写了个连拍脚本去抓。抓了 14 张全屏截图（每张 33 毫秒，覆盖 0~460 毫秒），
**一张都没拍到残影**——按这个结果本来该判「没问题、用户看错了」。

**但不能这么下结论**：用户描述的现象很具体，不该因为我没抓到就否定用户。
于是换成**复现用户的真实操作顺序**再截图，一眼就看出来了。

### 真正的原因：那不是选框，是上一轮的坐标提示框

- 选框在 `EndOverlay()` 里已经被设为隐藏，所以它**不会**残留（第一反应确实想错了）；
- 真正还在屏幕上的是**上一轮的坐标提示框**——它要活 **3 秒**。
- 你在这 3 秒内开始下一次框选，它就跟着新遮罩一起出现在画面上，
  看着就像「上一次的框又冒出来了」。

**教训**：测不出来的时候，先怀疑自己的测试方法，再怀疑用户。
用户描述操作现象通常比 AI 描述得更准——**AI 抓不到，不等于现象不存在**。

### 改法

新��轮框选一开始（按下 Ctrl+Alt、遮罩弹出的同一瞬间），**先把上一轮还没消失的提示框关掉**。
`DebugToastWindow` 加了 `CloseIfOpen()`：先看 `IsVisible` 再关，并包 try——
因为 WPF 的窗口 `Close()` 之后不能再操作，对关过的窗口再关一次会抛异常。

### 验证

连做 3 轮「框选 → 不等 3 秒就开始下一次」，每一轮日志都出现：

```
[INFO] 已关闭上一轮残留的坐标提示框（开始新一轮框选）
```

并且这一行**排在「遮罩已铺满」之前**——说明是先收提示框、再弹遮罩，顺序正确。
本次启动 ERROR / WARN **0 条**。

### 顺带做的防御性修复

`BeginOverlay()` 原先是「先 `Show()`、后把选框设为隐藏」，中间差一帧。
虽然实测证明那一帧不会真的闪（选框早就在 `EndOverlay` 里隐藏了），
但这属于「顺序不对就是不对」，已改成**先隐藏再 `Show()`**，杜绝这一类问题。

### 顺带修好的一个测试脚本 bug（第三次了）

这次坐标测试**同一条命令时而对时而不对**：有时 (400,300) 500×300，有时 (741,304) 159×296。
查下来是脚本的 `Goto()` 只「挪一下 + 睡 90 毫秒」就接着按左键，
而 `SendInput` 是**异步投递**的，光标有时还没走到位，左键就落在上一位置了。
已改成**轮询 `GetCursorPos`，等光标真的到位（±1 像素）才继续**。

> **同一个坑这次是第三次踩了**（前两次是坐标归一化、模拟拖拽拖不动窗口）。
> 一句话总结：**测试脚本自己出错时，表现出来就是「程序 bug」，必须先排除尺子。**

修好脚本后连测 11 次，**10 次坐标精确**；2 次起点差了 2~10 像素。
查了状态机源码：它直接用钩子事件里的坐标，没有做任何换算或取整，
所以这几像素是**脚本注入时桌面光标本身的抖动**（活着的桌面上还会有人动鼠标），不是程序的 bug。

## 二之四、真正的旧蓝框闪现（前两次都修错了地方）

> 用户第二次澄清：「**还是有框，并不是小卡片的问题**，不过小卡片改的还行。
> 这个框就是框选的蓝框，左下角还有框了多少像素呢。」

### 为什么前两次没修对

1. **第一次**：以为是选框没隐藏干净 → 连拍 14 张截图，一张都没拍到 → 误以为是坐标小卡片。
2. **第二次**：把提示框收掉后，用户说蓝框还在 → 说明我认定的对象就错了。

**根因**：我从头到尾**假设自己知道用户说的是什么东西**，
两次都在优化「怎么让它消失」，却没去问「它到底是什么状态」。

### 靠加日志才查出来的真相

在 `Show()` 之前打一行诊断（只查状态，不猜）：

```
[诊断] Show() 之前：框可见=Collapsed  宽=500  高=300  位置=(400,300)
```

真相一目了然：

- 逻辑上框**已经是 Collapsed**（所以程序「什么都没做错」，截图也拍不到）；
- 但它**仍然留着上一轮的宽高和位置 500×300 @(400,300)**；
- 本窗口 `AllowsTransparency=True` 是**分层窗口**，`Hide()` 再 `Show()` 时，
  **合成器会短暂重放最后一帧**，而那一帧里画着上一次的蓝框和像素标签。

**这就是为什么外部截图抓不到**：它在合成器里，不在 WPF 的逻辑树里。
日志查逻辑状态，截图查合成结果，两者要配合着用。

### 改法（两处，一起才有效）

1. `ClearSelectionBox()`：清空时**不但隐藏，连宽高和位置一起归零**（`0×0 @(0,0)`）；
2. `EndOverlay()`：顺序改成 **清空 → `UpdateLayout()` 让「干净的一帧」真的画出来 → 才 `Hide()`**。
   反过来的话，Hide 的那一刻画面上还有蓝框，合成器重放的就是那一帧。

`BeginOverlay()` 同样改成 **清空 → `UpdateLayout()` → `Show()`**，双保险。

### 验证

加诊断跑一轮，确认第二次框选时：`框可见=Collapsed 宽=0 高=0 位置=(0,0)` ✅
然后**删掉诊断代码**重新出包（诊断日志不进正式版），再跑全量回归：

| 项目 | 结果 |
|---|---|
| 五种场景 | 全部正确 |
| 连做 4 轮连续框选 | 坐标全部精确 = 500×300，每轮都收掉残留提示框 |
| 遮罩残留 | 无 |
| ERROR / WARN | **0 条** |

> **这一条我无法自己验收**：这个闪现发生在合成器里，外部截图抓不到（已实测多次）。
> 必须由你实际看一眼才能确认。**所以这条暂时记为「已修复、待用户确认」，不是「通过」。**

## 二之五、旧蓝框闪现（真正的修复：换掉 Hide/Show）

> 用户第三次反馈：「**还在冒，他出现在上一次框选的位置，闪了大概 0.2s 左右**。」

### 关键线索：0.2 秒

我上一版判断是「合成器重放最后一帧」，**被这个数字直接否掉了**——
重放一帧是 16 毫秒，0.2 秒是**十二帧**，那是实实在在画了好几帧，不是重放。

### 这次只做一件事：把过程记成时间线

不再猜，加日志把每一步都记下来（只记状态，不改逻辑）。第二次框选的时间线：

```
[时间线] UpdateComboOverlay：Ctrl+Alt 按下
[时间线] BeginOverlay 清空旧框          ← 遮罩弹出
[时间线] EndOverlay 清空并隐藏           ← 上一轮结束
...
[时间线] BeginOverlay 清空旧框          ← 新一轮弹出
[时间线] UpdateSelection 画框 (299,200)-(300,204)   ← 新框，从新位置开始
```

**结论很清楚**：第二次框选的第一个绘制就是新位置的小框，
**从头到尾没有任何一行画过旧框**。逻辑侧是干净的。

又让程序用 `RenderTargetBitmap` 把「遮罩刚弹出那一刻」自己渲染成图来看——
结果是一张全白图（那一刻遮罩矩形绑的 `ActualWidth` 还是 0），这张图说明不了什么。

**所以问题不在「谁画了旧框」，而在「旧画面被重新摆了出来」。**

### 换思路：不再隐藏窗口

既然猜不动，就换成**根本不会犯这类毛病**的做法：

> **窗口句柄只创建一次，之后永不 `Hide()`。**
> 显示/隐藏只切根节点 `Root` 的 `Visibility`：
> `Root` 显示 → 灰罩和选框照常出现；`Root` 折叠 → 整个窗口渲染成全透明，
> 配合 `WS_EX_TRANSPARENT` 鼠标照常穿透，**用户看到的画面和「窗口不存在」完全一样**。

这样就没有「画面表面被重建」这个环节了，这类闪现从根上消失。

```
[2026-10-08 07:58:15.734] 触发=Ctrl+Alt 拖拽 物理像素=(400,300)-(900,600) 尺寸=500×300
```

## 五、这次踩到的三个真 Bug（都是测出来的，不是想出来的）

### Bug 1：坐标日志写错了地方
- **现象**：框选成功了，但 `tools\日志\框选坐标.log` 不存在；文件被写到了 `tools\框选坐标.log`。
- **原因**：`ResolveLogDir()` 找到 `tools` 目录后就直接返回了，忘了还要拼上「日志」子目录。
- **修法**：返回 `tools\日志`；顺带修成日志和 AppLogger 放同一个目录，以后找文件不用两头找。
- **怎么发现的**：验收时特意去核对规格要求的文件路径，发现不存在，顺藤摸瓜找到的。

### Bug 2：坐标提示框第二次框选就再也不出现
- **现象**：第一次框选能看到坐标小卡片，**第二次起就再也没有卡片**，界面上完全看不出来，只有日志里躺着一串 ERROR。
- **原因**：提示框 3 秒后会自动关闭，而 WPF 窗口一旦 `Close()` 就**不能再 `Show()`**。我原来写的是「复用一个实例」。
- **修法**：改成每次框选都新建一个提示框，让它自己 3 秒后消失。
- **怎么发现的**：**只连测一次是发现不了的**。规格要求连测 20 次，第 2 次开始日志里就刷出了
  `InvalidOperationException: 关闭窗口后，无法设置可见性`。这类「安静地什么都不发生」的 bug，
  靠肉眼看界面根本发现不了——所以「连测 20 次」这条要求不是形式主义。

### Bug 3：坐标提示框永远是 0×0
- **现象**：修完 Bug 2 后，提示框一次都不出现，日志里**一条错误都没有**。
- **原因**：我先 `Measure()` 再把 `DesiredSize` 赋给 `Width`/`Height`，但 `DesiredSize` 拿到的是 0，
  于是窗口被设成 0×0，什么都看不见。
- **修法**：改用 XAML 里的 `SizeToContent="WidthAndHeight"`，让窗口自己撑到内容大小，不手算。
- **怎么发现的**：日志里没有错误，截图也看不出异常，只能靠**把「提示框的实际位置和尺寸写进日志」**
  才看出来是 `0×0`。修完现在日志会写：`提示框已显示：位置=(1112,300) 尺寸=268×67`。

### 另外修掉的一个测试脚本 bug（不是程序的问题）
第一次做坐标测试时，测出来的坐标全是乱的（比如拖 (400,300) 却得到 (26,9)）。
排查后发现是**测试脚本自己错了**：`SendInput` 的绝对坐标不是直接给像素，而是要归一化到 0~65535。
**教训：结果不对时，先怀疑尺子（测试方法），再怀疑被量的东西。** 否则很容易冤死正确的程序。

## 七、留给用户做的事

### 1. 录一段框选录屏（规格的硬性证据，AI 录不了）

1. 按 `Win + R`，输入 `snippingtool`，回车；
2. 点左上角「+」新���，选「录制」；
3. 框住屏幕上一个能框字的窗口（比如打开一个网页）；
4. 点「开始」；
5. 按住 `Ctrl` + `Alt` + 鼠标左键，在屏幕上画一个框，**松手**；
6. 再重复两次，每次框不同位置、框不同大小；
7. 点「停止」，保存到任意位置；
8. 回放确认：选框是否跟手、有没有明显延迟。

### 2. 自己正常用一会儿，重点确认这几件事

1. 双击 `release\v0.2\TranslatorApp.exe`，托盘出现「译」字图标；
2. 随便打开一个网页或文档，按住 `Ctrl+Alt` 拖一个框——屏幕上应该有灰罩 + 亮框；
3. 松手后，右下角/框边应该弹出坐标小卡片，3 秒后消失；
4. **不按 Ctrl+Alt 时，正常点按钮、拖文件、拉滚动条、选中文字，一切照旧**；
5. 按住 `Ctrl+Alt` 拖到一半松开 Ctrl 或按 Esc，选框应该立刻消失，什么都不出；
6. 用十分钟以上，再回来试一次框选——确认「用一会儿就失灵」的老毛病没有出现。
