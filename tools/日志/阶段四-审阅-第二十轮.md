# 阶段四 审阅 第二十轮：15 段回放失败的根因定位（2026-11-07）

审核对象：`阶段四-行基线`（`7419e82`）的 S1 全量回放暴露出「28 段退步」。
审核人：架构师（只读源码/日志/配置，不写代码，不改已有文件）。

## 0. 结论

**这不是代码退步，是配置漂移。** 一行代码没坏。

真正发生的事：`%APPDATA%\TranslatorApp\settings.json` 里 `rapidOcrPrimary` 现在是 `true`，
而 10-26 生成 331 段基线那次它是 `false`。**两套基线不是同一个配置跑出来的**，不可比。

**S1 报的「退步 28 段」是假警报。** 但**顺带炸出一个真 bug**：RapidOCR 主通道采纳门槛
只看分数、不看字数，认到 0~1 个字符也敢直接返回，把能认对的 Tesseract 挡在门外。

## 2. 配置漂移的证据

```
%APPDATA%\TranslatorApp\settings.json  修改时间 2026-11-07 11:01
  "rapidOcrPrimary": true
```

这个文件今天 11:01 被写过一次（那一轮在测行基线）。而 `AppSettings.cs:65` 的默认值是
`public static bool RapidOcrPrimary { get; private set; } = false;` —— **默认是关的**。

10-26 那天的日志里「已读取设置」出现 0 次、`RapidOCR` 出现 0 次，说明那天跑的是
「RapidOCR 关闭」的状态。**331 段基线是 RapidOCR 关闭时生成的。**

所以：

- 基线（10-26，RapidOCR 关） vs 今天（RapidOCR 开）→ **两把不同的尺子**
- 报「退步 28 段」不是程序变差，是**换了赛道还在比同一条线**

## 3. 真正的 bug（这才是要修的）

`src/Core/Capture/OcrTextCapture.Foreign.cs:59`：

```csharp
if (rapidText is not null && rapidScore >= RapidOcrMinScore)   // 0.55
```

`OcrTextCapture.Tuning.cs:35` 定的 `RapidOcrMinScore = 0.55`，注释原文：

> 0.55 只比它高一点点，含义是「引擎留下了，而且不像噪声」

这个门槛是**为「一整行文字的平均分」设计的**，但代码里没有任何**字数**保护。
于是「1 个字符、平均分 0.55」和「50 个字符、平均分 0.55」被同等对待。

实测统计（今天那次全量回放，1,268 次 RapidOCR 采纳里）：

- **99 次是「认到 ≤3 个字符就采纳」**
- 其中含 **0 个字符 / 0.61 分**、**0 个字符 / 0.62 分** 这种
- 平均分 < 0.75 的有 82 次

`材料2-E1` 的日志把这件事演得很清楚：

```
第一遍完成：0 行，未识别（没有文字），有效字符 0 个
重认一遍（放大 2 倍并二值化）：第二遍读到 "The quick b rown fox jumps over the 》 a d og"
两遍比分：原图 0 分（0 字），二值化版 81 分（32 字）
采用第二遍
【RapidOCR 主通道】认到 1 个有效字符，平均分 0.59
→ 最终原文：c
→ 取词失败：识别到 1 行但没有有效文字
```

Tesseract 那条路已经读到 32 个字（虽然串了），结果被 RapidOCR 的 1 个字顶掉。

## 4. 修法建议（不动手，等审）

**不要动 `RapidOcrMinScore` 本身**（0.55 是有实测依据的，`阶段3-S3-集成AB.md:44`）。
应该加一道**独立的字数闸门**，形状建议：

```
RapidOCR 采纳条件（现在）：  rapidText is not null && rapidScore >= 0.55
建议：                      rapidText is not null && rapidScore >= 0.55
                            && CountMeaningfulChars(rapidText) >= <下限>
```

下限怎么定，我的建议是**按「比它更差的那条路能不能救」来判断**，而不是拍一个数：

- 认到 0 个字符 → **永远不采纳**（`trimmed.Length > 0` 那个判断已经在做，但它在采纳之后）
- 认到 1~2 个字符 → 只有 Tesseract 老路也认不出来时才采纳（即：先跑老路，老路更差才回来用这 1 个字）

后一条要改流程（现在是 RapidOCR 认到就 return），成本高。**保守做法只要第一步**：

```
if (rapidText is not null && rapidScore >= RapidOcrMinScore
    && TextNormalizer.CountMeaningfulChars(rapidText) > 0)
```

这一条能挡掉「0 字符」那两段，**但挡不住 13 段「1 字符」**。

所以真正的修法需要量：**这 15 段里，RapidOCR 认的那 1 个字，跟 Tesseract 认的 32 个字，哪边对？**
日志已经证明是 Tesseract 对。那闸门该定在「字数 < N 就回退跑老路」—— N 取多少要实测。

## 5. 必须同时处理的两件事（否则下次还会被骗）

### 5.1 基线要记「它是用什么配置跑出来的」

`tools\素材\基线.json` 现在只记 `时间 / 结果 / 段 / 差`，**没记影响成绩的配置**。
`rapidOcrPrimary` 一改，基线就悄悄失效了，而且**没有任何东西会告诉你**。

建议基线加一栏（不是改结构，是加字段）：

```json
"配置": { "rapidOcrPrimary": true, "rapidOcrRec": "en", "rapidOcrUseOriginal": false }
```

`比对回放.ps1` 读基线时，配置跟当前 `settings.json` 不一致就**红字警告或直接拒绝比**：
「基线是 rapidOcrPrimary=false 跑的，现在是 true，不可比」。

**这一条比修 bug 更重要** —— 没有它，以后任何配置改动都会伪装成「代码退步」或「代码变好」。

### 5.2 331 段基线要重生

现在的 `基线.json`（10-26，111 段，91 对）是 RapidOCR 关闭时生成的，
**和现在开的配置不同赛道**。要么：

- **A**：重生成一份「RapidOCR 开」的基线（那 15 段会被记成「错」）
- **B**：临时关掉 RapidOCR 重生一份（跟上基线同赛道）

我建议 **A**——现在默认配置就是开的（`settings.json` 里 true），
基线该反映用户实际在用的配置。15 段记成「错」是**诚实的记录**，
等 bug 修好后它们会自然「修好」。

## 6. 顺带说清楚：为什么之前没人发现

1. **行级回放（80 张）全过**，因为那 80 张恰好都不在这 15 段里 —— 尺子只量了一部分，没量到坏的那部分。
2. **段级基线从 10-26 起就没再生过**（`-Approve` 只做过一次），所以一直是拿旧配置比新配置。
3. **`-Approve` 的退步闸门会拒绝写**，于是「基线过期」这件事被闸门反向锁死 ——
   闸门保护了数据，但也让人看不到「这轮差得离谱」这个事实。这轮要不是我手动去跑一次比对，
   依然不会有人发现。

## 7. 给下一轮的口径

**这不算退步，算「基线过期 + 一个新 bug」。** 收口账上要这么记，不能写成「阶段四回退 28 段」。
