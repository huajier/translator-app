## 2. 我另外查的一件汇报里没提的事：Expect: 100-continue

假服务器**从不回 `HTTP/1.1 100 Continue`**。而 .NET Framework 的 `HttpWebRequest`
默认会发 `Expect: 100-continue` 并等最多 1 秒。实测同一条请求：

```
HttpWebRequest + Expect100=true    718ms   ← 等不到 100 Continue
HttpWebRequest + Expect100=false     6ms
HttpClient     默认（不发 Expect）  175ms   ← 首个请求，含类型加载；之后 5ms
```

（注：718ms 里混着进程冷启动，不能全算在 Expect 头上，但「等不到 100 Continue」这个坑是真实存在的。）

**这条不进 T2 的账，进 T3 的账**：T3 必须用 `HttpClient` + `SocketsHttpHandler`，
**不许用 `HttpWebRequest`**。`SocketsHttpHandler` 默认不发 `Expect: 100-continue`，天然躲过这个坑；
换成 `HttpWebRequest` 就等于每次翻译平白多几百毫秒，够把 400ms 的 P95 预算吃光。

## 3. T2 遗留的两处小瑕（不阻断，T3 顺手处理）

**3.1 端口是动态的**：脚本从 5099 起，被占就 +1，实际端口**只打印在 stdout**。
T3 的验收脚本必须先起服务器 → 解析 stdout 拿到真实端口 → 再写 `translateEndpoint`。
不能写死 5099（本机 5090 段常年有别的服务）。

**3.2 单线程 + `Connection: close`**：每个请求新开一条 TCP。
回环上开销可忽略，但**不要把「假服务器 5ms」当成「真实网络 5ms」**——
T3 报 P95 时必须注明「本地假服务器」，真机数字要到 T6 才有。

## 4. 进 T3 之前必须回答的三个问题

**Q1（最关键）：你现在手上有没有微软 Azure 的翻译密钥？**
- 有 → T3 写完能立刻做一次真机抽检，不用等到 T6 才发现协议还有没对上的地方。
- 没有 → T6 会卡在「无法真机验」，而「认字离线翻译联网」这个决策等于没落地。
  这种情况我们要么改用免费的备用通道，要么先把「未配置密钥」做成一个明确的用户可见状态。
**决定它，才能决定 T3 的验收里要不要含一次真联网。**

**Q2：密钥存磁盘，明文还是加密？**
- 明文（最简单）：任何能打开 `%APPDATA%\TranslatorApp\settings.json` 的人都能看到你的密钥。
  你自己一个人的电脑，风险不大；学校机房、公司共用电脑，等于把密钥贴在屏幕上。
- 加密：Windows 自带 `ProtectedData.Protect(..., CurrentUser)`，只有你这个 Windows 账户能解开，
  多两行代码。代价是配置文件不能再手工编辑（环境变量那条路仍然可用，不受影响）。

**Q3：目标语言下拉给几种？**
- 全量（微软支持 100 多种）：一次做对，但下拉框很长，且我们没测过冷门语言。
- 只给常用 8 种左右（中文简体/繁体、英文、日文、韩文、俄文、法文、德文）+ 允许手填语言码：
  覆盖你说的「学校/家里/公司」三种场景，出问题也好排查。
