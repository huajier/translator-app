## §1 这两答改变了什么

### 1.1 Q2 是设计变更，不是数字微调

Q2 之前的口径（我给的 P1-C2 硬性要求，源自用户早期回答 Q5「等译文到了才开始」）：

> **翻译跑完才调一次 `card.UpdateWith(result, translation)`，绝不分两次调。**
> 理由：`UpdateWith` 末尾会重启 3 秒自动关闭计时器，分两次调会让译文晚到后只剩 1 秒能看。

**用户现在明确要的正好是相反的**：原文先出 → 显示「翻译中…」→ 译文到了再补上。

**P1-C2 当场撤销。** 不是用户改主意改错了，是当时的约束变了：
- 当时担心「分两次调只剩 1 秒能看」，前提是**两次都在 3 秒倒计时里倒着走**。
- 但现在**第二次调用会把计时器重置一遍**（`DebugToastWindow.xaml.cs:470-471` 每进一次 UpdateWith 就 `Stop(); Interval=3s; Start()`），
  所以译文落地那一刻用户**重新拿到完整 3 秒**。担心不成立。

**这条要写进代码注释，免得以后有人看到 P1-C2 的旧记录又改回去。**

### 1.2 Q1 被 Q2 吃掉了大半

Q1 选的是「给翻译留 1.5 秒保底，第一次最长等 3.6 秒」。

但 Q2 一旦成立，**「等 3.6 秒」这个说法就不存在了**：用户 1.9 秒就看到原文了，不是盯着空白等 3.6 秒。
「等待」被变成了「有内容可读的等待」。

所以 Q1 的「1.5 秒保底」不用照字面实现。**更简单也更满足用户意图的做法：翻译这一步拿独立的固定预算，不从认字时间里扣。**

- 旧：`budget = 2500 - 认字耗时`（冷启动 1922ms → budget=578；4031ms → budget≤0 → 一个请求都不发）
- 新：`budget = HardTimeoutMs`（固定 2500ms，从翻译开始算）

理由：
1. 用户已经有原文可读，不阻塞，多等一会儿可以接受；
2. 2500 > 真 Bing P95 1240ms，留足 2 倍余量；
3. **删掉减法 = 删掉一整类边界情况**（「只剩 300 ms」这种日志彻底消失）；
4. 比用户选的 1.5 秒保底更宽松，效果只强不弱。

**这是对用户 Q1 答案的简化实现，不是无视。** 要在汇报里说清楚。

## §2 要改的三处（T3a 显示时序重做）

### 2.1 `UpdateWith` 加第三态

现状（`DebugToastWindow.xaml.cs`）：

```csharp
internal void UpdateWith(Core.Capture.CaptureResult result)
    => UpdateWith(result, null);

internal void UpdateWith(Core.Capture.CaptureResult result, Core.Translate.TranslationResult? translation)
```

`translation == null` 现在被 `ApplyTranslation` 当成「不显示译文区」→ `HideTranslation()`。

需要第三态：**「正在翻译」**。改法（最小）：

```csharp
internal void UpdateWith(Core.Capture.CaptureResult result, Core.Translate.TranslationResult? translation, bool translating = false)
```

`ApplyTranslation` 增加一条前置分支：

```csharp
if (translating)
{
    // 原文已显示，这里只是把「还有一个东西在路上」说出来。
    // 不用灰色/斜体之外的额外装饰——用户的注意力应该在原文上。
    TranslationText.Text = "翻译中…";
    TransScroll.Visibility = Visibility.Visible;
    TransSep.Visibility = Visibility.Visible;
    return;
}
```

**注意措辞**：现在代码里是「正在翻译…」，用户原话写的是「翻译中...」。
用「翻译中…」（中文省略号，和项目里其它文案一致）。

### 2.2 「翻译中」这一态必须用长倒计时，不能用 3 秒

**这是分两次调后唯一的真风险**：原文显示后 3 秒卡片就关，而翻译最坏要 2.5 秒——
余量只有 0.5 秒，I/O 一抖就关在翻译到达之前，用户永远看不到译文。

改法：`translating == true` 时用 `PendingCloseDelay`（8 秒），和 `ShowFor` 认字期间同一套逻辑。

```csharp
_closeTimer.Interval = translating ? PendingCloseDelay : TimeSpan.FromSeconds(CloseDelaySeconds);
```

理由：认字期间用 8 秒是因为「有个东西在路上」，翻译期间同理。**同一个语义，同一个常数。**

### 2.3 调用时序改两段

`App.xaml.cs` `RunCaptureAsync`：

**旧**（现在线上）：
```
OCR 完成
  → card.ShowTranslating()          // 只显示「正在翻译」，原文还没出
  → await 翻译
  → card.UpdateWith(result, translation)
```

**新**：
```
OCR 完成
  → card.UpdateWith(result, null, translating: true)   // 原文 + 「翻译中…」一次到位
  → await 翻译
  → card.UpdateWith(result, translation)               // 译文补上，3 秒重新计时
```

`ShowTranslating()` 方法**直接删掉**（YAGNI，新时序用不到它，留着就是两套并存）。

翻译不启用时（`!AppSettings.TranslateEnabled`）：`card.UpdateWith(result)` 一次，和阶段三完全一致，**一行都不多**。

## §3 连带要改的口径（P0-F2 落地）

### 3.1 回放日志必须拆两段

`ReplayRunner` 现在打的是：
```
回放 行-01：成功，31 字，翻译 = 成功 36 字，端到端 1002 ms
```
`端到端` 含翻译，但**真机现在原文先出**，用户感知的「等了多久」是**认字那一段**，不是合计。
再抱着一个合计数当指标，等于量错了东西。

改成三段：
```
回放 行-01：成功，31 字，认字 780 ms / 翻译 1002 ms / 合计 1782 ms，翻译 = 成功 36 字
```

验收脚本统计时分两个数：
- **原文可见 P95** ← 认字那一段（这是用户感知的主指标）
- **译文可见 P50/P95** ← 认字 + 翻译（合计）

### 3.2 方案里耗时表必须两列分家

第十轮已提，这里再钉一遍：

| 指标 | 本地假服务器（回归用） | 真 Bing（用户实际体验） |
|---|---|---|
| 翻译单项 P50 | 46 ms | **1040 ms** |
| 翻译单项 P95 | 221 ms | **1240 ms** |

**两列不许写成同一张表的相邻格**——假服务器和真 Bing 差 20 倍，并排放一定会被误读。

### 3.3 长文本真 Bing 耗时是空白，必须补

现在真 Bing 只测过 `Hello world` / `line 1 test` 这种极短串。
300 字整块的翻译耗时**一次都没测过**。T3b 验收时必须补，至少 5 条真实游戏文本（≥200 字）。

## §4 「AI 框歪 / 要不要开识图」（用户另一问）

### 4.1 事实

我试了 `read_image` 读 `tools\日志\取证截图\sel_20261014_091520_107.png`，报：
```
model "deepseek-v4.1-flash" does not declare image input
```
**我看不见图，这是真的。**

### 4.2 但开识图治不了框歪

框歪的根因不是「看不见」，是**验收脚本用写死坐标去框一段文字，而框和文字区贴太近**。

`_p0e2_验收.py` 自己造的字窗口是 `Left=100 Top=100 Width=900 Height=420`（占 `100~1000 × 100~520`），
而框选坐标写死 `["150","150","950","450"]` —— **右边 950 离文字区右边缘 1000 只有 50px，长句会排到最右**。

日志里每次都在报警：
```
⚠️ 选区的左边、右边和下边正好顶在文字上，很可能切到了半个字
```
**这是内缩不够，不是看不见。** 给我看图我也只能猜个新坐标，还是可能歪。**治标不治本。**

### 4.3 三条真解法（都不需要识图）

**① 框选区往文字区内缩一圈**：文字窗口 `100~1000 × 100~520`，框改 `["160","160","940","480"]`，四周各留 60px。

**② 验收必须断言「认出来的内容对不对」**——现在两条断言只看卡片高度：
```
断言1 译文真画上去(开>关)：PASS
断言2 限高生效(增量 <= 220px)：PASS
```
框歪了只认到半句话，**两条照样 PASS**。必须加：
```python
assert LONG_TEXT[:20] in ocr_text                    # 开头认得对
assert LONG_TEXT[-20:] in ocr_text                   # 结尾认得对（专防框歪切尾巴）
assert len(ocr_text) >= len(LONG_TEXT) * 0.95        # 没丢大段
```

**③ 需要视觉的场景，让程序自己截图存档，人看。**
`tools\日志\取证截图\` 已有机制。真出现框歪，人打开图一眼定位，比 AI 猜坐标快。
**该加的不是「AI 识图」，是「每次真机验收自动存一张截图 + 认出来的原文」。**

### 4.4 什么时候识图真有用

**只有一种**：UI 长得丑不丑、排版有没有歪、颜色对比够不够——这类**审美判断**，图是唯一载体。
现在的任务是功能验证，不是审美。**等 T3b 主窗口设置区做完，那时候再开识图看界面是有意义的。**
