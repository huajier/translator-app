## 一、决策合并规则

用户会在 `用户版\02-决策总表.md` 里填写每个决策点的选择。AI 的处理流程是固定的四步，**不许跳步、不许变通**：

1. **逐项读取**：把 `用户版\02-决策总表.md` 从头到尾读完，建立「**决策编号 → 已选方案**」的映射表（编号形如 `2-1`、`9-4`，编号唯一，不许用「阶段 2 的第二个」这种模糊指代）。
2. **遇到留空的项，停下来问用户**，不许默认使用推荐项。一次问清同一阶段的全部留空项，问法示例：「阶段 2 的 **2-1** 与 **2-3** 你还没选，请回复 `2-1：A / 2-3：B`」。
3. **只有用户明确说「都按推荐来」时**，才使用各决策点标注的 AI 推荐项；且必须在记录里写明「本条采用 AI 推荐，用户授权原文：……」。
4. **把映射表写进 `翻译软件\tools\日志\决策执行记录.md`，每次开工前复核**。规则：
   - 每个决策点一行：`编号 | 用户选择 | 来源（用户填写 / 用户口头 / AI 推荐+用户授权）| 确认时间`；
   - 已确认项在后续阶段**不许"顺手改一下"**：要改必须重新问用户，并在记录里追加一条变更行（保留旧行，不许覆盖）；
   - 每个阶段开工前，先复核本阶段涉及的编号，缺项立即停下问；
   - 由于技术栈已确认，`0-2`（.NET 10 LTS）、`1-1`（WPF）、`4-1`/`4-2`（DeepSeek 主 + 免费谷歌/必应兜底）、`9-1`（单文件自包含 exe）以及「三种显示形态全做」视为**用户已拍板**，但仍要在记录里留行、仍不许改变其含义。

## 二、阶段开工前的自查清单

**每一条都要打勾才算「可以开工」。任何一条打不上勾，先解决它，不许先写代码。**

- [ ] 1. **上一阶段是否已验收通过**？（用户明确回复「通过」；没通过不许开工，R1）
- [ ] 2. **上一阶段的验收证据是否齐全**？（exe + 测试用例结果 + 截图/日志；没有证据 = 没做完，R4）
- [ ] 3. **是否已备份到 `翻译软件\backup\阶段N\`**？（备份的是「当前能跑的版本」，不是半成品，R8）
- [ ] 4. **本阶段的决策点是否已全部确认**？（对照 `决策执行记录.md`，缺一项就停下来问，R2）
- [ ] 5. **本阶段涉及的历史决策是否仍然成立**？（有没有被后续阶段反向影响，例如 `8-2` 影响阶段 6 的数据库位置）
- [ ] 6. **本阶段依赖的接口是否已存在**？（`ITranslationEngine` / `ITextCapture` / `IDisplayPresenter` / `IFeatureModule`，各自首成形阶段见 03 文件 §0.3）
- [ ] 7. **本阶段依赖的基础设施是否就绪**？（配置读写、日志、网络、存储，各自所属阶段见 03 文件 §0.2）
- [ ] 8. **是否已用 3-5 句话向用户说明「我要改哪些文件、改完会出现什么效果」**，并得到用户确认？（R7）
- [ ] 9. **本阶段的「改动文件清单」是否与 03 文件一致**？（路径符合四层架构，没有把后面阶段的文件提前建）
- [ ] 10. **本阶段的异常处理清单是否已读**？（03 文件对应阶段「必须实现的异常处理」，逐条要能说出实现位置）
- [ ] 11. **本阶段的性能指标是否已读**？（哪些指标会被验收，怎么测量）
- [ ] 12. **测试环境是否就绪**？（需要的测试素材、测试数据、第二块显示器、干净电脑、限速工具等）
- [ ] 13. **是否明确知道本阶段「不许做的事」**？（越界行为会导致返工，03 文件每阶段末尾已列）
- [ ] 14. **本阶段的产出物路径是否已确定**？（`release\vX.Y\`、`docs\` 哪份文档要更新、日志写哪里）
- [ ] 15. **临时脚本、测试素材、日志是否都规划在 `翻译软件\tools\` 下**？（不许污染 `翻译软件\` 根目录与 `src\`，R3）
- [ ] 16. **是否确认不会引入新的第三方依赖**？（引入前必须先问用户，并说明体积与维护代价）
- [ ] 17. **是否确认本阶段不改变已验收阶段的对外行为**？（改公共接口 / 改窗口交互都要先说明并得到同意）
- [ ] 18. **本阶段是否需要用户手动操作**？（装语言包、申请 Key、另一台电脑测试——要提前把步骤写成编号清单）
- [ ] 19. **出问题时的回退方案是否明确**？（哪份备份、怎么回退、回退后怎么重来）
- [ ] 20. **是否准备好「每完成一个阶段或每 5 个原子任务」写一次交接检查点**？（模板见第六节）

## 四、测试用例模板

**表格模板（每条用例一行，不许合并、不许省略「实际结果」列）**

| 用例编号 | 前置条件 | 操作步骤 | 期望结果 | 实际结果 | 是否通过 |
|---|---|---|---|---|---|
| T{N}-{M} | 环境/数据/开关状态 | 1. … 2. … 3. … | 可观测的现象（含数值门槛） | 实测记录（含数值/截图路径） | 通过 / 不通过 |
|  |  |  |  |  |  |

**填写规约**

1. **操作步骤**必须是「照着点鼠标就能做」的编号步骤，不许出现「验证一下功能是否正常」这种无法执行的描述。
2. **期望结果**必须可观测：要么是界面现象，要么是数值门槛，要么是文件/日志内容；不许写「应该没问题」。
3. **实际结果**必须写真实现象与测量值（例如「1.2 秒」而不是「很快」），涉及界面/日志的要附截图或日志片段路径。
4. **未测就写「未测」并注明原因**，不许留空、不许写「通过」。
5. 一个用例只测一件事；长流程拆成多条。
6. 修复后重测，要**重跑该组全部用例**（含原本通过的），并在编号后标 `(回归)`。

## 十、失败与升级规则

> 遇到失败先查这张表：**先确定失败类型，再决定重试次数，超限就按「超出后怎么办」执行**。不许凭感觉反复试。

| 失败类型 | 允许重试次数 | 超出后怎么办 |
|---|---|---|
| **安全 / 数据类失败**（写坏配置、删错数据、Key 泄露风险、覆盖用户文件、历史记录损坏） | **0 次**（一次都不许重试） | 立即停止当前动作，保留现场（备份损坏文件），向用户报告「发生了什么 + 影响范围 + 已保留的证据 + 建议的恢复方案」，等用户决定；不许「再试一次看看」 |
| **语法 / lint 类失败**（编译错误、类型错误、拼写、格式） | 3 次 | 第 3 次仍失败：把完整报错原文与已尝试的 3 种改法写给用户，说明最可能的根因，请用户确认后再动（可能需要改设计或换方案） |
| **验证类失败**（自测用例不通过、性能不达标、行为与期望不符） | 2 次 | 第 2 次仍失败：判定为「未达成」，在验收文件里写明「期望 vs 实际 vs 已尝试的修法」，按 R5 给出 2-3 个替代方案让用户重新选；**不许偷偷放宽验收标准** |
| **环境类失败**（SDK 缺失、语言包没装、没有第二台电脑、没有第二块显示器） | 1 次 | 立即停止，把「需要用户做什么」写成编号步骤（含截图指引）交给用户；在验收文件里记为「阻塞（环境）」，**不许标为通过** |
| **业务规则不明**（不知道用户想要哪种效果、决策点没选、两个决策互相冲突） | **0 次**（必须问用户） | 停下，用「问题 + 2-3 个选项 + 每个选项的代价」的形式问用户；在得到答复前，**不许写这部分代码**（R1 / R2） |
| **网络 / 远程类失败**（下载模型、拉取 version.json、调用云端 API） | 2 次 | 第 2 次仍失败：不再自动重试；**写操作（下载、上传、提交、更新）必须先确认幂等性**（同一请求执行两次是否会产生两份数据 / 重复计费），不幂等的一律不重试，改为向用户报告并给出手动步骤 |
| **第三方接口失效**（免费翻译端点失效、返回结构变化） | 1 次（换通道） | 标记该通道冷却（例如 30 分钟），切到下一个通道，并把「通道已失效」写进已知问题；不许谎称「永久可用」（非官方接口天然不保证） |
| **用户验收不通过** | 1 轮修复 | 修复后**重跑该组全部用例 + 回归 A 组**；第二轮仍不通过：把分歧点整理成「现象 / 期望 / 现状 / 可选方案」交给用户重新决定范围（可能要把该需求排到 v2.1+） |

### 10.1 反纠缠规则（硬性）

- **同一个 Bug 修 2 轮还没修好 → 标记为「已知限制」并继续**，写进「已知问题」+ FAQ（含规避方法），不许无限纠缠、不许为了它停掉整个阶段。
- 「标记为已知限制」不等于可以隐瞒：必须写清**触发条件、影响范围、临时规避方法、计划修复的版本**。
- **同一轮只改一件事**：一次改一大堆东西会导致无法定位问题；出问题时先回退到最近一个可用状态（`backup\阶段N\` 或 Git 存档点）。
- **不许用「应该可以」「大概没问题」结案**：要么给出验证证据，要么明确写「未验证 + 原因」。
- **不许为了通过验收而删测试项、放宽标准或改需求**：验收标准的任何变化都必须由用户同意，并记录在 `决策执行记录.md`。
