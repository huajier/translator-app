# 翻译软件 · 制作大纲

> 版本：v1.0
> 适用平台：Windows 10 / 11（64 位）
> 最终成品：一个 `.exe` 双击即用的划词翻译软件
> 核心功能：按住 `Ctrl + Alt` + 鼠标左键拖拽框选 → 自动翻译 → 译文显示在原文上
> 本文档受众：**完全不懂编程的你** + **负责动手的 AI**
> 状态：**等待用户勾选决策（第 3 章决策总表）后才开始制作**

---

## 第 0 章 · 这份大纲怎么用

### 0.1 三句话说明白

1. **你负责选**：每一小步我都给你 **3 个不同的方案**（方向真的不一样，不是换个说法糊弄你）。你只需要在自己的水平上挑一个，告诉我编号，比如「阶段 2 选 A、B、A」。
2. **AI 负责做**：你选完之后，AI 严格按大纲的顺序一步一步做，每做完一个阶段就停下来让你验收，**验收不通过不许往下走**。
3. **你负责试**：每个阶段都会告诉你「怎么测」和「什么样算过关」。测试的步骤全部用大白话写，照着点鼠标就行。

### 0.2 为什么每一步都要你选

因为软件是给你用的，有些东西没有标准答案，只有「你更喜欢哪个」：

- 窗口长得圆一点还是方一点？
- 翻译完 3 秒自动消失，还是等你按 Esc 才消失？
- 历史记录留 100 条还是 1000 条？

这些问题 AI 替你决定了，做出来你可能不顺眼。所以**凡是会影响你使用感受的地方，都摆出来让你挑**。

### 0.3 AI 必须遵守的铁律（这一节是给 AI 看的）

| 编号 | 铁律 |
|---|---|
| R1 | **不许跳步**。用户没选完当前阶段的决策，不许动下一阶段的代码。 |
| R2 | **不许替用户决定**。每个决策点必须停下来问，哪怕你觉得某个选项明显更好，也只能「推荐」，不能「代替选」。 |
| R3 | **不许在 `翻译软件\` 里乱建文件**。所有临时脚本、下载的安装包、测试图片、日志，一律放 `tools\` 对应子目录。 |
| R4 | **每个阶段结束必须给验收证据**：能运行的 exe（或截图/录屏）+ 一段「你自己怎么测」的说明。没有证据 = 没做完。 |
| R5 | **不许偷偷降级需求**。如果某步做不到，必须明确说「做不到，原因是 X，替代方案是 Y/Z/W」，让用户重新选。 |
| R6 | **代码必须能被未来的自己看懂**。每个模块前面写一段人话注释，说明这个模块干嘛的、怎么改。 |
| R7 | **写代码前先说人话**：用 3-5 句话说明「我要改哪个文件、改完会出现什么效果」，用户确认后再动手。 |
| R8 | **改坏了要能退回**。每个阶段开始前把当前能跑的版本复制一份到 `翻译软件\backup\阶段N\`。 |

## 阶段 0 · 开工准备

### 🎯 目标
电脑上装好「写代码的工具」，能编译出一个 Hello World 程序。这一阶段**不写任何翻译相关代码**。

### 📖 你需要先懂的三件事（大白话）

1. **什么是 .NET？**
   你可以把它想成「C# 程序的发动机」。你写的代码是图纸，.NET 是让图纸跑起来的发动机。装一次，以后都能用。

2. **什么是 SDK？**
   SDK = 工具箱。里面有发动机（运行时）+ 扳手（编译器）+ 说明书。你装 SDK 就够了，不用单独装运行时。

3. **什么是编译？**
   你写的代码是「人能看懂的字」，电脑看不懂。编译就是「翻译给电脑听」，翻译完产出一个 `.exe`，双击就能跑。

### 🤔 决策点

#### 决策 0-1：用哪个工具写代码

| 选项 | 方案 | 优点 | 缺点 | 适合谁 |
|---|---|---|---|---|
| **A** | **Visual Studio 2022 Community** | 微软官方，图形界面，点按钮就能建项目、点按钮就能运行；出错会画红线提示 | 装完占 10-20 GB；启动慢；界面复杂 | **零基础首选**。想「少踩坑、快点看到东西」选这个 |
| **B** | **VS Code + C# Dev Kit** | 轻量，装完 1-2 GB；启动快；界面清爽 | 很多操作要在终端敲命令；调试配置要自己折腾 | 愿意学一点命令行、电脑空间紧张的人 |
| **C** | **JetBrains Rider** | C# 体验最好，智能提示最强，重构最安全 | 收费（个人非商业免费，商用要钱）；中文资料少 | 打算长期学编程、以后可能靠这个吃饭的人 |

> 💡 **AI 推荐：A**。零基础用图形界面，能在前 30 分钟就看到「自己做的窗口弹出来」，这个正反馈很重要。

#### 决策 0-2：用哪个版本的 .NET

| 选项 | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **.NET 10 LTS** | 最新长期支持版，官方支持到 2028 年 11 月；性能最好 | 部分老教程对不上（但 WPF 部分基本通用） |
| **B** | **.NET 8 LTS** | 网上教程最多，遇到问题一搜就有答案 | 官方支持到 2026 年 11 月，之后不再更新安全补丁 |
| **C** | **.NET Framework 4.8** | Windows 自带，打包出来的 exe 最小（几 MB） | 技术老旧，新库基本不支持，以后想加功能会很难受 |

> 💡 **AI 推荐：A**。支持周期最长，一次装好管三年。

#### 决策 0-3：代码怎么备份

| 选项 | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **只放本地硬盘** | 最简单，什么都不用装 | 硬盘坏了 / 改乱了，全部白做，**无法回退** |
| **B** | **本地 Git 仓库** | 每次改完存一个「存档点」，随时能退回任何一步；不联网也能用 | 要学 3-5 条命令（我会给现成的，复制粘贴即可） |
| **C** | **GitHub 私有仓库** | 在 B 的基础上多一份云端备份，换电脑也能接着做 | 国内访问 GitHub 有时慢；要注册账号 |

> 💡 **AI 推荐：B**。「随时能退回上一步」对新手太重要了——改崩了不用重头来。

### 🛠 制作步骤（你来做，AI 给指令）

> ⚠️ 以下步骤全部由**你手动操作**，AI 只提供文字指令。遇到不确定的地方，把屏幕截图发给 AI 问。

**步骤 0.1 · 检查系统版本**
1. 按键盘 `Win + R`，弹出「运行」小窗
2. 输入 `winver`，回车
3. 看弹出的窗口，确认是 **Windows 10 或 11**
4. 顺便记下版本号（比如 22H2、23H2），后面可能要用

**步骤 0.2 · 检查是不是 64 位系统**
1. 按 `Win + I` 打开设置
2. 点「系统」→「关于」

## 阶段 2 · 组合键 + 拖拽监听

### 🎯 目标
在任何软件里（浏览器、PDF 阅读器、记事本），按住 `Ctrl + Alt` 再按住鼠标左键拖动，屏幕上能出现一个跟随鼠标的**半透明选框**，松手后选框消失，并且能拿到框的坐标（左上角 X/Y、宽、高）。

**注意**：这一阶段还**不取词、不翻译**，只解决「怎么知道用户在框选」。

### 📖 你需要先懂的两件事（大白话）

1. **什么是「全局钩子」？**
   普通程序只能收到「点在自己窗口上」的鼠标事件。钩子（Hook）是向 Windows 系统申请：「请把全系统的鼠标键盘动作都告诉我一份」。这样你才能在浏览器里框选也能被本软件感知到。

2. **为什么不能用普通快捷键？**
   普通快捷键（比如 `Ctrl+Alt+T`）只能识别「按下了」，识别不了「按住不放 + 拖鼠标 + 松开」这种连续动作。必须用鼠标钩子。

### 🤔 决策点

#### 决策 2-1：怎么监听全局按键和鼠标

| 选项 | 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **手写低级钩子（P/Invoke 调 Win32 API）** | 直接调用 Windows 的 `SetWindowsHookEx`，挂 `WH_MOUSE_LL` 和 `WH_KEYBOARD_LL` | 完全可控；不依赖第三方；出问题你自己能查；体积最小 | 代码量最大（约 200-300 行）；要处理 32/64 位、超时被系统摘钩等问题 |
| **B** | **用现成的开源库** | 用 `SharpHook` 或 `MouseKeyHook` 这类 NuGet 包 | 代码少一半；库作者处理了很多坑 | 多一个第三方依赖；库停止维护的话以后要自己接手；出问题要等作者 |
| **C** | **定时轮询按键状态** | 用定时器每 10 毫秒查一次 `GetAsyncKeyState` 和鼠标位置 | 代码最少（50 行）；绝对不会被系统摘钩 | **费电费 CPU**（一直在跑）；快甩鼠标时会漏事件；精度差；可能被游戏反作弊误判 |

> 💡 **AI 推荐：A**。这东西是这个软件的心脏，自己写的才能改得动。而且写一次就再也不用碰了。

#### 决策 2-2：触发方式

| 选项 | 方案 | 用户怎么操作 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **固定 `Ctrl+Alt+左键拖拽`** | 就这一种 | 代码最简单；不会误触发 | 用户想换成别的键就得改代码重新编译 |
| **B** | **可配置组合键** | 默认 `Ctrl+Alt+左键`，设置里能改成 `Ctrl+Shift+左键` 等 | 灵活；不同软件冲突时能换 | 要做设置界面（阶段 8 的事提前了）；配置格式要想清楚 |
| **C** | **双模式** | 组合键拖拽 **+** 双击 `Ctrl` 翻译剪贴板内容 | 多一种快捷用法；比如复制一段文字后双击 Ctrl 就能翻 | 功能变多，要防误触；代码多 30% |

> 💡 **AI 推荐：C**。多出来的「双击 Ctrl 翻剪贴板」非常实用（有些软件框选不了），而且实现成本不高。

#### 决策 2-3：框选时的画面反馈

| 选项 | 方案 | 用户看到什么 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **无反馈** | 什么都没有，松手后直接出译文 | 最干净、最不干扰；性能最好 | 用户不知道软件有没有响应，容易重复操作 |
| **B** | **半透明遮罩 + 亮色选框** | 整个屏幕变暗，框内保持原色，选框是蓝色边框 | 视觉最清晰；一眼看出框住了哪里；**符合主流截图工具的习惯** | 要做一个覆盖全屏的透明窗口，多一层性能开销 |
| **C** | **十字光标 + 尺寸提示** | 光标变成十字，旁边跟着小字显示「320 × 85」 | 轻量；能精确知道框多大；不用全屏窗口 | 视觉提示弱一些；屏幕内容复杂时看不清 |

> 💡 **AI 推荐：B**。用户框选时最怕「我框对了吗」，全屏遮罩能给出最明确的答案。

### 🛠 制作步骤

**AI 要做的事：**
1. 在 `src\` 下新建独立模块（比如 `InputHook` 项目或文件夹）
2. 实现低级鼠标钩子：捕获左键按下 / 移动 / 抬起
3. 实现低级键盘钩子（或实时查键状态）：判断 Ctrl 和 Alt 是否按住
4. 实现状态机：`空闲 → 按下(Ctrl+Alt+左键) → 拖拽中 → 抬起`，处理各种异常情况（中途松开 Ctrl、按 Esc 取消、鼠标移出屏幕）

6. 在遮罩上绘制选框
7. 松手后，把选框坐标输出到调试日志：`tools\日志\框选坐标.log`

**关键异常处理清单（AI 必须实现）：**
- 拖拽过程中松开 Ctrl 或 Alt → 取消框选
- 拖拽过程中按 Esc → 取消框选
- 框太小（小于 10×10 像素）→ 视为误触，忽略
- 多显示器 → 坐标要正确（注意每个显示器的缩放比例）
- 屏幕缩放 125% / 150% → 坐标要换算回真实像素

**你（用户）要做的事：**
1. 运行新版本
2. 在浏览器、记事本、PDF 里各试一次框选
3. 看提示框和日志里的坐标对不对

## 阶段 3 · 取词（把框里的内容变成文字）

### 🎯 目标
框选之后，能拿到框里的**文字内容**（一个字符串）。这一阶段还是**不翻译**，只把文字显示在提示框里。

### 📖 你需要先懂的一件事（大白话）

**屏幕上的字，本质上是画上去的像素点**。浏览器里的文字，程序可以「读」出来（因为浏览器知道自己在显示什么）；但 PDF 扫描件、视频字幕、游戏画面里的字，程序读不出来，只能**拍照识别**。这个「拍照认字」的技术叫 **OCR**（光学字符识别）。

### 🤔 决策点

#### 决策 3-1：怎么拿到框里的文字

| 选项 | 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **纯 OCR（截图识别）** | 把框选区域截成图片，交给 OCR 引擎认字 | 通用性最强：网页、PDF、视频、游戏、图片，全都能识别；**所见即所得，框住什么就识别什么** | 识别有错误率（尤其中文小字）；识别要时间（0.2-1 秒） |
| **B** | **纯剪贴板（模拟 Ctrl+C）** | 松手后程序模拟按一下 `Ctrl+C`，然后读剪贴板 | 准确率 100%（文字本来就是文字，不用猜）；速度极快（几毫秒） | **只对「能选中文字」的软件有效**；PDF 扫描件/视频/游戏完全无效；会**覆盖你剪贴板里原来的内容** |
| **C** | **混合：剪贴板优先，失败转 OCR** | 先试 Ctrl+C，200 毫秒内剪贴板有新内容就用；没有就截图走 OCR | 两者优点都占：能选中的地方又快又准，不能选中的地方也能翻 | 代码最复杂；要处理「剪贴板没变化」的判断；要备份/还原原剪贴板 |

> 💡 **AI 推荐：C**。这是成熟划词翻译软件（有道、欧路）的标准做法。多花的功夫换来的是「什么场景都能用」。

#### 决策 3-2：用哪个 OCR 引擎

| 选项 | 方案 | 成本 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **Windows 自带 OCR**（`Windows.Media.Ocr`） | 免费 | 系统自带、无需下载模型、离线可用、速度快（几十毫秒）；微软官方维护；中英日韩都支持 | 依赖系统装了对应语言包（第一次要设置一下，我会给步骤）；对小字/花体字识别一般 |
| **B** | **Tesseract**（开源老牌） | 免费 | 完全离线；可自己训练；支持 100+ 语言；社区大 | 中文识别率明显不如现代引擎；要另外下载语言数据文件（约 15-50 MB）；速度慢（0.5-2 秒） |
| **C** | **云端 OCR**（百度 OCR / 腾讯 OCR / RapidOCR） | 前两个收费（有免费额度），RapidOCR 免费 | 识别率最高（尤其中文）；不占本地空间 | 要联网；要申请账号和 Key；有额度限制；**隐私问题**（你的屏幕内容要传到别人服务器） |

> 💡 **AI 推荐：A**。免费、离线、够快、够准，而且不用申请任何账号。**先把 A 做通，将来不满意再换成 C。**

#### 决策 3-3：识别前要不要处理图片

| 选项 | 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **不处理** | 截出来什么样就识别什么样 | 最快；代码最少 | 小字（小于 12 像素）识别率低；浅色文字/花背景容易失败 |
| **B** | **放大 + 灰度化** | 图片放大 2 倍（用高质量插值），然后转成灰度图 | 小字识别率**大幅提升**；代码不复杂；耗时增加约 50 毫秒 | 对彩色背景文字帮助有限 |
| **C** | **二值化 + 版面分析分行** | 在 B 基础上做自适应阈值二值化，再按行切分，逐行识别 | 识别率最高；能保留原文的换行结构（对阶段 7「覆盖原文」很有用） | 代码最复杂；处理耗时 200 毫秒以上；某些情况过度处理反而更差 |

> 💡 **AI 推荐：B**。性价比最高。C 的「分行」能力在阶段 7 会很有价值，那时候可以再回来升级。

## 阶段 4 · 翻译内核

### 🎯 目标
把上一步拿到的文字**翻译成目标语言**，并且做到：DeepSeek 能用就用 DeepSeek，用不了自动切到免费通道。

### 📖 你需要先懂的三件事（大白话）

1. **什么是 API？**
   API 就是「别人家服务器的点餐窗口」。你按格式递过去一句英文，它回你一句中文。你不掌握后厨（模型），只负责点餐。

2. **什么是 API Key？**
   点餐要凭证。Key 就是一串密码，代表「这顿饭记在你账上」。**泄露了别人就能花你的钱**，千万别发到群里、别传到 GitHub。

3. **为什么要有「兜底」？**
   DeepSeek 要花钱，钱花完（额度耗尽）或服务器抽风时，如果你只接了它一家，软件就直接不能用了。所以要有备胎。

### 🤔 决策点

#### 决策 4-1：主翻译引擎用哪家

| 选项 | 方案 | 价格（大致） | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **DeepSeek API** | 极便宜（百万字约几块钱） | 中文理解最好；翻译自然不像机翻；一个 Key 通用；接口和 OpenAI 兼容（代码好写） | 要充值；高峰期偶尔慢 |
| **B** | **微软 Azure Translator** | 有免费额度（每月 200 万字），超出约 ¥70/百万字 | 专业翻译引擎，术语准确；微软官方 SLA；支持语言最多 | 要注册 Azure 账号（要信用卡）；国内访问偶尔不稳 |
| **C** | **百度翻译开放平台** | 有免费额度（每月 5 万字），超出按量付费 | 国内访问最快最稳；中文场景优化好；注册简单（手机号即可） | 免费额度少；超出后比 DeepSeek 贵；翻译偏「直译」 |

> 💡 **AI 推荐：A**。你原本就选了这个方向。DeepSeek 按量付费、单价极低，日常使用一个月花不了几块钱。

#### 决策 4-2：免费的兜底通道用哪个

| 选项 | 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **谷歌翻译免费端点** | 用 `translate.googleapis.com` 的免费接口 | 翻译质量好；速度快；不需要 Key | **非官方接口**，随时可能失效；国内直连需要代理 |
| **B** | **必应/微软免费端点** | 用 Edge 浏览器翻译用的那个接口 | 质量好；国内可直连；不需要 Key | 同样是**非官方接口**；要带 token，实现稍麻烦；随时可能失效 |
| **C** | **MyMemory / LibreTranslate 公共实例** | 有官方免费额度的公益翻译 API | 有正式文档，不会突然消失；MyMemory 每天 5000 字免费 | 质量明显不如前两个；速度慢；公共实例经常限流排队 |

> 💡 **AI 推荐：A + B 都做**。反正都要写兜底逻辑，多写一个成本不高。A 不通就试 B，B 不通再试 C。**但要提醒你**：非官方接口属于「借用」，哪天失效了要接受，不能让 AI 保证永久可用。

#### 决策 4-3：什么时候切换引擎

| 选项 | 方案 | 逻辑 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **手动切换** | 设置里有个下拉框，你自己选当前用哪个 | 完全可控；逻辑最简单，几乎不会出 bug | 额度耗尽时你得自己去发现、自己去改，很烦 |
| **B** | **报错自动降级** | DeepSeek 返回错误（额度不足/超时/限流）→ 自动用免费通道；成功后**一直用免费的** | 省心；额度用完你不会察觉，翻译不会中断 | 免费通道质量差一些，你可能过了很久才发现「怎么翻得变差了」 |
| **C** | **自动降级 + 定期回探** | 在 B 基础上，每 30 分钟偷偷试一次 DeepSeek；恢复了就自动切回来，并在托盘弹个气泡告诉你 | 体验最好：既不会中断，也会自动用回好的引擎，还告知你状态 | 代码最复杂；要处理「回探失败」的静默逻辑 |

> 💡 **AI 推荐：C**。多加的代码量不多，但体验差别很大。「自动切回来了还告诉你一声」这个细节，是成熟软件和新手软件的分水岭。

### 🛠 制作步骤

**AI 要做的事：**

1. **定义统一接口**（这是「升级通道」的地基，非常关键）：
   ```
   ITranslationEngine（翻译引擎接口）
     ├─ 名字（"DeepSeek" / "Google免费" / ...）
     ├─ 是否可用（Key 填了吗？网络通吗？）
     ├─ 翻译(文本, 源语言, 目标语言) → 译文
     └─ 剩余额度（能查就查，查不到返回"未知"）
   ```
2. **实现 DeepSeek 引擎**：走 `https://api.deepseek.com/chat/completions`，用精心设计的 prompt 让它只输出译文（不要输出「好的，以下是翻译：」这种废话）
3. **实现免费引擎**：谷歌端点、必应端点各一个实现类
4. **实现调度器**：按优先级依次尝试，第一个成功就返回；全部失败返回友好错误
5. **实现降级状态机**：
   - `正常` → 用 DeepSeek
   - `降级中` → 用免费通道，同时后台每 30 分钟回探一次
   - `已恢复` → 切回 DeepSeek，托盘弹气泡提示
6. **实现本地缓存**：同样的原文 + 同样的目标语言，短时间内不重复请求（默认缓存 24 小时）
7. **实现错误处理**：网络不通、Key 错误、额度不足、超时，各有各的提示话术，不能只弹「出错了」
8. **配置项**：API Key、超时时间、引擎优先级、缓存开关

**你（用户）要做的事：**

1. **申请 DeepSeek API Key**（照着做，5 分钟）：
   - 浏览器打开 `platform.deepseek.com`
   - 手机号或邮箱注册
   - 登录后点左侧「API keys」→「创建 API key」
   - **复制那串 `sk-` 开头的字符**（只显示一次，一定要存好）
   - 到「充值」页面充 ¥10 试试（够用很久了）
   - 把这串 Key 贴给 AI 配置（或者等阶段 8 有了设置界面自己填）

   > ⚠️ **安全提醒**：这串 Key 等于你的钱包。不要发到聊天群、不要截图发出去、不要传到 GitHub。如果怀疑泄露了，立刻去网站删除重新创建一个。

2. 准备测试句子：找 10 句不同难度的英文（短句、长句、专业术语、俚语、带格式的代码）

## 阶段 5 · 显示形态 A：跟随鼠标悬浮窗 🎉

> **里程碑阶段**：做完这一阶段，你就拥有了一个**真正能用的翻译软件**。

### 🎯 目标
框选 → OCR/剪贴板取词 → 翻译 → 在鼠标旁边弹出一个小窗显示译文。加上复制按钮。

### 🤔 决策点

#### 决策 5-1：悬浮窗长什么样

| 选项 | 方案 | 视觉 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **系统默认边框窗** | 就是普通 Windows 窗口，有标题栏和关闭按钮 | 5 分钟就能做完；绝对不会出显示 bug | 丑；标题栏占地方；和「现代工具」的调性不符 |
| **B** | **无边框圆角卡片** | 白底圆角，有淡淡的阴影，右上角一个小 × | 好看；现代感强；占屏幕小 | 要自己写拖动、阴影、圆角（WPF 里不算太难） |
| **C** | **圆角卡片 + 毛玻璃/半透明** | 在 B 基础上背景半透明，能看到后面的内容（类似 Win11 的亚克力效果） | 最漂亮，不遮挡后面的内容 | 半透明文字在复杂背景上**可能看不清**；性能开销略大；某些老显卡不支持 |

> 💡 **AI 推荐：B**。C 虽然好看，但「看不清字」对翻译软件是致命伤。而且 B 可以随时升级成 C。

#### 决策 5-2：窗口出现在哪

| 选项 | 方案 | 逻辑 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **固定偏移** | 永远出现在鼠标右下角 20 像素处 | 逻辑最简单；位置可预测 | 鼠标在屏幕右边缘/下边缘时，窗口会跑到屏幕外看不见 |
| **B** | **智能避让** | 默认右下角；如果放不下就自动改成左上角/右上角/左下角，保证完整显示在屏幕内 | 永远不会跑出屏幕；体验专业 | 位置不固定，偶尔会「跳」一下 |
| **C** | **实时跟随鼠标** | 窗口一直跟着鼠标移动 | 感觉最「活」；离视线最近 | **非常干扰**：鼠标一动窗口就动，想点复制按钮都点不准 |

> 💡 **AI 推荐：B**。C 看起来酷，实际上很难用（你试试一边看译文一边鼠标不能动是什么感觉）。

#### 决策 5-3：窗口什么时候消失

| 选项 | 方案 | 行为 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **点 × 才关** | 一直留着，直到你点关闭 | 绝对不会错过内容；可以从容阅读 | 翻几次之后屏幕上堆满小窗 |
| **B** | **失焦自动消失** | 你在别的地方点一下鼠标，窗口就消失 | 符合直觉（像右键菜单）；不会堆积 | 想「对照着看」的时候容易误关 |
| **C** | **定时消失（可设置）** | 默认 5 秒后淡出，设置里可改成 3/10/30 秒或「永不」 | 最灵活；老人小孩都能用 | 读得慢的话还没看完就没了 |

> 💡 **AI 推荐：C**。默认 5 秒，但鼠标**悬停在窗口上时暂停计时**（这个细节很关键），想细看就把鼠标放上去。

### 🤔 决策点

#### 决策 6-1：面板做成什么形态

| 选项 | 方案 | 样子 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **角落固定面板** | 屏幕右下角一个固定大小的面板，永远在那儿 | 一眼就能看到历史；符合「仪表盘」直觉 | 一直占着一块屏幕；窗口最大化时可能挡住内容 |
| **B** | **贴边自动隐藏侧边栏** | 贴在屏幕右侧边缘，平时缩成一条细线，鼠标移过去才滑出来 | 不占地方；需要时才出现 | 鼠标不小心碰到边缘就会滑出来，有点烦；动画要调好 |
| **C** | **独立历史窗口** | 平时不显示，点托盘菜单「历史记录」才打开一个完整窗口 | 完全不干扰主流程；空间大，能做复杂功能（搜索、筛选、导出） | 想「快速回看刚才翻了啥」时要多两步操作 |

#### 决策 6-2：历史记录存在哪

| 选项 | 方案 | 技术 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **内存** | 一个 List 存在内存里，关掉软件就没了 | 最快；零磁盘占用；绝对不会有隐私问题 | 关了软件就清空；想看昨天的记录没戏 |
| **B** | **JSON 文件** | 存成一个 `.json` 文件，用记事本能打开看 | 简单；人可读；备份方便（复制文件就行）；出问题好排查 | 记录多了（超过 1 万条）会变慢；全文搜索要自己写 |
| **C** | **SQLite 数据库** | 存进一个 `.db` 文件，用 SQL 查询 | 快；支持复杂查询和全文搜索；记录百万条也不卡；工业标准 | 多一个依赖（约 1 MB）；要写 SQL；文件不能直接用记事本看 |

> 💡 **AI 推荐：C**。历史记录会越攒越多，一开始就选对省得以后迁移。SQLite 只有 1 MB，对体积无影响。

#### 决策 6-3：历史记录要有什么功能

| 选项 | 方案 | 功能 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **只记录 + 展示** | 按时间倒序列出，点一条能复制 | 够用；做得快 | 记录多了找不到东西 |
| **B** | **A + 搜索 + 单独复制原文/译文** | 加搜索框，能按关键词搜；每条能分别复制原文或译文 | 实用；找东西方便 | 代码量增加约 50% |
| **C** | **B + 收藏 + 导出 + 清空策略** | 再加：星标收藏、导出成 txt/csv、自动清理（比如只留最近 1000 条或 30 天） | 完整；能和别的工具配合；不会无限膨胀 | 代码量翻倍；界面要设计好，不然按钮太多反而难用 |

> 💡 **AI 推荐：C**。但**自动清理策略必须有**，不然数据库会无限长大。「收藏」的记录永远不清理，这个细节很重要。

## 阶段 7 · 显示形态 C：覆盖原文（最难的一步）

### 🎯 目标
译文像字幕一样**直接盖在原文的位置上**，视觉上像是原文被替换成了译文。

### 📖 你需要先懂的一件事（大白话）

**为什么这个最难？** 因为屏幕上的内容**不是你的软件画的**，是浏览器画的。你的软件**没有权限去修改别人画的东西**。所以「覆盖原文」实际上的做法是：

```
1. 把框选区域截图
2. 分析出原文每一行的位置和背景色
3. 在原文上面盖一块「和背景色一样」的色块（看起来像擦掉了原文）
4. 在色块上写译文（看起来像原文变成了译文）
```

本质上是「**魔术贴**」——不是真的改了，是贴上去的。

### 🤔 决策点

#### 决策 7-1：怎么「盖住」原文

| 选项 | 方案 | 做法 | 效果 | 缺点 |
|---|---|---|---|---|
| **A** | **统一半透明色块 + 译文** | 在框选区域盖一块半透明黑/白色块，上面写译文 | 实现简单；一定能盖住；视觉上明确是「翻译覆盖」 | 原来的画面被遮挡，看不到原文长什么样；色块可能和周围不协调 |
| **B** | **取样背景色填充 + 译文** | 分析原文区域的背景色（取边缘像素的平均值），用完全相同的颜色填充，再写译文 | **最像原生替换**，效果最惊艳 | 复杂：渐变背景、图片背景会穿帮；文字颜色也要跟着适配（浅底用深字，深底用浅字） |
| **C** | **不遮盖，只描边显示译文** | 原文不动，译文用描边字体（白字黑边或黑字白边）叠在上面 | 一定能看清；实现最简单；原文也还在（方便对照） | 两种文字叠在一起，会显得乱；原文密集时完全看不清 |

> 💡 **AI 推荐：B 为主，A 兜底**。先试着取样填充，如果检测到背景是渐变/图片（颜色方差太大），自动降级成 A。**C 作为快捷选项**放在设置里，给「想对照看原文」的用户。

#### 决策 7-2：译文怎么排版

| 选项 | 方案 | 排版方式 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **整段居中一行** | 所有译文拼成一段，在框里居中显示 | 最简单；短句效果好 | 长文本会溢出；和原文的行对不上，看着晕 |
| **B** | **按原文行数分行** | OCR 时记录每行的位置，译文按相同的行数分行，每行对到原来的位置 | **视觉最自然**，就像原文本身变成了中文 | 依赖 OCR 的分行能力（决策 3-3 要选 C）；中英文长度差异大时对不齐 |
| **C** | **自适应字号** | 根据框的大小和译文长度自动算字号，保证塞得下 | 永不出界；长文本也能显示 | 字号忽大忽小；太小的时候看不清 |

> 💡 **AI 推荐：B + C 结合**。按行对齐，同时每行自适应字号（有最小字号下限，低于下限就改成整段显示）。

#### 决策 7-3：覆盖层能不能点

| 选项 | 方案 | 行为 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **鼠标穿透（纯展示）** | 点覆盖层等于点下面的东西，覆盖层完全透明 | 不干扰正常使用（可以继续滚动网页、点链接）；最安全 | 不能复制译文；不能关闭（要靠快捷键或点别处） |
| **B** | **可点击复制** | 点一下覆盖层就复制译文 | 方便 | **会挡住下面的操作**（想点原文下面的按钮时点到覆盖层了） |
| **C** | **悬停显示原文对照** | 鼠标穿透；但鼠标悬停在上面时，弹一个小气泡显示原文 | 兼顾：平时不干扰，需要对照时有 | 逻辑复杂；气泡和覆盖层可能打架 |

> 💡 **AI 推荐：A**。覆盖层的定位是「看一眼就走」，不要让它拦截鼠标。复制功能悬浮窗已经有了。

### 🛠 制作步骤

**AI 要做的事：**

1. **升级 OCR 模块**：改用能返回**每个文字块坐标**的模式（如果阶段 3 选了 A，这里要补上）
2. **背景分析**：
   - 取原文区域四边的像素，算平均色和颜色方差
   - 方差小 → 纯色背景，走「取样填充」
   - 方差大 → 复杂背景，降级成「半透明色块」
3. **文字颜色自适应**：算出背景色的亮度，亮背景用深色字，暗背景用浅色字
4. **创建覆盖窗口**：
   - 位置 = 框选区域的坐标
   - 大小 = 框选区域的大小
   - 置顶、无边框、鼠标穿透（`WS_EX_TRANSPARENT | WS_EX_LAYERED`）
5. **渲染译文**：按行对齐 + 自适应字号
6. **加淡入动画**：出现时 150 毫秒淡入，比突然出现舒服
7. **关闭方式**：
   - 再次框选时，自动关掉上一个覆盖层
   - 按 `Esc` 关掉
   - 点屏幕其他地方（可选）
   - 设置里能选「自动淡出时间」
8. **兜底**：如果定位失败（比如拿不到原文行坐标），自动降级成显示悬浮窗（阶段 5 的形态），不能让用户「什么都没看到」

**你（用户）要做的事：**
1. 在**不同背景**的网页上测试：白底、深色模式、带图片的页面、带渐变的按钮
2. 反馈哪种效果不好，AI 调参数

## 阶段 8 · 设置中心

### 🎯 目标
把前面所有「写死在代码里」的东西都变成**你能自己改的**，并且做一次全面的易用性打磨。

### 🤔 决策点

#### 决策 8-1：设置界面怎么做

| 选项 | 方案 | 形式 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **独立设置窗口** | 点托盘「设置」弹出一个标准 WPF 窗口，左边分类右边内容 | 标准做法；空间大；好扩展；用户熟悉 | 要设计界面布局（约 1-2 天工作量） |
| **B** | **托盘右键菜单内嵌** | 所有设置都在右键菜单里点 | 最快；不用做界面 | 菜单层级多了很难用；改个 API Key 要翻三层菜单；做不了复杂控件 |
| **C** | **本地网页设置页** | 用 WebView2 内嵌一个 HTML 设置页 | 界面能做得很漂亮；改设置页不用重新编译主程序 | 多一个 WebView2 运行时依赖（约 100 MB，或依赖系统 Edge）；打包复杂；启动慢 |

> 💡 **AI 推荐：A**。标准、稳、好维护。C 的「漂亮」不值得多背 100 MB。

#### 决策 8-2：配置文件放哪

| 选项 | 方案 | 位置 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **exe 同目录** | `翻译软件\config.json` | 绿色软件，整个文件夹拷走就能换电脑用；一眼能看到配置 | 装在 `C:\Program Files\` 时没写权限（会失败）；容易被误删 |
| **B** | **%APPDATA%** | `C:\Users\你\AppData\Roaming\翻译软件\` | Windows 标准做法；一定有写权限；卸载时好清理 | 路径深，用户不好找；换电脑要手动拷 |
| **C** | **SQLite** | 和阶段 6 的历史数据库合并成一个文件 | 配置和历史统一管理；支持复杂结构 | 配置文件不能手动编辑了（JSON 能直接用记事本改，SQLite 不能）；配置读写出错时不好排查 |

> 💡 **AI 推荐：B，但加个「便携模式」**：默认用 `%APPDATA%`；如果 exe 同目录存在 `portable.txt` 文件，就改用 exe 同目录。这样两种需求都满足。

#### 决策 8-3：API Key 怎么保存

| 选项 | 方案 | 安全性 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **明文存 JSON** | ★☆☆☆☆ | 最简单；能直接打开看；出问题好排查 | **任何能读到你电脑文件的人/软件都能看到你的 Key**，能拿去花你的钱 |
| **B** | **DPAPI 加密后存文件** | ★★★★☆ | 用 Windows 自带的加密 API，**只有你这台电脑的这个用户**能解开；拷到别的电脑上是乱码；代码只多 20 行 | 换电脑要重新填 Key（这是好事）；用户不能手动改配置文件里的 Key |
| **C** | **Windows 凭据管理器** | ★★★★★ | 系统级保险箱，最规范；在「控制面板→凭据管理器」里能看能删 | 代码复杂一点；调试麻烦（看不到明文）；有时候会因为权限问题读不到 |

> 💡 **AI 推荐：B**。20 行代码换来「Key 不会被偷」，性价比最高。C 的安全提升有限，但麻烦不少。

**AI 要做的事：**

1. 设计配置文件结构（每一项都要有默认值，缺项也能启动）：

   - **常规**：开机自启、语言、日志级别

## 阶段 9 · 打包发布（变成一键运行的 exe）

### 🎯 目标
把开发环境里能跑的程序，变成一个**别人电脑上双击就能用**的单文件 exe。

### 📖 你需要先懂的一件事（大白话）

**为什么不能直接把开发时生成的 exe 发给别人？**
因为开发时的 exe 是「半成品」——它依赖你电脑上装的 .NET 运行时。别人电脑上没装，双击就报错「缺少 .NET」。所以打包时要选择：**是把运行时也塞进 exe（体积大但哪都能跑），还是让人家自己去装运行时（体积小但要装东西）**。

### 🤔 决策点

#### 决策 9-1：怎么打包

| 选项 | 方案 | 命令要点 | 体积 | 优点 | 缺点 |
|---|---|---|---|---|---|
| **A** | **单文件自包含 exe** | `--self-contained true -p:PublishSingleFile=true` | 约 80-150 MB | **双击就能用**，对方电脑什么都不用装；一个文件方便传输 | 体积大；每次启动要把自己解压到临时目录（首次启动慢 1-3 秒）；某些杀软会误报 |
| **B** | **框架依赖 exe** | `--self-contained false` | 约 1-3 MB | 体积最小；启动最快 | 对方必须先装 .NET 运行时，否则报错；要写安装说明 |
| **C** | **Inno Setup 安装包** | 用 B 或 A 的产物 + Inno Setup 打包成 `Setup.exe` | 30-100 MB | 专业：有安装向导、开始菜单、卸载程序、能写注册表 | 要学 Inno Setup 脚本；用户要「安装」而不是「双击」；多一道工序 |

> 💡 **AI 推荐：A**。你的硬性要求是「一键运行」，A 是唯一真正满足的。**首次启动慢的 2 秒，可以接受。**

#### 决策 9-2：怎么控制体积

| 选项 | 方案 | 效果 | 风险 |
|---|---|---|---|
| **A** | **不优化** | 约 150 MB | 无风险，最稳 |
| **B** | **开启裁剪 Trim**（`PublishTrimmed=true`） | 能降到约 40-60 MB | **WPF 不支持裁剪**！如果选 WPF 界面，这个选项会直接编译失败或用不了。如果用 WinForms 可以试 |
| **C** | **ReadyToRun + 压缩**（`PublishReadyToRun=true -p:EnableCompressionInSingleFile=true`） | 体积降到约 60-80 MB，且启动更快 | 编译时间长一点；压缩后首次启动稍慢（要解压） |

> 💡 **AI 推荐：C**。既减体积又加快启动，是目前性价比最好的组合。
> ⚠️ **重要提醒**：如果你在阶段 1 选了 WPF（推荐方案），**决策 9-2 不能选 B**，WPF 和裁剪不兼容。这在打包时会直接报错，到时候别慌，改回 A 或 C 就行。

#### 决策 9-3：开机自动启动怎么做

| 选项 | 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **注册表 Run 键** | 往 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 写一条 | 标准做法；任务管理器的「启动」标签里能看到，用户能自己关 | 杀软可能报警（写注册表是敏感行为） |
| **B** | **启动文件夹快捷方式** | 在 `shell:startup` 文件夹里放一个快捷方式 | 用户最容易理解（打开文件夹就能看到、能删）；杀软不报警 | 相对老派；路径要处理中文 |
| **C** | **任务计划程序** | 创建一个延迟 30 秒启动的计划任务 | 能设置延迟（等系统启动完再启动，不拖慢开机）；能设最高权限 | 实现最复杂；用户不好自己管理；调试麻烦 |

> 💡 **AI 推荐：A**。标准且用户可控。**默认关闭**，让用户自己开（不要默认就开机自启，那叫流氓软件）。

#### 决策 9-4：杀毒软件误报怎么办

| 选项 | 方案 | 成本 | 效果 |
|---|---|---|---|
| **A** | **买代码签名证书** | ¥1000-4000/年 | 一劳永逸：SmartScreen 不再警告，杀软基本不报；但个人开发者买 OV 证书要企业资质，EV 证书更贵 |

## 阶段 10 · 升级通道（以后能加新功能）

### 🎯 目标
让这个软件**不是一次性的**：以后你想加功能（比如翻译 PDF、朗读、截图翻译整页），不用把整个软件重写。

### 📖 你需要先懂的一件事（大白话）

**「升级通道」有两层意思：**

1. **软件能更新**：以后修了 bug、加了功能，你能拿到新版本（而不是重新下载整个软件、重新配置一遍）
2. **架构能扩展**：以后加新功能时，是「加一块积木」而不是「把房子拆了重建」

这两件事都要在**现在**就设计好，等做完了再改就来不及了。

### 🤔 决策点

#### 决策 10-1：新功能怎么加进来

| 选项 | 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **配置开关（功能都编译在主程序里）** | 所有功能都在主程序里，配置文件决定哪些显示 | 最简单；性能最好；不会出现「插件加载失败」 | 加新功能还是要更新主程序；主程序体积会慢慢变大 |
| **B** | **插件 DLL 机制** | 定义好接口，把功能做成独立的 `.dll` 文件放 `plugins\` 目录，主程序启动时扫描加载 | **加新功能不用更新主程序**；第三方也能写插件；主程序体积不变 | 要设计好接口（设计错了以后改很痛苦）；插件版本兼容问题；调试麻烦 |
| **C** | **内置脚本引擎** | 内置一个 JS/C# 脚本引擎（如 Jint / Roslyn Scripting），功能写在 `.js` 文件里 | 最灵活：改功能不用重新编译，改个文本文件就行 | 性能差；安全性差（脚本能干啥都能干）；调试困难；体积增加 |

> 💡 **AI 推荐：A 起步，B 预留**。**现在**把所有东西做成「配置开关」（A），但**接口设计成插件友好的样子**（比如 `ITranslationEngine`、`ITextCapture`、`IDisplayPresenter`）。等真的需要第三方插件时，再把 B 加上——因为接口已经在了，加 B 只需要写个「加载器」，不用改业务代码。

#### 决策 10-2：软件怎么更新

| 选项 | 方案 | 用户操作 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **手动下载覆盖** | 托盘提示「有新版本 v1.5」→ 点一下打开浏览器下载 → 自己解压覆盖 | 最简单；不用写更新逻辑；不会有「自动更新把软件搞坏」的风险 | 用户要手动操作几步 |
| **B** | **内置自动更新** | 后台自动下载新版 → 提示「重启后生效」→ 点一下自动替换并重启 | 体验最好；用户无感 | 要写：下载、校验、替换自身（exe 正在运行时不能覆盖自己，要用辅助进程） |
| **C** | **增量更新** | 只下载变化的部分（差量包） | 下载量最小 | 要搭服务器做差量计算；复杂度高一个量级；个人项目不值得 |

> 💡 **AI 推荐：A**。个人软件，A 完全够用，而且最不容易出事。**「自动更新把自己更新坏了」是真实存在的坑**，不值得为省两步操作去冒这个险。

#### 决策 10-3：接口预留到什么程度

| 选项 | 方案 | 预留的接口 | 好处 |
|---|---|---|---|
| **A** | **只留翻译引擎接口** | `ITranslationEngine` | 以后能加新翻译引擎（Claude / GPT / 本地模型） |
| **B** | **翻译 + 取词接口** | `ITranslationEngine` + `ITextCapture` | 还能加新取词方式（比如直接读 PDF 文字层、UIA 读取） |
| **C** | **三层全留** | `ITranslationEngine` + `ITextCapture` + `IDisplayPresenter` | 还能加新显示形态（比如朗读、双语对照、表格翻译） |

> 💡 **AI 推荐：C**。这三个接口本来在阶段 4/3/5 就会自然形成，把它们**正式定义成接口**只是多写几行注释的事，但带来的扩展性差别巨大。

### 🛠 制作步骤

**AI 要做的事：**

1. **接口整理**：把三个阶段自然形成的模块正式抽象成接口
   ```
   ITranslationEngine   ← 翻译引擎（阶段 4）
   ITextCapture         ← 取词方式（阶段 3）
   IDisplayPresenter    ← 显示形态（阶段 5/6/7）
   IFeatureModule       ← 功能模块（新加的统一入口）
   ```
2. **模块注册表**：所有功能模块在启动时注册到一个注册表，配置决定启用哪些
3. **版本更新检查**：
   - 在服务器（或者 GitHub Releases）放一个 `version.json`：
     ```json
     { "版本": "1.5.0", "下载地址": "https://...", "更新说明": "...", "发布日期": "..." }
     ```
   - 软件启动 3 秒后（不拖慢启动）去拉这个文件
   - 有新版就弹托盘气泡：「发现新版本 v1.5，点击查看」
   - 设置里能关掉更新检查
4. **写扩展开发文档** `docs\如何添加新功能.md`：
   - 加一个新翻译引擎要改哪几个文件
   - 加一个新显示形态要改哪几个文件
   - 每个接口的方法说明
   - 一个完整的例子（比如「加一个免费翻译引擎」的完整代码）
5. **功能开关**：设置里加一个「功能模块」页，能启用/禁用各个模块

**你（用户）要做的事：**
1. 想一下以后可能想加什么功能，告诉 AI 预留接口（比如「我以后想加朗读」「我想加翻译整页 PDF」）
2. 看一遍 `docs\如何添加新功能.md`，确认你看得懂（看不懂说明写得太技术了，让 AI 重写）

### ✅ 如何测试

|---|---|---|

| T10-2 | 让 AI **照着文档真的加一个新引擎**（比如加一个「假引擎」返回倒序文字） | 只加了一个新文件，**没有改动其他模块的业务代码** |
| T10-3 | 让 AI 照着文档加一个新显示形态（比如「底部横幅」） | 同上 |

- [ ] 四个接口定义清晰，有注释说明

## 阶段 11 · 本地离线翻译兜底

### 🎯 目标
**断网也能翻译**。质量不如云 API，但总比「网络连接失败」强。

### 📖 你需要先懂的一件事（大白话）

云翻译要联网。本地翻译是把一个「小号的翻译模型」下载到你电脑上，用你自己的 CPU 算。代价是：

- **模型文件大**（几百 MB 到几 GB）
- **翻译质量差一些**（尤其长句和口语）
- **吃电脑性能**（翻译时要占 CPU，笔记本会风扇响）

好处是：**不要钱、不要网、内容不外传**。

### 🤔 决策点

#### 决策 11-1：用哪个本地翻译引擎

| 选项 | 方案 | 模型大小 | 质量 | 优点 | 缺点 |
|---|---|---|---|---|---|
| **A** | **Argos Translate** | 中英各约 100 MB | ★★★☆☆ | 开箱即用，安装包一装就好；支持几十种语言对；社区活跃 | 依赖 Python 运行时（打包进 C# 程序很别扭，约多 100 MB）；翻译速度一般 |
| **B** | **CTranslate2 + OPUS-MT 模型** | 约 300 MB（量化后约 100 MB） | ★★★★☆ | 质量比 Argos 好；CTranslate2 是 C++ 写的，速度快；有 C# 绑定 | 要自己下模型、自己写加载代码；模型转换要折腾 |
| **C** | **ONNX Runtime + 量化小模型** | 约 50-150 MB | ★★★☆☆ | 体积最小；ONNX Runtime 有官方 C# 包；纯 .NET 方案，和主程序融合最好 | 要自己找合适的 ONNX 模型（中英翻译的现成 ONNX 不多）；要自己实现分词（tokenizer），这块最容易出错 |

> 💡 **AI 推荐：C**。虽然要自己处理分词，但它是**唯一能和 C# 主程序干净融合**的方案，不会引入 Python 这个庞然大物。如果嫌麻烦，就退到 B。

#### 决策 11-2：怎么集成进主程序

| 选项 | 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **打包进主程序** | 模型和推理引擎都塞进 exe | 用户无感，装完就能离线用 | exe 体积增加 100-300 MB；**不用离线功能的人也被迫下载** |
| **B** | **独立子进程** | 本地翻译做成一个独立的 `LocalTranslator.exe`，主程序用管道和它通信 | 主程序体积不变；本地翻译崩了不影响主程序；能单独升级 | 多一个进程要管理（启动、退出、崩溃重启）；通信要写协议 |
| **C** | **可选下载组件** | 主程序不带模型；用户在设置里点「下载离线翻译包」，从服务器下载 | 主程序体积最小（60-80 MB）；用户自己选要不要 | 要搭一个下载服务器（或用 GitHub Releases）；要处理下载失败、断点续传、校验 |

> 💡 **AI 推荐：C**。你的硬性要求是「一键运行的 exe」，那就让主 exe 保持轻量，离线包按需下载。**而且要默认不下载**，在设置里给一个明显的按钮。

#### 决策 11-3：模型怎么管理

| 选项 | 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|---|
| **A** | **固定内置中英模型** | 只支持中↔英 | 最简单；体积可控 | 想翻日语、韩语就没辙 |
| **B** | **用户自选语言包** | 设置里列出可选的语言对，用户勾选要哪些 | 灵活；用户只为需要的语言付体积 | 界面要设计；要处理语言包列表的更新 |
| **C** | **按需自动下载** | 用户第一次翻某个语言时，自动下载对应模型 | 最省心 | 第一次翻译要等下载（可能几分钟）；下载失败时体验差；要处理并发下载 |

> 💡 **AI 推荐：B**。让用户自己选，明确知道「我下载了什么、占了多少空间」。

### 🛠 制作步骤

**AI 要做的事：**

1. 选型调研：确认决策 11-1 选的引擎在 C# 里能跑起来（**这一步要先做一个小实验验证可行性**，不能直接开写）
2. 实现 `LocalTranslationEngine`，实现 `ITranslationEngine` 接口（阶段 10 的接口在这里发挥作用了）
3. 实现模型管理：下载、校验（MD5）、解压、删除
4. 实现调度器集成：
   - 联网时优先云 API
   - 断网时自动用本地
   - 设置里能强制「只用本地」（比如处理敏感内容时）
5. **性能优化**：模型只加载一次常驻内存；小文本批量翻译；加缓存
6. 在设置里加「离线翻译」页：下载/删除语言包、显示占用空间、测试按钮

**你（用户）要做的事：**
1. 决定要不要这个功能（如果不要，可以跳过整个阶段 11）
2. 如果要，选 1-2 个你需要的语言对

### ✅ 如何测试

| 测试项 | 怎么做 | 通过标准 |
|---|---|---|
| T11-1 | 下载中英语言包 | 能下载成功，显示进度和体积 |

### ⚠️ 常见坑

| 坑 | 症状 | 怎么办 |
|---|---|---|

## 第 6 章 · 术语表（大白话版）

| 术语 | 大白话解释 |
|---|---|
| **API** | 别人家服务器开的「点餐窗口」。你按格式递过去问题，它回你答案 |
| **API Key** | 点餐的会员卡号。代表「这顿饭记你账上」，泄露了别人能花你的钱 |
| **编译** | 把人能看懂的代码，翻译成电脑能执行的机器指令 |
| **exe** | Windows 上的可执行程序文件，双击就能运行 |
| **SDK** | 工具箱。装一次，以后写这类程序都能用 |
| **运行时 / Runtime** | 发动机。程序跑起来必须有的底层支持 |
| **框架 / Framework** | 别人写好的半成品，你在此基础上继续搭 |
| **OCR** | 光学字符识别。把图片里的文字「认」出来变成可以复制的文字 |
| **钩子 / Hook** | 向系统申请「把全系统的鼠标键盘动作告诉我一份」的权限 |
| **剪贴板** | 复制粘贴用的那块临时内存（Ctrl+C 存进去，Ctrl+V 取出来） |
| **剪贴板污染** | 软件偷偷改了你剪贴板里的内容，把你原来复制的东西弄丢了 |
| **悬浮窗** | 浮在其他窗口上面的小窗口 |
| **鼠标穿透** | 鼠标点这个窗口，等于点在它下面的东西上（窗口「透明」了） |
| **DPI / 缩放** | 屏幕显示的放大比例。150% 缩放时，界面元素看起来更大，但坐标要换算 |
| **多显示器** | 接了不止一个屏幕 |
| **单文件发布** | 把程序和它需要的一切打包成一个 exe 文件 |
| **自包含 / Self-contained** | exe 里自带运行时，别人电脑不用装任何东西 |
| **框架依赖 / Framework-dependent** | exe 很小，但别人电脑要先装运行时 |
| **裁剪 / Trim** | 打包时把用不到的代码删掉，减小体积（WPF 不支持） |
| **ReadyToRun** | 提前编译好一部分代码，让启动更快 |
| **降级 / Fallback** | 主方案不行了，自动用备用方案 |
| **兜底** | 最后一层保障，保证「再差也能用」 |
| **缓存** | 把结果先存起来，下次同样的问题直接给答案，不用再问一遍 |
| **接口 / Interface** | 一个「插座标准」。只要按这个标准做，就能插上来用 |
| **插件** | 按接口标准做的独立小模块，能插进主程序里 |
| **降级状态机** | 记录「我现在用的是主引擎还是备用引擎」的状态，以及什么时候该切换 |
| **热更新** | 改了设置不用重启软件，立即生效 |
| **防抖** | 连续快速触发时，只执行最后一次（比如拖动滑块时不要疯狂保存） |
| **内存泄漏** | 程序用过的内存没释放，越用越卡，最后崩掉 |
| **回归测试** | 改了新功能后，把老功能再测一遍，确保没改坏 |
| **里程碑** | 一个重要的阶段性成果（本项目的里程碑是阶段 5 的「核心功能闭环」） |
| **MVP** | 最小可用版本。功能最少但能用的版本 |

### 7.2 每阶段必须交付的东西

### 7.3 绝对不许做的事

| 禁止 | 原因 |
|---|---|
| ❌ 跳过决策点自己选 | 用户要的是「我选的软件」，不是「AI 觉得好的软件」 |
| ❌ 偷偷降级需求 | 做不到就说做不到，给替代方案 |

```

  1. 明确说「做不到，原因是 X」（X 要说人话）
  2. 给出 2-3 个替代方案，每个方案说明代价
  3. 等用户重新选
```
