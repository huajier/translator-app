# 01 · 方案A — 代码拆分（OcrTextCapture.cs：2842 行 → 7 个文件）

> 给谁看：**这份是给项目里的 AI 执行用的施工图**（你看不懂没关系，看 03 操作手册就行）。
> 目标一句话：**把 2842 行的 `OcrTextCapture.cs` 按职责拆成 7 个文件，一个字的逻辑都不改**，拆完以后加新语言有固定位置。
> 做完这个，接下来你想加日语/韩语/新引擎，都是"加一个文件 + 注册一行"，不用再钻进大文件里找地方。

## 一、为什么要拆（体检报告）

**现状数字（2026-10-16 实测）：**

| 位置 | 内容 | 行数 |
|---|---|---|
| 第 1–151 行 | 文件头 + 7 个门槛常量 | ~150 |
| **第 153–2337 行** | **一个方法 `CaptureAsync` —— 整套流程全在里面** | **~2190** |
| 第 2339–2388 行 | `PassResult`、`RecognizeOnce` | ~50 |
| 第 2390–2842 行 | 其余 20 个小工具方法 | ~450 |

**真正的问题不是"文件大"，是"一个方法 2190 行"**：截图、反色、第一遍、四次识别、英文/俄文/中文三个语言方向的全部规则、投票仲裁、清理收尾，全塞在 `CaptureAsync` 这一个方法里，互相之间靠几十个局部变量传来传去。

**这带来的三个具体卡点（就是你现在感觉到的天花板）：**
1. **加新语言没地方放**——没有"一个语言一个家"，加日语只能继续往大方法里塞；
2. **每改一处都在 2800 行里找位置**，改前改后全靠人工比对"有没有碰到别的分支"；
3. 注释越写越长（很多段落一半是"当年为什么这么改"的历史），因为没人敢动，只能靠注释保命。

**行业参照**（这次查的资料，两句话）：
- 工程界对单个代码文件的常见阈值是 **~800 行就该考虑拆**（超了基本等于"职责太多"）；拆分的方式里，"按职责提取成几个文件"是标准做法。
- 遗产代码"先固定当前行为、再动结构"是教科书方法（Michael Feathers 的"表征测试"）：**本项目已经在用**——`tools\探针\` 就是你们的"尺子"，每次改动前先钉行为、改完再对拍。这次拆分继续沿用同一套。

## 二、拆成什么样（目标文件地图）

**技术手法**：用 C# 的 **partial class（部分类）**——同一个类拆到多个文件，**类名不变、方法名不变、行为不变**，只是"住址"变了。

**为什么必须用 partial、不能用"独立类"**（关键依据）：
> `tools\探针\E6末尾\Program.cs` 等探针是**按「类名 + 方法名」用反射直接调真程序集里的规矩**的
> （已核实：`:37` 反射 `SecondVoteRecoversTail`、`:116` 反射 `MergeSplitDottedTokensFrom`、`:152` 反射 `DropLowScoreSingleChar`、`:215` 反射 `ClampAxis`、`:247` 反射 `FindCutEdge`、`:303` 反射 `Normalize`）。
> **partial class 拆分后类名、方法名全不变 → 探针零改动、照样能验。**
> 如果拆成"独立类"，这些探针全要跟着改——那就不叫"纯搬家"了，风险白白翻倍。

**7 个文件（全部住在 `src\Core\Capture\`，同一个类 `OcrTextCapture`）：**

| # | 新文件 | 装什么 | 来源（现行行号） | 拆完估计 |
|---|---|---|---|---|
| 1 | `OcrTextCapture.cs` | **总调度**：类头说明、属性、`CaptureAsync` 主干（截图→第一遍→分岔→收尾）、异常兜底 | 1–151 的文件头部分 + 153–407 的骨架 + 2178–2337 收尾 | ~450 行 |
| 2 | `OcrTextCapture.FirstPass.cs` | **第一遍**：深底判断/整张反色、转灰度、Windows 先认一遍、决定要不要"放大 2 倍重认" | 200–407 的主体 | ~230 行 |
| 3 | `OcrTextCapture.Foreign.cs` | **外文方向**：放大 4 倍、eng/rus/rus+eng 三个模型竞选、英文第二票、彩色底重认、四路择优、红通道、中文兜底、中英俄混排合流 | 409–1768 | ~700 行 |
| 4 | `OcrTextCapture.Chinese.cs` | **中文方向**：chi_sim 交叉验证、红通道补试、紧行距补救、第三/第四证人、点号回填 | 1770–2176 | ~500 行 |
| 5 | `OcrTextCapture.Rules.cs` | **候选之间的小裁决规矩**（一条规矩一个方法，以后改规矩只进这个文件）：劈词证据、第二票四条路、低分单字、点号合并 | 2469–2540、2539–2617、2672–2809、2810–2842 | ~300 行 |
| 6 | `OcrTextCapture.Utils.cs` | **通用小工具**：`RecognizeOnce`、`ToSoftwareBitmap`、`Preview`、`Resize`、`Fail`、一串字符判断小方法 | 2339–2467、2585–2700 | ~220 行 |
| 7 | `OcrTextCapture.Tuning.cs` | **全部门槛常量集中一处**（调参数、加语言只进这个文件）：`GoodConfidence`、`GoodConfidenceForRescue`、`LowWordScoreCeiling`、`LowWordScoreRatio`、`MinCyrillicRatioForRussian`、`MinimumAcceptableConfidence`、`PlaneNames` | 29–147 | ~140 行 |

## 三、怎么保证"一个字都不改"（三道保险）

1. **行为对照物不变**：探针（6 段合计 72 条断言）全过 + 构建 0 错误 0 警告；
2. **每步只做一步**：每步搬完就构建 + 跑探针 + `git diff` 人工通读（**diff 里只许看到"同样的代码换了个位置"，不许看到逻辑改写**）；每步一个 commit + 一个 tag，随时可退；
3. **最后一道**：全部拆完后，**交用户跑一轮快测单 28 段**（按 RULE 7，这属于"动识别框架"，若用户愿意也可以顺带全量 56 段）。成绩必须"和拆之前一样"，掉一分就停下来查。

**施工纪律（红绿灯）：**
- 🟢 **允许的附带动作**（搬家必须的）：① 新文件加 `using`；② 类声明加 `partial` 关键字；③ 新增"阶段方法"的签名与调用点（把一段代码装进方法里、原来的位置改成一句调用）；④ 注释跟着代码走。
- 🔴 **一律禁止**：改任何判断条件、改任何阈值、删注释、改日志文案（**一个标点都不许**——用户是靠日志核对成绩的）、顺手修 bug、顺手清理"死代码"、改方法名/改命名空间、动 `TesseractOcr.cs`/`ImagePreprocessor.cs`/`TextNormalizer.cs` 的任何代码。
- 🔴 **剪出来发现"要改一行才能编译"时**：先确认是不是上面🟢清单里的；是就别改，是别的就**停下来汇报**，不许顺手改。

## 四、施工步骤（每步 = 一轮 = 一次 commit + 一个 tag）

> 总时长参考：5 步可以分 2~4 次对话做完，不必一口气。
> **每一步做完都按项目的汇报格式交**：先结论（这步过了/没过），再证据（构建多少错误、探针多少条、diff 结论）。

### 第 0 步：地基（不改任何代码）
1. `git status` 确认干净；有未提交的先 `git commit`；
2. 跑一次构建确认现状是绿的：`powershell -ExecutionPolicy Bypass -File "tools\脚本\构建.ps1" -Version v0.3.3.0`（按当时版本号传，**带 v**）；
3. 跑三套探针记**基线数字**（后面每步都要对得上）：
   - `tools\探针\E6末尾`（`dotnet run -c Release`）→ 记下断言条数（当前基线：含第二票 23、点号回填 11、低分单字 10、弹框拖动 5、切边 10、折行 13，六段合计 72 条）；
   - `tools\探针\折行` → 折行对拍；
   - `tools\探针\真实数据` → 出手/救回计数；
4. 打 tag：**`V0.3.3.0-大拆分前`**（真正的"退路起点"，以后哪一步不对就从这里重来）。

### 第 1 步：工具、裁决规矩、常量搬家（零接触主流程）
1. 新建三个文件（类声明一律 `internal sealed partial class OcrTextCapture : ITextCapture`）：
   - `OcrTextCapture.Utils.cs`：搬 `PassResult`、`RecognizeOnce`、`ToSoftwareBitmap`、`Preview`、`Resize`、`Fail`、`IsAsciiAlnum`、`OnlyWhitespace`、`IsDottedToken`、`LettersAndDigitsOnly`、`HasIsolatedShortWord`、`IsCjk`；
   - `OcrTextCapture.Rules.cs`：搬 `SplitWordEvidenceFavorsCandidate`、`MergeSplitDottedTokensFrom`、`SecondVoteRecoversTail`、`IsSubsequence`、`AllowedSecondVoteDistance`、`EditDistance`、`DescribeTailGain`、`DropLowScoreSingleChar`（**连注释一起搬，注释里的历史一场别丢**）；
   - `OcrTextCapture.Tuning.cs`：搬 7 个常量（连注释一起搬）；
2. 主文件 `OcrTextCapture.cs` 的类声明同步加 `partial`；
3. **验证**：构建（0 错误 0 警告）→ 三套探针（对基线）→ `git diff` 通读（应只见"移动"）；
4. commit + tag：**`V0.3.3.0-拆分1-工具搬家`**。

### 第 2 步：把"第一遍"抽成方法，搬进 FirstPass 文件
1. 在 `CaptureAsync` 里把"深底判断/反色 → 转灰度 → 第一遍 → 放大重认判断"这一段（约 200–407 行）**原地剪成一个新方法**（先想清楚：这段"读"了哪些外层变量、"写"回哪些——读的多，写回的是 `text / lineCount / ocrMs / note / upscaled`；写成一个小结果结构体返回，`upscaled` 位图的生命周期**必须原样交给最外层 finally 释放**，不许提前 Dispose）；

3. **验证**：构建 + 探针 + diff 通读；
4. commit + tag：**`V0.3.3.0-拆分2-第一遍`**。

### 第 3 步：外文方向整体搬家（本方案最重的一步）
1. 新建 `OcrTextCapture.Foreign.cs`，把"外文方向"整段（约 409–1768 行）按现有注释分界线切成**一个入口方法 + 3~4 个子方法**（建议切法：①模型竞选〔eng+第二票+rus+rus+eng〕②彩色底重认+四路择优〔含红通道、中文兜底、英文补试〕③中文红通道补试+质量门槛+中英俄混排合流）；

## 五、以后怎么加新语言 / 加新引擎（拆完后的"插槽"）

**加一门新语言（比如日语）——3 个动作：**
1. 新建 `src\Core\Capture\OcrTextCapture.Japanese.cs`，照 `OcrTextCapture.Foreign.cs` 的"形状"写（入口方法固定签名 + 自己的助手 + 自己的常量）；
2. 在 `CaptureAsync` 的分岔处（现在分"外文 / 中文"两块）**注册一行调用**；
3. 在 `OcrTextCapture.Tuning.cs` 里加日语的门槛值。
→ **除了分岔处那一行，老语言的文件一个字不用改。**

**加一个新引擎（比如以后想试别的 OCR）：**
- 引擎封装（怎么调、怎么转图）放在 `TesseractOcr.cs` 的同类位置（或新文件）；
- "哪个引擎来认哪一段"的调度逻辑在 `OcrTextCapture.cs` 分岔处 + 对应语言文件里接线；
- 全部门槛值进 `Tuning`。
→ 这也是为什么第 1 步先把 `RecognizeOnce`/`ToSoftwareBitmap` 搬进 `Utils`——**引擎相关的基础件以后只有一处要动**。

> ⚠️ 注意（诚实交底）：partial class 是"整理遗产代码"的标准过渡手法，不是终点站。将来如果发现某两个文件"几乎从来不一起改"，那时可以考虑升级成独立类——**那是以后单独一轮的事，这次明确不做**（现在做会碰探针，得不偿失）。

## 七、风险与"什么时候停下来问用户"

| 风险 | 怎么防 |
|---|---|
| 抽方法时变量接错（编译器抓不到的） | 每切一段立刻构建；探针对拍；最后 diff 通读 + 用户快测 |

| 用户快测成绩掉了 | 立即停，跑全量 56 段 + 翻旧日志对同一段（第 12/13 次翻车教训：先翻旧日志再下结论）；**回退必须先问用户（RULE 5）** |
| 连续 3 次同一问题修不好 | 按铁律 8 停下汇报，列已试方案 |
