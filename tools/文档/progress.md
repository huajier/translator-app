> ### 丢词 / 丢空格是模型限制（查证结论，别再试）
>
> **官方 issue 确认这是 PP-OCRv5 的已知问题，不是我们的 bug：**
> - `PaddlePaddle/PaddleOCR#16231`（**至今 open**）「Spaces between words/numbers missing in pp_ocr_v5」
>   - 回复：「paddleocr 的 det 模型就是将所有数字框成一个 box」「只能微调」
> - `docling-project/docling#2887`「OCR is consistently missing spaces」
>   - wittjeff 实测：**空格丢失发生在 RapidOCR 的识别模型内部**，ch 模型 CER 0.136 vs EN 模型 0.050
> - `RapidAI/RapidOCR#636`「outputs English text without spaces on low-resolution images」（closed，无回复）
>
> **已试过并否决的解法**：
> 1. 换 `latin` rec 模型 → 空格数完全一样（16 vs 16），字母还更差
> 2. `ReturnWordBox` 词框重建 → 见上，规则自相矛盾，已回退
> 3. 加「3x 字数不许少于 1x」守卫 → 会误伤 `INT`→`INT 1` 这种真改善，**没做**
>
> **剩下的路只有「微调模型」（要几百张标注图），不在本项目范围内。**

> ### 本轮五件事（2026-11-09 ~ 11-12，全部用户实测通过）
>
> **① 俄文识别 0/11 → 11/11**
> 用户报「游戏字识别（快）能认英文不能认俄文，任何长度都乱码」。
> 根因用数字坐实（非推理）：`ppocrv5_en_dict.txt` **436 行里西里尔条目 0 条** ——
> `en` 识别头结构上不可能输出俄文。11-07 回放实证：RapidOCR 通道 339 段产出西里尔 **0 段**。
> 做法：加第二个 rec 模型 `cyrillic_PP-OCRv5_rec_mobile`（字典 850 条：西里尔 242 + 拉丁 52），
> 两个模型都跑、按判据择优。输出维度 852 = 850+2，与 en 版 438 = 436+2 同规律，接口零改动。
> 判据（离线 91 样本扫出来的，别自己调）：cyr 西里尔 ≥0.50 且脏字符 <0.02，
> 且（**cyr 分数比 en 高 ≥0.05** 或 en 混排比 ≥0.15 或 en 明显更短）；平手一律保 en。
> **试过并否决的两条路**（别再走）：闸门式（en 可疑才跑 Tesseract rus，俄文只有 8/11）；
> 纯分数判据（分低≠读错，行-18/28 内容全对被换掉）。
>
> **② 短俄文 5/9 → 9/9**
> 用户发截图：`Старые хиты` 被认成 `CTapble xitbl`。根因是 en 把俄文拼成「看起来正常的英文」
> —— 混排比 0.00、长度也够，老两条判据一条都命中不了。补了「比自信度」这第三条并联条件。
>
> **③ 长文本取词 4359 → 2969 ms**
> 两处浪费：同一张图被完整识别两遍（`TryRecognize` 那一遍结果被 `TryRecognizeBoth` 覆盖）；

### 版本号规矩（用户定的，m00478；**放慢规矩 m00017**）
四位是四个**累加计数器**：第1位=发布可用版本、第2位=阶段性更新、第3位=小阶段重要改动（换引擎/识图框架）、第4位=内部小更新（改日志/换办法）。改哪档只把那一位 +1，后面归零。

🔴 **放慢规矩（用户 2026-10-13 原话：「不要版本更新这么快……这种随时能改回去的小修改就不用变成一个新版本号了」）**：
- **攒着发**：一轮里改几处，等这一批改完要交付用户测时，**才升一次版本号**。
- **只打 commit/tag 的不算发布**：能靠 git tag 随时回退掉的小改动（改日志、加诊断、改版本显示、试一个参数），**不升版本号**，照样 commit + 打 tag 留退路。
- 什么算该升：① 用户要测的一批改动攒完；② 换引擎/换识图框架（第3位）；③ 阶段收口（第1位）。其余都不升。
- 后果：**连续几轮小改动可能都还在同一个版本号上**，这是正常的，不是漏改。

🔴 **第 4 位的新节奏（用户 m01288 拍板，2026-10-16 起生效）**：
- **每攒满 5 个小更新 → 第 4 位 +1**（例 `V0.3.4.0` → `V0.3.4.1`）。**不是每个小改动升一次**，是攒够 5 个才升一次 —— 原「放慢规矩」的具体化。
- **计数放在「★ 当前状态」块里**（写成本轮次 `n/5`），**升位后归零**。
- 为什么这么做：以前「小改动一律不升号」的结果是版本号长期停着、看不出「这批小改动攒到第几个了」。加个计数器，既不违反放慢，又能一眼看出进度。

当前 **V0.3.4.0**（2026-10-16 发布；**第 3 位 +1 = 方案A 代码拆分：`OcrTextCapture.cs` 2842 行单文件拆成 7 个 partial 文件，识别行为零改动**；用户快测 28 段 28/28 与拆前一致）。映射：v0.3.2=V0.3.2.0 → .1 字数容忍 → .2 词级自报日志 → .3 补跑诊断 → .4 page 释放修复 → .5 Otsu 修复 → .6 反色判据 → .7 比分日志 → .8 第一遍单独记分 → .9 删补跑+psm6 → .10 版本号显示四段（用户已验收） → .11 Sauvola（❌ 已证伪撤回） → .12 第四证人 chi_sim+eng（❌ 没救回 X2） → **V0.3.3.0 真把原生引擎换成 5.5.3（第 3 位：换引擎）** → **V0.3.4.0 方案A 代码拆分（第 3 位：重要结构改动）**。
